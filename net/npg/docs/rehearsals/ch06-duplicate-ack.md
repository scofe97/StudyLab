# 로그에 같은 블록이 두 번씩 나간다 (T4)

- 장: ch06
- 날짜: 2026-10-23

## 장면

혼잡한 시간대에 TFTP 서버 로그를 보면 어느 순간부터 블록마다 패킷이 두 번씩 나가고, 회선 사용량도 그만큼 늘었다. ACK 하나가 서버의 재전송 타임아웃보다 늦게 도착했을 때 서버가 어떻게 반응하는지 본다. 노트 06-02 의 서버는 번호가 다른 ACK 를 받으면 지금 블록을 곧바로 다시 보내는 결함이 있고(마법사의 제자 증후군), RFC 1123 §4.2.3.1 은 이를 금지한다. ADR 0009 는 재전송을 타임아웃 때만 하기로 정했다.

## 증상

"혼잡한 시간대 TFTP 서버 로그를 보면 어느 순간부터 블록마다 패킷이 두 번씩 나가고, 회선 사용량도 그만큼 늘었습니다."

## 실행 전 예측

사용자가 고른 예측이다. 실행 뒤에도 고치지 않는다.

**이 예측들은 눈가림이 아니다.** 첫 질문에서 사용자가 "모르겠다"를 고른 것으로 처리되어(사용자는 직접 고른 기억이 없다고 했다) 창이 "10번 장의 ACK 가 늦으면 서버가 한 번 더 보내고, 결함 있는 서버는 지난 번호의 ACK 에 다음 장을 또 보내므로 이어지는가"를 타임라인 표로 설명한 뒤에 받은 예측이다. 따라서 예측 1~3 은 메커니즘 설명을 들은 상태에서 고른 것이다.

조건: `fw.bin`(1 MiB, 512바이트 블록 2,048개 + 끝 표시 1개 = 2,049블록), 클라이언트가 10번 블록의 ACK 만 300ms 늦게 보낸다(`-ack-delay-block 10 -ack-delay 300ms`), 서버 타임아웃 200ms, 지연 없는 링크(RTT 0).

1. 결함 있는 서버(`tftpd-legacy`)의 서버 로그 `sent=`: **"2,050 안팎"**
2. 고친 서버(`tftpd`)의 서버 로그 `sent=`: **"2,050 안팎"**
3. 결함 있는 서버로 받을 때 클라이언트 로그 `dup_data=`: **"1 안팎"**
4. 결함 있는 서버에서 시작된 반복이 스스로 멈추는가: **"멈추지 않고 파일 끝까지 이어진다"**

## 실행 (사용자가 친 명령)

모든 터미널은 `orb -m ubuntu` 안에서 저장소 루트에서 쳤다. T3 에서 건 지연을 먼저 걷었다(`tc qdisc show` 가 `noqueue`).

```bash
# 터미널 2: 지연 제거 (RTT 0)
sudo ./scripts/tftp-netns.sh clear
# 터미널 1: 결함 있는 서버 (우리 서버의 지난 ACK 처리를 "곧바로 다시 보내고 재시도 하나 사용"으로 바꾼 변형)
sudo ip netns exec tftp-srv ./bin/tftpd-legacy-linux -root work/tftp/root -listen 10.69.0.1:6969 -timeout 200ms
# 터미널 2: 10번 블록의 ACK 만 300ms 늦추는 클라이언트
sudo ip netns exec tftp-cli ./bin/tftpget-linux -server 10.69.0.1:6969 -ack-delay-block 10 -ack-delay 300ms -o - fw.bin
# 터미널 1: 서버를 고친 판으로 바꿔 같은 클라이언트 명령을 다시 실행
sudo ip netns exec tftp-srv ./bin/tftpd-linux -root work/tftp/root -listen 10.69.0.1:6969 -timeout 200ms
```

`tftpd-legacy-linux` 는 저장소 작업 트리를 바꾸지 않고 scratchpad 의 복사본에서 `sendBlock` 의 지난 ACK 처리(`st.staleAcks++` 뒤)를 `continue outer` 로 바꿔 빌드했다. 노트 06-02 의 옛 루프와 같은 동작(번호가 다른 ACK 에 같은 타임아웃으로 곧바로 다시 보내고 재시도 하나를 쓴다)을 내도록 만든 것이고, 노트 코드와 바이트 단위로 같은지는 확인하지 않았다.

## 관찰

| 항목 | 결함 있는 서버 | 고친 서버 |
|---|---|---|
| 서버 `sent` | 4,089 | 2,050 |
| 서버 `stale_acks` | 2,039 | 1 |
| 서버 `timeouts` | 1 | 1 |
| 클라이언트 `dup_data` | 2,040 | 1 |
| 서버 `elapsed_ms` | 392.0 | 393.5 |
| 클라이언트 `elapsed_ms` | 397.8 | 397.6 |
| 받은 내용 | 2,049블록, 1,048,576바이트 | 같음 |

두 실행 모두 `strangers=0`, 클라이언트 `timeouts=0` 이다.

## 해석

| 예측 | 관찰 | 판정 |
|---|---|---|
| 1. 결함 서버 `sent` "2,050 안팎" | 4,089 | 빗나감 |
| 2. 고친 서버 `sent` "2,050 안팎" | 2,050 | 맞음 |
| 3. 결함 서버 클라이언트 `dup_data` "1 안팎" | 2,040 | 빗나감 |
| 4. 반복이 스스로 멈추는가 "멈추지 않고 파일 끝까지 이어진다" | 11번부터 2,049번까지 모든 블록이 두 번씩 나갔다 | 맞음 |

예측 1 과 3 이 틀렸고 4 는 맞았다. 세 예측은 서로 모순된다(4 가 맞다면 1 은 약 2배가 되어야 한다). 같은 사람이 같은 장면을 놓고 낸 예측이 "이어진다"와 "한 번 더 나가고 끝"을 동시에 믿고 있었다는 점이 이 장면의 학습 대상이다.

**메커니즘.** 클라이언트가 10번 블록의 ACK 만 300ms 늦추면 서버 타임아웃(200ms)이 먼저 와서 10번을 한 번 더 보낸다(`timeouts=1`). 클라이언트는 10번을 두 번 받아 ACK 10 을 두 번 보내므로 서버는 11번을 보낸 뒤 번호가 맞지 않는 ACK 10 을 받는다. 결함 있는 서버는 이 지난 ACK 에 11번을 곧바로 다시 보낸다. 클라이언트가 11번을 두 번 받으면 ACK 11 도 두 번 나가고, 이 일이 파일 끝까지 되풀이된다. 숫자로 보면 `sent=4,089` = 필요한 2,049 + 여분 2,040 이고, 여분은 10번의 타임아웃 재전송 1회와 11번부터 2,049번까지 지난 ACK 에 반응한 2,039회의 합이다. `stale_acks=2,039` 와 클라이언트 `dup_data=2,040` 이 같은 일을 양쪽에서 센 것이다. 첫 어긋남(ACK 하나 늦음)은 한 번뿐이었지만 이후 매 블록이 두 번 나갔다.

**고친 서버.** 지난 ACK 는 `stale_acks` 로 세기만 하고 다시 보내지 않아서(`server.go:160~161`) 재전송은 타임아웃으로 인한 1회뿐이다(`sent=2,050`, `stale_acks=1`, 클라이언트 `dup_data=1`).

**시간에는 드러나지 않는다.** 두 서버의 `elapsed_ms` 가 같다(약 393ms). 이 링크는 지연이 0 이라 여분의 패킷이 전송 시간을 늘리지 못했다. 티켓이 "회선 사용량"을 증상으로 든 이유가 이것이다. 패킷 수가 두 배인 것은 로그의 `sent` 로 보이지 시간으로는 보이지 않는다.

**점검 실수.** 사전 점검에 쓴 `pgrep -a -x tftpd-legacy-linux` 는 프로세스 이름이 15자를 넘으면 아무것도 찾지 못한다(경고 메시지로 확인). 그 점검은 의미가 없었다. 결함 서버가 남지 않았다는 근거는 같은 주소·포트로 새 서버가 시작됐다는 사실이다.
