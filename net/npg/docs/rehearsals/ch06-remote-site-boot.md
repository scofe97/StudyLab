# 원격 지사 부팅이 수십 분 걸린다 (T3)

- 장: ch06
- 날짜: 2026-10-23

## 장면

본사 랙에서는 PXE 부팅이 금방 끝나는데, RTT 가 50ms 인 지사에서는 커널과 initrd 를 받는 데만 한참 걸린다. 회선은 1Gbps 다. TFTP 는 블록 하나를 보내고 ACK 를 기다리는 정지-대기라서, 회선이 빨라도 블록 하나에 RTT 하나가 걸린다. 이 장면은 그 식의 어느 항을 blksize 협상이 바꾸는지 본다.

## 증상

"원격 지사에서는 부팅이 수십 분 걸린다. 본사 랙에서는 금방이다."

## 실행 전 예측

사용자가 실행 전에 고른 예측이다. 실행 뒤에도 고치지 않는다. windowsize 는 이번 장에서 구현하지 않아 관련 문항은 뺐다.

1. 기본 설정(블록 512바이트)으로 `boot-128k.bin`(131,072바이트)을 RTT 20ms 에서 받는 시간: **"0.1초 이하로 받는 거 아닌가?"** (회선이 1Gbps 라서 라는 전제에서 고름)
2. `-blksize 1428` 로 RTT 50ms 에서 받는 시간: **"128K 를 1428바이트로 하면 대략 100번 정도 하고, 50ms 의 100번이면 5000ms, 5초 안팎으로 예상"**
3. 서버 상한을 8192 로 올리고 `-blksize 8192` 로 받을 때(MTU 1500) IP 계층에서 생기는 일과 1428 대비 시간: **"조각나고 비슷하거나 느려진다"**
4. TFTP 정지-대기를 TCP 슬라이딩 윈도와 BDP(대역폭 × RTT)로 설명하면: **"창이 블록 1개라 BDP 대비 극히 작아 회선을 못 채운다"**

## 실행 (사용자가 친 명령)

모든 터미널은 `orb -m ubuntu` 안에서 저장소 루트(`/Users/user/study/npg-lab`)에서 쳤다. 사전 점검으로 네임스페이스·netem·남은 프로세스가 없고 두 veth 의 MTU 가 1500 임을 확인했다.

```bash
# 터미널 2: 서버용·클라이언트용 네임스페이스를 가상 케이블(veth)로 잇는다
sudo ./scripts/tftp-netns.sh up
# 터미널 1: 서버 (tftp-srv 안, 이후 blksize 8192 실험에서는 -max-blksize 8192 를 더해 다시 띄움)
sudo ip netns exec tftp-srv ./bin/tftpd-linux -root work/tftp/root -listen 10.69.0.1:6969
# 터미널 2: RTT 를 바꿔 가며 받는다 (set 의 지연은 한 방향이라 RTT 는 두 배)
sudo ./scripts/tftp-netns.sh set 10ms 0%        # RTT 20ms (RTT 0 은 set 없이)
sudo ./scripts/tftp-netns.sh set 25ms 0%        # RTT 50ms
sudo ./scripts/tftp-netns.sh set 50ms 0%        # RTT 100ms
sudo ip netns exec tftp-cli ./bin/tftpget-linux -server 10.69.0.1:6969 -o - boot-128k.bin
sudo ip netns exec tftp-cli ping -c 5 10.69.0.1  # 실제 RTT 대조군
sudo ip netns exec tftp-cli ./bin/tftpget-linux -server 10.69.0.1:6969 -blksize 1428 -o - boot-128k.bin
# blksize 8192: 서버 상한을 올려 다시 띄우고 조각을 tcpdump 로 본다
sudo ip netns exec tftp-cli tcpdump -i veth-cli -nn -c 40 'udp or (ip[6:2] & 0x1fff != 0)' > work/tftp/t3-8192.txt
sudo ip netns exec tftp-cli ./bin/tftpget-linux -server 10.69.0.1:6969 -blksize 8192 -o - boot-128k.bin
```

tcpdump 필터를 이렇게 고른 이유: `udp` 만 걸면 IP 조각 중 둘째 이후 조각은 UDP 헤더가 없어서 잡히지 않는다. 그래서 조각 오프셋이 0 이 아닌 IPv4 패킷(`ip[6:2] & 0x1fff != 0`)을 함께 건다.

## 관찰

파일은 `boot-128k.bin`(131,072바이트), 타임아웃·중복·낯선 출처는 모든 실행에서 0 이다.

| 설정 | 블록 수 | 클라이언트 `elapsed_ms` | 서버 `elapsed_ms` | 블록당 |
|---|---|---|---|---|
| RTT 0, 512 | 257 | 15.9 | 12.9 | 0.06ms |
| RTT 20, 512 | 257 | 5,872.6 | 5,862.4 | 22.85ms |
| RTT 50, 512 | 257 | 13,990.6 | 13,988.1 | 54.44ms |
| RTT 100, 512 | 257 | 26,816.5 | 26,814.4 | 104.34ms |
| RTT 50, 1428 | 92 | 4,963.2 | (줄 확보 못 함) | 53.94ms |
| RTT 50, 8192 (조각남) | 17 | 956.2 | 953.9 (`sent=18`: DATA 17 + OACK 1) | 56.24ms |

실제 RTT 를 `ping -c 5` 로 확인했다: 설정 RTT 100 에서 평균 103.3ms(mdev 0.95), 설정 RTT 50 에서 평균 53.0ms(mdev 0.95). 설정보다 약 3ms 크다.

tcpdump(blksize 8192, RTT 50): 요청은 `UDP, length 35`(RRQ), 응답 `length 15`(OACK), `length 4`(ACK 0), 이어서 블록마다 `UDP, length 8196` 한 줄과 `ip-proto-17` 다섯 줄, 그 뒤 `length 4`(ACK)가 이어진다. 블록 하나가 IP 패킷 여섯 개다. 첫 조각만 UDP 헤더가 있어 포트가 보이고, 나머지 다섯은 포트 없이 `ip-proto-17` 로만 보인다.

## 해석

예측 네 개와 관찰을 대조한다.

| 예측 | 관찰 | 판정 |
|---|---|---|
| 1. RTT 20ms, 512 → "0.1초 이하" | 5,872.6ms (약 59배) | 빗나감 |
| 2. RTT 50ms, 1428 → "100번 × 50ms = 5초 안팎" | 4,963.2ms, 블록은 92개(131,072 ÷ 1428 = 91.8) | 맞음 (블록 수 100 은 근사) |
| 3. blksize 8192 → "조각나고 비슷하거나 느려진다" | 조각남(블록당 IP 패킷 6개), 시간은 956ms 로 1428 의 약 1/5 | 조각은 맞고 시간은 빗나감 |
| 4. 윈도·BDP 설명 → "창이 블록 1개라 BDP 대비 극히 작아 회선을 못 채운다" | 아래 계산 | 맞음 |

**예측 1 이 빗나간 까닭.** 예측은 "1Gbps 라서 빠르다"에서 출발했지만, 이 프로토콜은 블록 하나를 보내고 ACK 가 올 때까지 멈추므로 시간은 회선 속도가 아니라 `블록 수 × RTT` 로 정해진다. 관찰이 이를 보여 준다. 블록 수가 257 로 같을 때 시간은 RTT 에 비례했다(RTT 20 → 50 은 2.5배에 시간 2.38배, 50 → 100 은 2배에 1.92배). 블록당 시간(22.85, 54.44, 104.34ms)은 ping 으로 잰 실제 RTT(53.0, 103.3ms)와 1~1.4ms 안에서 같다. 설정 RTT 보다 3ms 정도 큰 것은 netem 쪽(ping 도 같은 만큼 크다)에서 오고, 전송 코드 때문이 아니다.

**1Gbps 의 의미.** 블록 512바이트를 1Gbps 로 보내는 데는 약 0.004ms 가 들어 RTT 50ms 에 비하면 사실상 0 이다. 그래서 회선을 10Gbps 로 올려도 시간이 줄지 않는다.

**예측 2 가 맞은 까닭.** `블록 수 × RTT`(92 × 53ms ≈ 4.9초)가 실측과 맞는다. 블록이 2.8배 커져 대기 횟수가 257 → 92 로 줄었고 시간이 2.8배 줄었다(13,990 → 4,963ms).

**예측 3: 조각은 맞았고 시간은 틀렸다.** 8192 바이트 블록은 UDP 헤더를 더해 8204바이트이고, MTU 1500 인 링크에서는 호스트의 IP 계층이 1480바이트씩 6개로 나눈다. 받는 쪽 호스트가 합쳐서 응용에는 DATA 한 개로 올려 준다(그래서 `tftpget` 은 조각난 줄 모르고 `blocks=17` 로 센다). 시간이 오히려 줄어든 것은 이번 환경이 **손실 0%** 라서 조각의 비용이 보이지 않고, 대기 횟수가 17회로 줄어든 효과만 남았기 때문이다. 조각 하나만 유실돼도 블록 전체(8196바이트)가 사라져 다시 보내야 하는 비용은 이 실험에서 측정하지 않았다.

**예측 4.** 1Gbps 회선과 RTT 50ms 의 BDP 는 125,000,000 B/s × 0.05 s = 6,250,000바이트다. 정지-대기에서 한 번에 떠 있는 데이터는 블록 하나뿐이라 창/BDP 는 512바이트일 때 0.008%, 1428바이트일 때 0.023%, 8192바이트일 때 0.131% 다(계산값). 회선의 1% 도 못 채운다. 블록을 키우는 것은 이 비율을 올리는 방법이지만 MTU 한계(조각)에 막힌다. 근본적으로 창을 키우려면 RFC 7440 의 windowsize 가 필요하다.

**티켓의 "수십 분"과의 연결.** 측정한 블록당 54.4ms 를 쓰면 10MiB 이미지는 512바이트 블록 20,481개로 약 18.6분, 40MiB 는 약 74분이다(계산값). 블록 크기 1428 로 올리면 블록 수가 2.8분의 1 이라 같은 비율로 줄어든다.

**프로덕션이면 더 필요한 것.** windowsize(RFC 7440 §6 예시: windowsize 8, blksize 1456, 재시도 6, 타임아웃 1초)로 블록 여러 개를 한 번에 보내기. 경로 MTU 를 보고 blksize 를 고르는 로직. 이번 장에서는 구현하지 않았다.
