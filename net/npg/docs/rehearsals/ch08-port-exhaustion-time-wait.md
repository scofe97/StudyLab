# 부하 시험만 하면 포트가 바닥난다 (I3)

- 장: ch08
- 날짜: 2026-10-26 (진단은 10-27~28 에 이어서)
- 앞 장면과의 연결: I1 과 같은 v0 프록시(`0286401`, Go `http.DefaultTransport` 그대로). I1 이 "동시에 여는 연결 수 상한이 없다(`MaxConnsPerHost` 0)"의 얼굴이었다면, I3 은 같은 기본값의 다른 얼굴인 "남겨 두는 빈 연결이 호스트당 2개(`MaxIdleConnsPerHost` 0 → 2)"다.

## 신고

> "동시 50 으로 부하 시험을 하면 프록시 호스트에 TIME_WAIT 가 수만 개 쌓이고 `connect: cannot assign requested address` 가 납니다."

### 창이 몰래 켠 장애

없다. 백엔드는 기본값 그대로이고, 부하 모양(닫힌 고리 동시 50)만으로 난다.

## 진단 과정

| 순서 | 본 신호(명령·지표) | 세운 가설 | 남김 / 버림과 이유 |
|---|---|---|---|
| 1 | npgload 1초 줄: 처음 9초는 전부 200, 16:47:20 에 꺾여 이후 502 가 80% 안팎. 프록시 `reasons` 는 UF 37381 하나뿐. 로그 첫 에러 16:47:19.460 `dial tcp 192.168.139.208:9090: connect: cannot assign requested address` | TIME_WAIT 가 쌓여 출발 포트를 다 써서 새 연결을 못 열고 UF 로 실패한다 (학습자) | 남김. 무엇이 일어났는지는 이것으로 설명된다. 남은 질문은 "왜 연결을 그렇게 많이 닫았나" |
| 2 | TIME_WAIT 는 프록시 호스트에 쌓임 | 프록시가 먼저 끊었다 (학습자) | 남김. TIME_WAIT 는 먼저 닫은 쪽에 남는다 |
| 3 | 같은 신호 | 프록시가 서버로 보내는 처리량이 제한돼서 (학습자) | **버림.** v0 는 동시에 여는 연결 수 상한이 없다(`MaxConnsPerHost` 0). 제한은 여는 쪽이 아니라 남겨 두는 쪽에 있다 |
| 4 | npgwatch: 초당 1000 안팎 요청, 백엔드 열린 연결 10개 남짓 | 손님→프록시에 초당 1000 이 쌓인다 (학습자) | **버림.** `-c 50` 은 닫힌 고리라 손님 inflight 는 늘 50 이다. 꺾인 뒤의 초당 1000 은 백엔드에 가 보지도 못하고 UF 로 바로 끝나는 요청이 대부분이라 빨리 도는 것이다(UF 약 750/초) |
| 5 | 17:53:45 새 연결 1,364/초, 동시 요청은 50 | 빈 연결 50개를 남겨 두고 포트 50개로 계속 재사용하지 않나 (학습자) | 추론은 맞고 관찰이 반대다. 50개를 남겼다면 첫 1초 뒤 새 연결은 0 근처여야 한다. 매초 수천 개를 새로 연다는 것은 쓰고 난 연결을 대부분 닫는다는 뜻 |
| 6 | Go 1.25.1 `transport.go` 대조 | 빈 연결은 호스트당 2개만 남고 나머지는 닫힌다 | 남김. `DefaultTransport` 리터럴에 `MaxIdleConnsPerHost` 가 없어 0 → `maxIdleConnsPerHost()` 가 2 로 바꾼다. 돌려줄 때 풀에 이미 2개면 `errTooManyIdleHost` → `pconn.close` |
| 7 | (사고 실험) 두 값을 모두 100, 동시 300 | 200 개 요청이 버려진다 (학습자) | **버림.** 요청은 다 보내진다(연결 300 을 연다). 끝난 뒤 100 만 남고 200 을 닫는다. 버려지는 것은 연결이고 I3 이 더 큰 규모로 다시 난다 |
| 8 | 풀이 보내는 길목인가 | 풀에 2개뿐이면 2개를 못 넘겨야 한다 (학습자) | **버림.** 풀은 지름길이다. `getConn` 은 풀에서 찾고(`queueForIdleConn`), 없으면 새로 건다(`queueForDial`). 50 = 풀 2 + 새 연결 48 |
| 9 | (사고 실험) 닫힘이 없으려면 | 빈 연결 상한을 키우고 최대 연결 수를 거기에 맞춘다 (학습자) | 남김. `MaxConnsPerHost = N`, `MaxIdleConnsPerHost ≥ N` 이면 돌아온 연결이 모두 풀에 들어간다. 대가로 N 을 넘는 요청은 프록시에서 기다린다(I1 의 대기 자리 이동과 같은 문제) |

### 학습자의 원인 정리 (원문)

> I3에는 요청이 50개씩 들어옵니다 -> 프록시에서는 이 50개에 대해서 서버로 전송하는데 Idle은 2, 연결소켓 가능은 무제한이라 매번 2 + 48(새로운 소켓)이 발생합니다. -> 48의 소켓은 다시 닫아야하는데 소켓의 경우 TIME_WAIT시간동안 일시적으로 유지됩니다 -> 단 50개의 요청이 이 TIME_WAIT로 종료되는것보다 훨씬 빠르게 지금 요청되고 있기때문에 프록시에서 이 새로운 소켓이 계속해서 생성되고 포트 혹은 fd가 고갈됩니다. -> 프록시에서 더이상 제대로 처리하지 못하게되면 요청서버(클라이언트)에서부터 실패하게 됩니다.

창의 보정 두 가지: 바닥난 것은 fd 가 아니라 출발 포트다(에러가 `cannot assign requested address`, fd 고갈이면 `too many open files`). 실패는 손님 쪽에서 시작하지 않는다. 프록시의 dial 이 실패하고 프록시가 손님에게 502(UF)를 돌려준다.

## 실행 전 예측

재확인(2026-10-28)은 I1·I2 와 묶어 창이 화면 버튼으로 돌렸고, I3 은 따로 예측을 받지 않았다. 결과를 본 학습자의 말: "재사용이 굉장히 눈에 띄게 늘어난 것 같다".

## 실행 (사용자가 친 명령, OrbStack `ubuntu`)

```bash
./bin/fakeinv-linux -addr 192.168.139.208:9090
./bin/npgproxy-linux -addr 127.0.0.1:18080 -admin 127.0.0.1:18081 -upstream http://192.168.139.208:9090 2>/tmp/npgproxy.log
./bin/npgwatch-linux -proxy http://127.0.0.1:18081/debug/vars -backend http://192.168.139.208:9090/_stats
./bin/npgload-linux -url 'http://127.0.0.1:18080/v1/devices/7' -c 50 -d 60s
watch -n1 'ss -s | head -2; echo "TIME_WAIT→9090: $(ss -Htan state time-wait "( dport = :9090 )" | wc -l)"'
```

백엔드를 루프백 대신 VM 의 eth0 주소에 띄운 까닭: 이 VM 은 `net.ipv4.tcp_tw_reuse=2`(루프백에서만 TIME_WAIT 재사용)라, 127.0.0.1 로 붙이면 포트 고갈이 재현되지 않는다. 출발 포트 범위는 `ip_local_port_range` 32768–60999, 약 28,232개.

17:53 에는 npgwatch 웹 화면의 장면 버튼으로 같은 조건을 한 번 더 돌렸다.

## 포스트모템

- 근본 원인(진단까지): v0 프록시는 Go 기본 Transport 를 그대로 써서 호스트당 빈 연결을 2개만 남긴다. 동시 50 요청이 끝날 때마다 48개 연결을 프록시가 먼저 닫아 TIME_WAIT 로 남겼고, 동시 연결 상한도 없어 다음 요청마다 새로 열었다. 닫는 속도가 TIME_WAIT 60초가 풀리는 속도보다 빨라 출발 포트가 바닥났고, dial 실패가 UF → 502 로 손님에게 갔다.
- 고친 것(ADR 0012 결정 2): 나머지 풀 `MaxConnsPerHost` 24 와 `MaxIdleConnsPerHost` 24 를 같게 둬 돌아온 연결을 닫지 않는다. 동시 50 이어도 프록시 연결 24개를 계속 재사용한다(백엔드 열린 연결 25 중 1 은 npgwatch 의 `/_stats` 수집 연결로 보이나 확인하지 않았다).
- 배운 것: 남겨 두는 수(빈 연결 상한)와 여는 수(동시 연결 상한)를 함께 정해야 닫힘이 없다. 하나만 키우면 I3 이 더 큰 규모로 다시 나거나(빈 연결만), 요청이 프록시에서 기다린다(동시 상한만).

## 알려진 한계

- 16:47 실행의 TIME_WAIT 최댓값은 기록에 없다(U5 화면에만 떴다). 17:53 실행으로 보충했다.
- 16:47 의 새 연결 카운터 14,148 은 포트 범위 28,232 의 절반쯤인데 그 상태로 dial 이 실패했다. 17:53 실행의 TIME_WAIT 는 28,213 까지 찼다. 차이의 원인은 확인하지 않았다.
- 17:53:40→45 사이 TIME_WAIT 증가(약 3,300/초)가 같은 구간 새 연결/초(1,364)보다 크다. npgwatch 표본 시각이 프록시·ss 사이에 어긋난 탓으로 보이나 확인하지 않았다.

## 원문 근거

- Go 1.25.1 `net/http/transport.go:45-56` — `DefaultTransport` 리터럴. `MaxIdleConns: 100`, `MaxIdleConnsPerHost` 없음.
- 같은 파일 `:60` `const DefaultMaxIdleConnsPerHost = 2`, `:1040-1045` `maxIdleConnsPerHost()` 가 0 이면 2 를 돌려준다.
- 같은 파일 `:1115` `if len(idles) >= t.maxIdleConnsPerHost() { return errTooManyIdleHost }`, `:1034-1037` 넣지 못한 연결을 `pconn.close`.
- 같은 파일 `:1515-1516` `getConn` — 풀에서 먼저 찾고(`queueForIdleConn`), 없으면 새로 건다(`queueForDial`).
- 같은 파일 `:1568` `queueForDial` — `MaxConnsPerHost <= 0` 이면 세지 않고 바로 건다. 상한이 있으면 넘는 요청은 `connsPerHostWait` 에 줄 선다.
- 같은 파일 `:99` `idleConn map[connectMethodKey][]*persistConn`, `:2049` `connectMethodKey{proxy, scheme, addr, onlyH1}` — 풀은 Transport 하나에 하나이고 호스트별 칸으로 나뉜다.
