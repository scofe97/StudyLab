# 죽은 연결을 늦게 알아챔

- 장: ch03
- 날짜: 2026-10-21

## 장면

OrbStack `ubuntu` 한 대 안에서 provd 와 agent 를 띄워 연결을 맺고 하트비트(5초 간격, 읽기 데드라인 15초)가 오가게 둔다. 그 상태에서 `iptables` 로 7100번 포트로 가는 패킷을 조용히 버려, 케이블이 빠진 것처럼 침묵하게 만든다. 두 프로세스는 살아 있고 어느 쪽에도 오류가 나지 않는다.

## 증상

연결은 양쪽 모두 `ESTABLISHED` 로 보이지만 데이터는 한쪽에서 다른 쪽으로 가지 않는다. 어느 쪽이 얼마나 늦게 알아채는지가 관찰 대상이다.

## 실행 전 예측

- 사용자 예측: provd 가 연결 끊김을 로그에 남기기까지 **10~15초**.
- agent 쪽은 예측을 받지 않았다.

## 실행 (사용자가 친 명령)

```bash
# 터미널 1, 2: provd, agent (로그 앞에 초 단위 시각을 붙임)
./bin/provd-linux 2>&1 | while IFS= read -r l; do echo "$(date +%T) $l"; done
./bin/agent-linux 2>&1 | while IFS= read -r l; do echo "$(date +%T) $l"; done

# 터미널 3: 침묵 시작, 소켓 상태 관찰, 규칙 제거
date +%T; sudo iptables -A INPUT -i lo -p tcp --dport 7100 -j DROP
ss -tn dst 127.0.0.1:7100
sudo iptables -D INPUT -i lo -p tcp --dport 7100 -j DROP
```

## 관찰

DROP 규칙을 건 시각은 09:50:40 이다.

| 시각 | 어디서 | 무슨 일 |
|---|---|---|
| 09:50:53 | provd | 연결 하나(remote 45906)가 `i/o timeout` 으로 끊김 (DROP 뒤 13초) |
| 09:50:54 | provd | 연결 하나(remote 49126)가 `i/o timeout` 으로 끊김 (DROP 뒤 14초) |
| 09:50:54 이후 | agent 소켓(`ss`) | 상태가 `CLOSE-WAIT`, `Send-Q` 가 15, 20, 30, 35 로 늘어남 |
| 09:51:39 | agent | `write: broken pipe` 로 끊김을 알아챔, 1.13초 뒤 재접속 |
| 09:51:40 | provd | 새 연결(remote 38532) 수락 |

- provd 쪽은 예측대로 10~15초 안에 감지했다.
- agent 는 DROP 이 유지되는 동안(약 59초) 아무 로그도 남기지 않았다. `ss` 의 `Send-Q` 는 5바이트(ping 한 번)씩 늘었다.
- agent 가 알아챈 시각은 규칙을 지운 직후로 보인다. 규칙을 지운 정확한 시각은 기록하지 않았다.
- provd 로그에는 연결이 둘 있다. 두 번째(remote 45906, 09:49:58)는 `Send-Q` 가 5초마다 5바이트씩 늘었으므로 ping 을 보내는 클라이언트였다. 그러나 실험 뒤 `ss -tnp` 에는 이 소켓이 없고, 이 기록에 로그가 없는 agent 프로세스로 보이며 정체는 확인하지 못했다(첫 시도에서 띄운 agent 가 남아 새 provd 에 붙었을 가능성은 있으나 증거는 없다). 실험 뒤에는 이와 별개로 OrbStack 의 `orbstack-agent` 프로세스가 7100번에 연결해 있는 것도 보였다.
- `ss` 에서 한 소켓(49126)만 `Recv-Q` 가 1 이었다. 이유는 설명하지 못했다.
- 09:45:37 에 건 첫 시도에서는 `ss` 에 연결이 하나도 없었으므로 이 기록에서 제외한다.

## 해석

1. **provd 가 13~14초에 알아챈 이유.** 읽기 데드라인은 "마지막으로 받은 시각 + 15초" 이다. DROP 직전 1~2초 사이에 마지막 ping 이 도착했기 때문에 15초에서 그만큼 짧아졌다. 침묵이 어느 순간 시작되든 감지 시간은 10~15초 범위에 든다.
2. **agent 가 모르는 이유.** agent 는 쓰기만 하고 읽지 않는다. provd 가 닫으면서 보낸 `FIN` 은 포트 7100이 출발지라 DROP 규칙에 걸리지 않고 도착했고, 그래서 `ss` 가 `CLOSE-WAIT` 을 보였다. 그러나 agent 는 `Read` 를 부르지 않아 EOF 를 볼 기회가 없다. `Write` 는 송신 버퍼에 넣는 순간 성공하므로 `Send-Q` 만 늘어난다.
3. **agent 가 알아챈 계기는 코드가 아니라 네트워크 복구였다.** 규칙을 지우자 재전송된 데이터가 이미 닫힌 provd 소켓에 닿아 `RST` 가 돌아왔고, 그 다음 쓰기가 `broken pipe` 로 실패했다. 규칙을 두었다면 커널이 재전송을 포기할 때까지 모를 가능성이 크다. 이 ubuntu 의 `tcp_retries2` 는 15(`/proc/sys/net/ipv4/tcp_retries2`)이고, 커널 문서(docs.kernel.org, ip-sysctl)는 기본값 15 의 가상 타임아웃을 924.6초(약 15.4분)이며 "하한"이라고 적는다. 즉 약 15분 이상이다. 노트 03-03 의 "약 13~30분" 중 13분은 이 하한보다 짧아 현재 문서와 맞지 않는다. 이번에는 이 시간을 실측하지 않았다.
4. 결국 3장의 구조는 비대칭이다. provd 는 15초 안에 알아채지만 agent 는 상대의 침묵을 스스로 감지할 수단이 없다.

## 실험 2: provd 프로세스만 얼리기

### 실행 전 예측

- 사용자 예측 1: provd 를 얼린 뒤 agent 에는 **15초 안팎에 끊김이 찍힌다**.
- 사용자 예측 2(`kill -CONT` 로 풀 때): 풀면 **바로 정상으로 돌아온다**. 이유로 "context 가 그걸 감지한다"고 했으나, provd 의 `signal.NotifyContext` 는 `SIGINT`·`SIGTERM` 만 등록하고 `SIGSTOP`·`SIGCONT` 는 프로그램이 받지 못하거나(STOP) 받지 않는다(CONT). 읽기 데드라인은 ctx 와 무관하다.

### 실행

```bash
sudo kill -STOP $(pgrep -x provd-linux)   # 10:00:14
ss -tn sport = :7100 ; ss -tn dst 127.0.0.1:7100
sudo kill -CONT $(pgrep -x provd-linux)   # 10:09:36
```

### 관찰

- 얼린 뒤 provd 쪽 `Recv-Q` 가 25 → 70 → 95 → 110 → (10:05) 295 로 늘었다. agent 쪽 `Send-Q` 는 계속 0 이었다. 커널이 ACK 를 하므로 `Write` 가 계속 성공한다.
- 얼린 지 4분 52초(10:05:06)에도 agent 소켓은 `ESTAB` 이고 로컬 포트가 38532 그대로였다. agent 가 재접속했다면 포트가 바뀌었을 것이다. agent 로그는 직접 보지 못했고 포트로 추론했다.
- 풀기 직전 마지막 `Recv-Q` 관찰은 295 였고, 풀자마자(10:09:36) 같은 소켓의 `Recv-Q` 가 0 이 되었다. 37초 뒤(10:10:13)에도 `ESTAB`, 포트 38532, `Recv-Q` 0, provd 프로세스 상태 `Sl+`(정상) 였다.
- provd 로그는 직접 보지 못했다. `ss` 와 프로세스 상태로 연결이 끊기지 않았다고 판단했다.

### 해석

1. **agent 는 provd 가 얼어도 모른다.** 예측 1(15초 안팎)은 빗나갔다. 15초 데드라인은 provd 코드의 일부라서 provd 가 멈추면 검사할 주체가 없고, agent 에는 `Write` 오류가 날 경로가 없다.
2. **풀면 연결이 유지됐다.** 쌓인 ping 이 읽혀 `Recv-Q` 가 0 이 되고 연결이 끊기지 않았다. 데드라인이 이미 4분 넘게 지났는데도 타임아웃이 나지 않은 이유는 확인하지 못했다. 읽을 데이터가 이미 있어 읽기가 먼저 처리되었을 것으로 추정하지만, Go 런타임 내부를 확인하지 않은 가설이다.
3. 실험 1과 실험 2 모두에서 agent 는 상대의 침묵을 스스로 감지하지 못한다. 원인(네트워크 단절 대 프로세스 정지)이 달라도 같은 비대칭이다.

## 실험 3: 양방향 하트비트로 바꾼 뒤 provd 를 다시 얼리기

### 실행 전 예측

- 예측 4: provd 를 얼린 뒤 agent 로그에 `끊김` 이 처음 찍히기까지 **10~15초**.
- 예측 5: 약 2분 동안 `retry_in` 이 **1초, 2초, 4초… 점점 늘어난다**.

### 실행

실험 2 와 같이 provd 를 `kill -STOP` 으로 얼리고 agent 로그를 약 5분 지켜봤고 11:08:05 에 정리하며 agent 를 종료했다. 바이너리는 ping·pong 과 "첫 pong 을 받으면 백오프 초기화" 가 들어간 새 빌드다.

### 관찰

| 끊김 시각 | `retry_in` |
|---|---|
| 11:03:16 | 0.82초 |
| 11:03:32 | 2.37초 |
| 11:03:49 | 4.00초 |
| 11:04:08 | 8.98초 |
| 11:04:32 | 18.29초 |
| 11:05:05 | 29.52초 |
| 11:05:50 | 35.92초 |
| 11:06:41 | 28.48초 |
| 11:07:24 | 24.13초 |
| 11:08:04 | 31.49초 |

- 연결마다 침묵 구간은 정확히 15초였다(연결 11:03:17 → 끊김 11:03:32 등 아홉 번 반복).
- 첫 연결만 20초였다(11:02:56 → 11:03:16). 얼리기 전에 pong 을 받았고 마지막 pong 이 11:03:01 쯤이라는 역산이다.
- 연결은 매번 성공했다. 대기 후 `Dial` 이 성공하고 곧 다시 침묵했다.

### 해석

1. **예측 5 는 맞았다.** 간격이 0.82초부터 2배씩 늘어 29.5초에서 상한(30초 ±20%, 24~36초) 근처에 머문다. 35.92초는 30초에 지터 +20% 를 곱한 36초 안쪽이다.
2. **예측 4 는 판정하지 못한다.** 얼린 시각을 기록하지 않았다. 첫 `끊김` 이 마지막 pong 에서 15초 뒤라는 점은 로그와 맞지만, 얼린 시점부터의 시간은 확인하지 못했다.
3. **agent 가 이제 provd 의 침묵을 스스로 감지한다.** 실험 2 에서는 4분 52초가 지나도 몰랐다.
4. 처음 구현은 `Dial` 이 성공하면 백오프를 초기화했고, 그 결과 얼린 provd 앞에서 재시도 간격이 매번 약 1초로 고정되어 연결이 3분 35초에 13개 쌓였다(`LISTEN` 의 `Recv-Q` 13, provd 쪽 `CLOSE-WAIT` 12). 연결 성공은 프로그램이 건강하다는 증거가 못 되므로 첫 pong 기준으로 바꿨다.
5. 프로세스가 멈춰도 연결이 성공하는 이유는 handshake 와 수신 버퍼·ACK 를 커널이 대신하기 때문이다. 멈춘 프로세스는 `Accept`·`Read`·`Write` 를 하지 못할 뿐이다.
