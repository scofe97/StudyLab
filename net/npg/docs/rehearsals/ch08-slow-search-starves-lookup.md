# 검색 하나가 단건 조회까지 멈췄다 (I1)

- 장: ch08
- 날짜: 2026-10-26
- 앞 장면과의 연결: 없음 (첫 장면). v0 프록시(`0286401`, Go `http.DefaultTransport` 그대로)를 출시한 상태에서 출발한다.

## 신고

> "장비 검색이 느린 건 알고 있었는데, 10분 전부터 장비 단건 조회(`GET /v1/devices/{id}`)까지 p99 가 50ms → 8초입니다. 프록시 메모리도 계속 오릅니다."

## 실행 (사용자가 친 명령)

```bash
./bin/fakeinv -addr 127.0.0.1:9090
./bin/npgproxy -addr 127.0.0.1:18080 -admin 127.0.0.1:18081 -upstream http://127.0.0.1:9090
./bin/npgwatch -proxy http://127.0.0.1:18081/debug/vars        # http://127.0.0.1:8090
./bin/npgload -url 'http://127.0.0.1:18080/v1/devices/7' -rate 50 -poisson -d 10m -label get
./bin/npgload -url 'http://127.0.0.1:18080/v1/devices?q=edge' -rate 5 -poisson -d 10m -label search
```

이 맥에서는 java 가 `*:8080`·`*:8081` 을 잡고 있어 프록시를 18080·18081 에 띄웠다.

## 관찰

- 장애 전: get p50 6ms·p99 8ms 안팎.
- 장애 직후 몇 초는 get 이 멀쩡하다(검색이 32칸을 다 채우기 전). 그다음 `n=0` 인 초가 끼기 시작하고 get p99 가 2s → 5s → 8s 로 오른다(보정 실행 기준 장애 30초쯤 8초).
- 장애가 이어지면 get·search 모두 손님 기한 30초에 막혀 `timeout` 으로 끝난다(붕괴). 백엔드는 떠난 손님의 요청을 줄에서 빼지 않고 처리해 줄이 줄지 않는다.
- 14:48 프록시 `inflight` 913, `HeapAlloc` 약 47MB 로 오름. 백엔드 `inflight` 2965·`queued` 2933·`conns_open` 2966(15:11).
- 프록시 `reasons`: DC 49150, UC 927, UT 0 (UC 는 백엔드를 다시 띄울 때 열려 있던 연결이 끊긴 것).
- 1초 줄의 p50·p99 는 그 1초에 끝난 요청만 센다. `n=1 p50=7ms` 다음 초에 `inflight=112 n=0` 처럼, 막히기 시작한 순간이 오히려 빨라 보인다. n 과 inflight 를 같이 읽어야 한다.

### 재확인 (2026-10-28·29, npgwatch `-lab` I1 장면, 리눅스 VM)

- 결정 1~5 뒤(2026-10-28 17:17~17:21): 검색은 15초에 UT 로 끝났지만 단건 조회도 성공 0. 17:17:42 백엔드 처리 중 69(> 창구 32)·떠난 뒤 작업 5 → 17:18:02 449 → 17:20:22 2,265. 프록시가 묶는 것은 연결 32개이고, 15초에 UT 로 떠난 칸은 바로 새 요청을 보낸다. 백엔드(`honor_cancel=false`)는 떠난 요청을 끝까지 처리해(떠난 뒤 작업 초당 약 41) 창구 32 뒤 줄이 초당 약 13씩 길어졌고((2,265 − 449) ÷ 140초), 같은 줄에 선 단건 조회도 15초를 넘겼다. 실행 전체 최대 처리 중 2,433·대기 2,401.
- 결정 6 뒤(2026-10-29 10:33:10~10:34:49, 100초): 단건 조회는 고장 내내 초당 50건 모두 200. 백엔드 처리 중 최대 13·대기 0(실행 전체). 검색은 초당 5.39건 중 UO 4.38·200 0.53·UT 0.48.
- 검색 200 이 처리량(초당 1건)의 절반인 까닭: 들어옴 5/s 가 나감 1/s 를 늘 넘어 줄 7 이 꽉 찬 채로 있다. 칸을 얻는 검색은 늘 줄 끝에서 약 7초(줄 7 ÷ 초당 1건)를 기다린 것이고, 백엔드 8초를 더하면 기한 15초와 같다. 칸이 비는 간격이 들쭉날쭉해 반은 14.8초에 200, 반은 15초에 UT. UT 로 끝난 검색도 백엔드는 끝까지 처리했다(떠난 뒤 작업 0.46/s ≈ UT 0.48/s). 다만 몇 초 안에 끝나 쌓이지 않는다.
- 줄 7 은 그대로 둔다(학습자 판단). 8초 검색은 고장 때뿐이고 평소 검색 30ms 에서는 줄이 순간 몰림만 받아 준다. 고장 때 줄 7 은 검색이 쓰는 몫을 15개로 묶어 단건 조회를 지킨다. 넘침이 계속될 때 줄 길이가 곧 기다림 시간이라는 점은 ADR 0012 결과에 남겼다.

## 포스트모템

- 근본 원인(진단까지): 느려진 검색이 백엔드의 공유 창구(32)를 오래 붙잡았고, v0 프록시는 업스트림 응답 기한·연결 상한·경로별 상한이 모두 없어 들어오는 대로 백엔드에 쌓았다. 백엔드는 취소를 무시해 떠난 손님의 요청까지 처리했다.
- 고친 것(ADR 0012): 요청 전체 기한 15초로 손님보다 먼저 UT, 검색 8칸/나머지 24칸 격벽, 그리고 재확인에서 드러난 떠난 작업을 막는 풀 줄 상한(검색 7·나머지 1024, 넘치면 503 UO, 결정 6).
- 배운 것: 프록시 상한은 프록시가 쥔 연결만 센다. 백엔드가 아끼는 것은 처리 창구다. 프록시가 기한으로 떠나면 칸은 비지만 백엔드 일은 남는다. 떠나는 일 자체를 줄여야(줄 상한) 백엔드 창구가 지켜진다.
- 남은 것: 백엔드가 취소를 존중하거나(`r.Context()`) 백엔드 쪽 줄 상한을 두는 일은 8장 범위 밖(ADR 0012 단순화 목록).
