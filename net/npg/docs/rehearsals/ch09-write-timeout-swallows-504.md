# 느린 검색이 504 대신 연결 끊김으로 보인다 (J2)

- 장: ch09
- 날짜: 2026-10-30 (재검사 2026-11-01)
- 앞 장면과의 연결: J1 을 막으려고 학습자가 연습 서비스의 서버 기한 네 개(헤더 2초·전체 읽기 10초·응답 쓰기 15초·빈 연결 60초)를 프록시에 그대로 옮겼다. 그중 응답 쓰기 15초가 이 장면을 불렀다.

## 신고

> "검색이 느린 날, 손님 앱에는 504 가 아니라 '연결이 끊겼다'로 찍힙니다."

### 창이 몰래 켠 장애

조회가 1500건을 넘으면 백엔드 검색을 20초로 늦췄다(3분 뒤 되돌림).

## 진단 과정

| 순서 | 본 신호 | 세운 가설 | 남김 / 버림과 이유 |
|---|---|---|---|
| 1 | 손님: 검색 eof, p50 15.001초. 프록시: `504 UT dur=15000 bytes=0` | 프록시도 15초, 손님도 15초라 서로 끊었다 (학습자) | 버림. 손님 앱 기한은 30초다 |
| 2 | 같은 신호 | 응답 쓰기 15초는 프록시→서버 응답 받기 기한이다 (학습자) | 버림. `WriteTimeout` 은 손님 쪽 서버 기한이고, 손님 헤더를 다 읽은 순간 시계가 시작한다 |
| 3 | 업스트림 기한 15초와 응답 쓰기 15초가 같은 순간 시작 | 두 시계가 겹쳐 504 를 쓰려는 순간 이미 쓰기 기한이 지나 있었다. 시계 크기를 손님 > 프록시 > 서버로 맞춰야 한다 (학습자) | 남김 |

## 실행 전 예측

재검사 예측은 ADR 0014 「결과」에 적었다: 느린 검색은 15초에 손님에게 504 로 도착한다.

## 실행

창이 같은 스크립트로 두 바이너리를 돌렸다. 조회 초당 50 + 검색 초당 0.5, 백엔드 검색 20초, 60초.

## 전후 수치

| 지표 | 고치기 전(`WriteTimeout` 15초) | 고친 뒤(ADR 0014) |
|---|---|---|
| 손님이 받은 것 | 연결 끊김(eof) 26/26, 15.0초 | `504` 33/33, 15.0초 |
| 프록시 로그 | `504 UT bytes=0` (쓰지 못함) | `504 UT` |
| 조회 p99 | 11ms | 11ms |

프록시 로그만 보면 전후가 같다. 다른 것은 손님이 실제로 받은 것이다. 로그의 상태 코드는 "쓰려고 한 것"이지 "도착한 것"이 아니다.

## 포스트모템

- 근본 원인: `WriteTimeout` 은 응답 전체를 시계 하나로 잰다. 업스트림을 기다리는 시간까지 세므로, 업스트림 기한과 같거나 짧으면 업스트림의 실패 응답(504)을 손님에게 쓸 수 없다.
- 전체 시계와 틈 시계의 차이: 전체 시계는 "응답을 다 쓰기까지 몇 초"를 잰다. 틈 시계는 "쓰기와 쓰기 사이 몇 초"를 잰다. 업스트림을 기다리는 동안은 아무것도 쓰지 않으니 틈 시계는 돌지 않는다. 손님이 받기를 멈춘 경우만 잡는다.
- 제품은 이렇게 한다: nginx `send_timeout`, caddy `write_idle_timeout` 모두 쓰기 사이 간격이다. envoy 는 손님 쪽 쓰기 기한을 따로 두지 않는다.
- 조치(ADR 0014 결정 2): `WriteTimeout` 을 빼고 쓰기 틈 10초. 응답을 쓰는 마디가 쓸 때마다 기한을 다시 건다.
- 재발 방지: `TestClientWriteGap`(업스트림이 쓰기 틈의 두 배를 걸려도 keep-alive 두 번째 요청까지 도착), `TestNewFrontServer`(`WriteTimeout` 0). 쓰기 틈을 전체 시계로 바꾸는 고의 결함을 시험이 잡았다.

## 원문 근거

- Go 1.25.1 `net/http/server.go` 1029-1031, 3033-3038: 헤더를 읽은 뒤 `WriteTimeout` 기한을 건다.
- nginx·caddy·envoy 원문: ADR 0014 「원문 근거」.
