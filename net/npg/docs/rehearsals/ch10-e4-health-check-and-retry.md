# 한 대를 재시작했더니 502 가 찍힌다 (E4)

- 장: ch10
- 날짜: 2026-11-05
- 앞 장면과의 연결: E3 뒤, 엣지 Caddy 뒤에 npgproxy 두 대(프록시1 `127.0.0.1:28080`, 프록시2 `127.0.0.1:28082`)를 세워 `round_robin` 으로 나누는 상태에서 시작한다.

## 신고

> "한 대씩 재시작하는 배포를 했더니 남은 한 대는 멀쩡한데도 손님이 502 를 받는다."

이 장면은 Caddy 옵션을 외우는 연습이 아니다. 앞단이 뒤쪽 서버의 상태를 아는 두 길(능동 검사, 재시도)이 각각 어떤 실패를 막고 어떤 실패를 못 막는지, 그리고 둘을 겹쳤을 때 무엇이 남는지를 같은 부하에서 판마다 비교하는 장면이다. 개념 설명과 결정은 [ADR 0018](../adr/0018-npgproxy-healthz-and-drain-delay.md) 에 있다.

### 이 장면의 설정

- 바탕 설정: `deploy/caddy/scenarios/e4-two-proxies.json`. `reverse_proxy`(`@id` 는 `npg_proxy`)가 두 npgproxy 로 `round_robin` 하고, 검사도 재시도도 없다.
- 판마다 바탕 위에 관리 API 로 조각을 올린다(`cmd/npgwatch/edge.go` 의 `e4Pieces`).
  - 능동 검사: `scenarios/e4-active-health.json`. `/healthz` 를 1초마다 보고 시간제한은 500ms 다.
  - 재시도: `scenarios/e4-try-duration.json`. `round_robin`, `try_duration` 2초, `try_interval` 100ms 다.
- npgproxy: `/healthz` 는 평소 200 `ok`, 종료 신호를 받은 뒤에는 503 `draining` 이다. npgwatch 가 두 대에 `-drain-delay 5s` 를 넘긴다.
- 부하: 손님 10명이 닫힌 고리로 요청한다(응답을 받아야 다음 요청을 보낸다). 20초 동안 건다.
- 재시작: 대시보드 버튼이 프록시1 에 SIGTERM 을 보내고(`lab.go` 의 `restart`) 끝나면 바로 다시 띄운다.
- 멈춤: 프록시1 을 ■ 로 멈추면 SIGINT 로 내려가고 다시 띄우지 않는다(`lab.go` 의 `stop`). 재시작과 달리 내려간 채로 남는다.

### 드레인이 하는 일

`drainThenShutdown`(`cmd/npgproxy/main.go`)의 순서는 이렇다. 종료 신호를 받으면 `/healthz` 만 503 으로 바꾸고, `-drain-delay` 만큼 듣는 소켓을 연 채 요청을 전부 처리한 뒤 `Shutdown` 을 부른다. 드레인은 문을 닫는 것이 아니라 "곧 내려간다"는 팻말을 거는 것이다. 보내는 쪽이 팻말을 읽을 시간을 벌어 주려는 것이며, 쿠버네티스에서 파드 종료 전에 `preStop` 으로 잠깐 기다리는 것과 같은 생각이다.

판 1 앞에는 개념 질문이 하나 있었다. 한 대를 재시작하는데 멀쩡한 한 대가 남았는데도 502 가 나는 이유를 묻자 학습자는 이렇게 답했다.

> 한대를 재시작하고 나머지 한대가 멀쩡한데 502를 받으면 재시작중인 서버로 라우팅되어서 그런거 아닐까요?

맞는 답이다. `round_robin` 은 뒤쪽 서버의 상태를 모르고 절반을 내려간 서버로 보내며, 연결이 거절되면 재시도가 없는 Caddy 는 502 로 바꿔 돌려준다.

## 실행 (사용자가 친 명령)

판 버튼은 대시보드(npgwatch)에 있고, 학습자가 버튼으로 돌렸다. 버튼이 하는 일은 아래와 같다.

```bash
# 판 버튼 (board-base / board-active / board-retry / board-both): 바탕을 다시 올린 뒤 그 판의 조각을 올린다
./run.sh load scenarios/e4-two-proxies.json
./run.sh admin POST /id/npg_proxy/health_checks scenarios/e4-active-health.json   # board-active, board-both
./run.sh admin POST /id/npg_proxy/load_balancing scenarios/e4-try-duration.json   # board-retry, board-both

# 프록시1 재시작 버튼: SIGTERM 을 보내고 끝나길 기다린 뒤 다시 띄운다
# 프록시1 ■ 버튼: SIGINT 로 내리고 다시 띄우지 않는다
```

1. 판을 고른다(조각이 Caddy 에 올라간다).
2. 손님 10명 부하를 20초 건다.
3. 부하 도중에 프록시1 재시작(판 1~4) 또는 ■(변형 5·6)을 누른다.
4. 대시보드의 초 단위 성공·실패·p50·p99 와 Caddy 로그를 읽는다.

## 포스트모템

- 근본 원인
  - 기본 판의 502 는 "닫힌 문"이다. 드레인은 문을 닫는 일이 아니다. 5초 동안 듣는 소켓을 연 채 전부 처리하고(요청 하나가 8ms 라 다 끝난다) `/healthz` 만 503 으로 바꾼다. 실패는 드레인이 끝나 옛 소켓을 닫고 새 프로세스가 열기 전의 틈에서 난다. 그 틈에 Caddy 에서 프록시1 로 가는 둘째 구간이 거절(RST)되고 Caddy 가 502 로 바꾼다. 손님에서 Caddy 로 가는 첫 구간은 멀쩡하다.
  - 능동 검사는 그 틈을 문 닫기 전에 미리 뺀다. 드레인이 검사 간격과 시간제한의 합(1초 + 500ms)보다 길어야 한다. 보내는 쪽이 팻말을 읽고 빼는 것이지, 받는 쪽이 새 요청을 거절해서 막는 것이 아니다. 받는 쪽이 바로 거절하면 Caddy 가 알아채기 전(최대 1.5초 안팎)의 요청이 실패한다. 능동 판의 +1.2초에도 프록시1 이 450건을 처리했다.
  - 재시도는 에러를 막고, 능동 검사는 느려짐을 막는다. 재시도만 있으면 `round_robin` 이 죽은 프록시1 을 계속 고르고, 고를 때마다 연결이 거절되어 100ms 쉬고 다시 고른다(동전 던지기). 실패 한 번의 비용은 100ms 이고 평균 실패가 1회라 요청 평균이 약 108ms 가 된다. 멈춤 변형에서 재시도만 처리량이 약 7%, 둘 다는 약 67% 가 남은 차이가 그것이다.
  - 남는 대기와 503 은 `round_robin` 공용 카운터 경합 때문이다. 아래 원문 근거의 `Select` 는 `r.robin.Add(1)` 을 루프 안에서 `n` 번 올린다. 한 요청이 두 번 `Add(1)` 하는 사이에 다른 요청이 카운터를 올리면 두 번 다 아픈 칸(프록시1)을 뽑을 수 있고, 그러면 `nil` 이 돌아온다. 재시도가 없으면 503 이고(판 2), 재시도가 있으면 `tryAgain` 으로 100ms 대기 뒤 다시 고른다(판 4·변형 6). 프록시2 는 멀쩡한데도 일어난다.
  - 프록시가 세 대여도 생길 수 있다. 같은 칸(1과 4)이 나머지 연산으로 다시 뽑히기 때문이다. 다만 `nil` 이 되려면 기회 세 번이 모두 아픈 칸이어야 하고 그때마다 다른 손님이 끼어야 하므로 두 대일 때보다 드물다. 아픈 칸이 3분의 2 이면 다시 잦아진다.
  - 이 경합이 소스에서 일어난다는 것은 소스 읽기와 로그가 맞아떨어지는 설명이다. 직접 계측은 하지 않았다. master 의 같은 함수도 모양이 같다(2026-11-05 확인).
- 응답 시간 계산(Little 법칙)
  - 손님 10명이 닫힌 고리로 걸므로 처리량은 10 / 평균 응답시간이다. 재시도만 판의 요청 평균이 약 0.108초이면 10 / 0.108 ≈ 92건/s 이고, 관찰한 초당 88~97건과 맞는다.
  - 판 4 의 처리량 하락도 같은 식으로 설명된다. 141건 × 0.1초 = 14 손님·초가 5초 × 10명 = 50 손님·초 중에서 빠지므로 약 28% 용량 손실이고, 1200 → 약 860 이어서 관찰(840~1000)과 맞는다. 판 3 의 하락은 대기 요청이 10건뿐이라 이 설명으로는 안 된다.
  - 변형 6 도 같은 이유로 설명된다. 초당 약 30건 × 0.1초 = 항상 손님 3명분이 대기 중이고, 10명 중 3명이므로 처리량이 약 1/3 줄어 2/3 가 남는다. 판 4 는 프록시1 이 돌아와 4초 만에 끝났지만 멈춤에서는 끝나지 않는다.
- 판 3 의 처리량 하락은 기계 잡음일 가능성이 크다. 측정 직후 load average 가 22 였고 백신 프로세스의 CPU 가 278% 였으며, 앞 두 판의 드레인 구간에는 하락이 없었다. 재측정하지 않았다.
- 접근 로그에 안 보이는 재시도
  - 재시도가 있으면 최종 응답이 200 인 요청의 재시도는 접근 로그에 남지 않는다. 판 3 은 error·warn 이 0 이었고 100ms 대기는 `duration` 으로만 보였다. 에러 로그가 비었다고 건강하다고 읽으면 안 된다.
- 조치: [ADR 0018](../adr/0018-npgproxy-healthz-and-drain-delay.md)
  - npgproxy 는 `/healthz` 를 내고 `-drain-delay` 동안 503 `draining` 을 알린 뒤 닫는다. 이 실습의 값은 5초이고 일반 권장값이 아니다.
  - 앞단은 능동 검사와 재시도를 겹쳐 쓴다. 능동 검사가 느려짐을, 재시도가 에러를 막는다.
  - 고르기 경합을 고치는 방향은 카운터를 한 번만 받고 `pool[(start+i)%n]` 으로 도는 것이다. 업스트림 이슈로 낼지는 학습자가 정한다(아직 미정). 이 경합만 다룬 이슈는 검색에서 찾지 못했고, 관련 이슈 #5838 에서 메인테이너는 재시도를 끈 상태의 `no upstreams available` 을 의도대로 동작하는 것으로 봤다.
- 채점 요약
  - 판 1: 5xx 가 난다는 예측은 맞았다. 구간(드레인 중, 5초 안에 못 끝난 요청)은 틀렸다. 드레인 중에는 정상 처리되고 실패는 소켓이 닫힌 뒤 틈에서 났다.
  - 판 2: "그대로"는 개수만 보면 맞았다. 종류(502 → 503), 시점(틈 → 빠진 5초 내내), 원인(닫힌 문 → 고르기 경쟁)이 모두 바뀌었다.
  - 판 3: 드레인 중 그대로 보냄과 새 요청이 재시도로 성공함은 맞았다. 틈에 이미 연결된 요청이 장애라는 것은 틀렸다(0건. `Shutdown` 이 처리 중인 요청을 마치고 닫는다). 응답 시간은 대체로 맞았고 대가는 10건의 +100ms 였다. 끊김은 없었다.
  - 변형 5: 10초 내내 생긴다는 예측이 맞았다. 이유는 학습자가 말하지 않았다. 죽은 프록시1 을 계속 고르기 때문이다.
  - 변형 6: 감지와 대폭락 방어(약 2/3 유지)는 맞았다. "이후에는 없어진다"는 틀렸다. 대기가 내려가 있는 내내 초당 약 30건씩 이어졌다.
- 창의 실수:
  - 판 4 는 예측을 받기 전에 실행됐다. 창이 예측 질문을 낸 뒤 학습자가 바로 돌려서, 판 4 의 예측 칸은 비어 있다.
