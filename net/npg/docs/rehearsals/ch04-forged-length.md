# 길이 필드 위조

- 장: ch04
- 날짜: 2026-10-21

## 장면

OrbStack `ubuntu` 안에서 provd 를 띄우고, `cmd/forgeframe` 로 위조된 프레임 헤더를 보낸다. 두 장면을 따로 본다.

- a. `huge`: 길이 필드에 `uint32` 최댓값(4,294,967,295)을 적고 본문은 보내지 않는다.
- b. `short`: 길이 100 이라고 적고 본문은 10바이트만 보낸 뒤 연결을 닫지 않고 침묵한다.

provd 의 상한은 `MaxFrameSize` 64 KiB 이고, 읽기 데드라인은 15초(`ReadDeadline`)이다(ADR 0004, ADR 0001).

## 증상

읽는 쪽이 헤더의 길이를 믿으면 위조된 값 때문에 메모리를 크게 잡거나, 오지 않을 본문을 영원히 기다릴 수 있다. 연결이 언제, 어떻게 끊기는지가 관찰 대상이다.

## 실행 전 예측

- a: **즉시 끊김.**
- b: **아무 문제 없이 처리할 것 같다.** 근거로 "`ReadFrame` 을 보면 크기에 대해 최대 크기 초과 여부를 따지고, 이후에는 그냥 전체 읽기만 진행한다"고 적었다.

## 실행 (사용자가 친 명령)

```bash
# 모두 orb -m ubuntu 안에서
# 터미널 1: provd (로그 앞에 초 단위 시각)
./bin/provd-linux 2>&1 | while IFS= read -r l; do echo "$(date +%T) $l"; done

# 터미널 2: 위조 프레임 전송
./bin/forgeframe-linux -mode huge
./bin/forgeframe-linux -mode short

# 터미널 3: 장면 b 진행 중 provd 쪽 소켓 관찰
ss -tnp 'sport = :7100'
```

| 14:07:08 → 14:07:23 | provd | `short` 연결이 15초 뒤 `read tcp ...: i/o timeout` 으로 끊김 |

| 14:07:10, 11, 14 | provd 소켓(`ss`) | `ESTAB`, `Recv-Q` 0 |

## 해석

- a 는 예측대로 즉시 끊겼다. `ReadFrame` 이 길이를 읽은 직후 `make` 앞에서 상한과 비교하므로, 4GB 를 할당하지 않고 본문을 읽기 전에 거절한다. 오류 뒤에는 이 연결의 다음 바이트가 어디서 프레임이 시작되는지 알 수 없어서 연결을 닫는다. 리스너는 그대로라 다른 연결은 받는다.
- b 는 예측이 빗나갔다. 상한 검사는 길이 100 이 상한 안이라 통과했지만, 그 뒤 `io.ReadFull(r, body)` 는 버퍼가 찰 때까지 돌려주지 않는다. 10바이트만 와서 나머지 90바이트를 기다리다 15초 읽기 데드라인에 걸려 `i/o timeout` 으로 끊겼다. 상대가 연결을 닫았다면 `io.ErrUnexpectedEOF` 였을 것이고, 침묵이라 데드라인 오류가 나왔다.
- `Recv-Q` 가 0 인 것은 보낸 14바이트를 provd 가 이미 `ReadFull` 로 가져갔다는 추론과 맞는다. provd 메모리를 직접 본 것은 아니다.
- 데드라인은 루프마다 `ReadFrame` 앞에서 한 번 걸고 절대 시각이라 헤더와 본문을 합친 프레임 하나에 15초이다. 본문을 찔끔찔끔 보내도 15초를 넘기지 못한다.
- 남은 한계: 상한 64 KiB 와 데드라인 15초를 곱하면 연결 하나가 최대 64 KiB 를 15초 동안 붙잡을 수 있다. 연결 수 상한은 없다.
