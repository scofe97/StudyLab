# 타임아웃·재시도 값을 정해 달라는 요청 (T5)

- 장: ch06
- 날짜: 2026-10-23

## 장면

지사 회선이 가끔 손실이 난다. TFTP 서버의 타임아웃과 재시도 횟수를 얼마로 해야 하는지 근거를 달라는 요청이 왔다. ADR 0009 는 초기 타임아웃 1초, 재전송마다 2배, 같은 블록을 최대 6번으로 정했다. 이 값이 손실이 있는 회선에서 알맞은지를 측정으로 확인한다. 손실이 어떻게 생기는지는 gonet-lab 02-03 에서 이미 본 것이라 다시 보지 않는다.

## 증상

"지사 회선이 가끔 손실이 난다. timeout 과 retries 를 얼마로 해야 하는지 근거를 달라."

## 실행 전 예측

사용자가 고른 예측이다. 실행 뒤에도 고치지 않는다.

조건: `boot-32k.bin`(32,768바이트 = 512바이트 블록 64개 + 끝 표시 1개 = 65블록), 한 방향 지연 10ms(RTT 약 20ms), 클라이언트는 `-timeout 3s -retries 3` 으로 서버보다 오래 버티게 둔다.

1. 방향마다 손실 10% 일 때 DATA 한 번과 그 ACK 한 번이 둘 다 살아남을 확률: **"약 81%"**
2. 손실 10%, RTT 20ms 에서 서버 타임아웃 200ms 와 1s 의 전송 시간 차이: 처음 질문에는 "모르겠다"를 골랐다. 쉬운 설명을 들은 뒤 사용자가 이렇게 말했다. **"RTT 20ms 라면 200ms 로만 잡아도 충분하지 않을까. 어차피 20ms 안에 온다는 소리이고, 손실을 빨리 알아채고 보내는 게 좋아 보인다. 늦게 도착하면 타임아웃을 좀 여유롭게 잡아 보는 게 좋아 보인다."** 즉 200ms 쪽이 빠를 것이라는 예측이다. 이 예측은 타임아웃이 무엇인지 설명을 들은 뒤에 나온 것이다.
3. 서버 타임아웃을 RTT 보다 짧게 잡으면 늘어나는 숫자: **"timeouts 와 서버 stale_acks, 클라이언트 dup_data 도"**
4. 손실 방향마다 20%, 서버 재시도 3번일 때 65블록을 끝까지 받을 확률: 처음 질문에는 응답이 없었고, 이후 사용자가 이렇게 말했다. **"방향마다 20% 면 정상 수신은 64% 정도겠네요. 재시도까지 하면 확률이 오를 테니 그래도 80~90 은 되지 않을까?"** 블록 하나의 성공률인지 파일 전체의 성공률인지 구분하지 않은 답이다.

## 실행 (사용자가 친 명령)

터미널은 `orb -m ubuntu` 안에서 저장소 루트에서 쳤다. 네임스페이스와 `scripts/tftp-netns.sh up` 은 T3 에서 만든 것을 그대로 썼다. 서버는 `scripts/tftp-t5-grid.sh` 가 칸마다 직접 띄운다(타임아웃·재시도 값이 칸마다 다르다). 클라이언트는 `-timeout 3s -retries 3` 으로 서버보다 오래 버티게 두었고, 칸마다 같은 파일을 N 번 받는다.

```bash
# 손실 10%, 한 방향 지연 10ms(RTT 약 20ms), 서버 타임아웃 200ms·1s × 재시도 3·10, 칸마다 5번
sudo env DELAYS="10ms" LOSSES="10%" TIMEOUTS="200ms 1s" RETRIES="3 10" N=5 ./scripts/tftp-t5-grid.sh | tee work/tftp/t5-loss10.csv
# 손실 20%, 서버 타임아웃 200ms × 재시도 3·10, 칸마다 10번
sudo env DELAYS="10ms" LOSSES="20%" TIMEOUTS="200ms" RETRIES="3 10" N=10 SERVER_LOG=work/tftp/t5-server-loss20.log ./scripts/tftp-t5-grid.sh | tee work/tftp/t5-loss20.csv
```

예측 3(서버 타임아웃을 RTT 보다 짧게 잡으면 늘어나는 숫자)을 확인하는 실행(한 방향 지연 50ms, 손실 0%, 타임아웃 50ms)은 **사용자 선택으로 건너뛰었다.** 예측 3 은 관찰과 대조하지 않는다.

## 관찰

**손실 10%** (RTT 약 20ms, 칸마다 5번)

| 서버 타임아웃 | 재시도 | 성공 | 성공한 전송 시간 (중앙값 / 최대) | 클라이언트 timeouts 합 |
|---|---|---|---|---|
| 200ms | 3 | 3/5 | 5,126 / 5,937ms | 0 |
| 200ms | 10 | 5/5 | 4,558 / 6,534ms | 0 |
| 1s | 3 | 5/5 | 19,516 / 27,534ms | 7 |
| 1s | 10 | 5/5 | 21,642 / 29,599ms | 9 |

서버 로그(전송 평균): 200ms 칸 `timeouts` 10.5~10.8, `stale_acks` 0.0. 1s 칸 `timeouts` 14.2~15.6, `stale_acks` 1.0. 전체 시도 1,365번 중 타임아웃 245번이라 시도당 타임아웃률 17.9%, 시도 성공률 82.1% 다. 200ms·재시도 10 칸에는 클라이언트가 5번 성공했는데 서버 로그의 `전송 끝` 줄이 4건뿐이다. 서버 종료 신호 시점에 마지막 전송이 진행 중이라 줄이 찍히기 전에 프로세스가 끝났을 것으로 짐작하지만 확인하지는 못했다.

**손실 20%** (RTT 약 20ms, 서버 타임아웃 200ms, 칸마다 10번)

| 재시도 | 성공 | 성공한 전송 시간 | 클라이언트 timeouts 합 |
|---|---|---|---|
| 3 | **1/10 (10%)** | 7,735ms (1건) | 10 |
| 10 | **10/10 (100%)** | 중앙값 13,566ms, 최대 20,576ms | 6 |

재시도 3 칸의 실패 9건은 클라이언트가 `서버 오류 0: transfer failed` 로 본 것이 7건, `재시도를 모두 썼습니다`(클라이언트 자신의 재시도 소진)로 본 것이 2건이다. 서버 로그에서는 같은 칸의 포기가 9건(`error="재시도를 모두 썼습니다"`)이라, 7 + 2 = 9 로 맞는다. 실패한 전송이 끝난 블록 수는 31, 15, 34, 3, 14, 1, 31, 47, 29 이고 1건은 65블록을 모두 보냈다. 이 시도들에서 블록 시도가 279번(성공 270, 실패 9)이므로 블록 하나가 3번 안에 성공하지 못한 비율은 약 3.2% 였다.

## 해석

| 예측 | 관찰 | 판정 |
|---|---|---|
| 1. 손실 10% 에서 DATA 와 ACK 가 둘 다 살아남을 확률 "약 81%" | 시도 성공률 82.1% (1,365번 중 타임아웃 245번) | 맞음 |
| 2. 서버 타임아웃 200ms 가 1s 보다 빠를 것 | 200ms 칸 약 4.6~5.1초, 1s 칸 약 19.5~21.6초 (약 4배) | 맞음 (여유를 두자는 부분은 이번에 측정하지 않았다) |
| 3. 타임아웃이 RTT 보다 짧으면 늘어나는 숫자 | 실행하지 않음 | 미실행 (사용자 선택) |
| 4. 손실 20%, 재시도 3 에서 끝까지 받을 확률 "정상 수신은 64%, 재시도까지 하면 80~90%" | 파일 전체는 10번 중 1번(10%), 블록 하나가 3번 안에 성공할 확률은 약 96.8%(279번 중 270번) | 블록 기준이면 맞고 파일 전체 기준이면 빗나감 |

**예측 1.** 시도 한 번(DATA 와 ACK)이 살아남을 확률은 0.9 × 0.9 = 0.81 이다. 측정값 82.1% 는 이 계산과 맞는다.

**예측 2 와 타임아웃의 효과.** 이 회선에서 정상 응답은 RTT 약 20ms 안에 온다. 서버는 손실이 날 때마다 타임아웃만큼 멈추므로 그 값이 곧 손실 하나의 비용이다. 같은 손실에서 200ms 는 약 5초, 1s 는 약 20초가 걸렸다. 타임아웃이 1초인 칸에서 `stale_acks=1` 과 클라이언트 `timeouts` 가 생긴 것은 서버가 1초 → 2초 → 4초로 대기를 늘리다가 클라이언트의 3초 타이머가 먼저 끝나 마지막 ACK 를 다시 보냈기 때문이다. 서버는 이 지난 ACK 를 세기만 했고(ADR 0009) 전송은 영향을 받지 않았다.

**예측 4 의 두 해석.** 한 번의 시도가 성공할 확률은 0.8 × 0.8 = 0.64 다. 블록 하나가 3번 안에 성공할 확률은 1 − 0.36³ = 약 95.3% 이고 실측은 96.8% 였다. 하지만 파일은 65블록이 모두 통과해야 한다. 계산하면 0.953⁶⁵ = 약 4.5% 이고 실측은 10번 중 1번(10%)이었다. 사용자의 "80~90" 은 블록 하나의 성공률로는 맞았고 파일 전체의 성공률로는 크게 빗나갔다. 이 예측의 학습 대상은 블록 단위의 확률이 파일 단위로는 곱해져서 급격히 떨어진다는 점이다.

**ADR 0009 와의 관계.** 같은 조건(손실 20%)에서 재시도 3 은 10%, 재시도 10 은 100% 성공했다. 손실 10% 에서도 재시도 3 은 5번 중 2번 실패했다(계산상 블록이 3번 연속 실패할 확률은 0.19³ = 0.69% 이고 65블록이면 파일 하나의 실패 확률은 약 36%). ADR 0009 의 재시도 6 은 이런 회선에서 파일 하나가 실패할 확률이 0.19⁶ × 65 = 약 0.3% 라서 계산상 알맞아 보이지만, 재시도 6 은 이번에 측정하지 않았다. 초기 타임아웃 1초는 RTT 20ms·손실 10% 회선에서 200ms 보다 약 4배 느렸다. ADR 0009 는 "T5 측정에서 초기 1초가 RTT 와 손실에 맞지 않으면 다시 본다"를 다시 볼 조건으로 적어 두었고, 이 측정이 그 조건에 해당할 수 있다. 이 판단은 사용자가 한다.

**관찰되지 않은 위험 하나.** 서버가 재시도를 다 쓰고 보내는 ERROR 패킷은 재전송되지 않는다. 이 ERROR 가 사라지면 클라이언트는 서버가 포기한 줄 모르고 자신의 재시도를 다 쓰고서야 끝낸다(재시도 3 칸에서 9건 중 2건). 패킷을 잡아서 확인하지는 않았고 정황으로 본 것이다.

**프로덕션이면 더 필요한 것.** RTT 를 재서 초기 타임아웃을 정하는 적응형 타이머, 끝 ERROR 의 재전송이나 서버 쪽의 종료 대기, 손실률에 따라 재시도 횟수를 정하는 정책.
