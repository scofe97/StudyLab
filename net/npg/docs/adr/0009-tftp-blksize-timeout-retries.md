# 0009. TFTP 서버는 blksize 를 협상하고 타임아웃을 2배씩 늘려 같은 블록을 최대 6번 보낸다

- 상태: 채택
- 날짜: 2026-10-22
- 장: ch06

## 맥락

agent 는 tftpd 에서 펌웨어를 받는다(이슈 #4). TFTP 는 UDP 위에서 블록 하나를 보내고 ACK 를 기다리는 정지-대기라서, 블록 크기·재전송 대기·재시도 상한이 속도와 안정성을 함께 정한다. 블록이 작으면 왕복(RTT)이 늘고, 대기가 고정이면 RTT 와 손실에 맞추지 못하며, 재시도에 상한이 없으면 사라진 클라이언트가 고루틴과 소켓을 붙잡는다. 또 ACK 가 늦게 도착한 것을 손실로 오해해 현재 블록을 다시 보내면 이후 모든 블록이 두 번씩 오가는 마법사의 제자 증후군(Sorcerer's Apprentice Syndrome)이 생긴다.

같은 문제를 푼 규격과 구현(원문 확인).

- RFC 1123 §4.2.3.1: 송신 쪽은 중복 ACK 를 받았다고 현재 DATA 를 다시 보내면 안 된다(MUST). 재전송은 타임아웃 때만 한다
- RFC 1123 §4.2.3.2: TFTP 구현은 적응형 타임아웃을 써야 하고(MUST), 최소한 지수 백오프가 필요하다
- RFC 2348: blksize 옵션의 유효 범위는 8~65464이다. 서버는 요청값 이하로만 OACK 로 답할 수 있다. 2.25MB 파일 실측에서 512바이트는 23.85초, 1428바이트는 13.70초, 8192바이트는 4.90초였다
- RFC 2349: timeout 옵션은 1~255초이고, 서버가 받아들이면 OACK 의 값이 요청과 같아야 한다
- RFC 7440 §6: 재시도 최대 횟수를 두어야 한다(SHOULD). 예시값은 windowsize 8, blksize 1456, 재시도 6회, 타임아웃 1초
- tftp-hpa (`common/tftp.h`, `tftpd/tftpd.c` 소스): 기본 타임아웃 1초, `TRIES` 6, 타임아웃마다 `timeout <<= 1` 이며 `rexmtval × 63` 이상이면 포기한다. 최악 대기는 1+2+4+8+16+32 = 63초
- dnsmasq (GitHub 미러 `imp/dnsmasq` `src/tftp.c`, 최신 여부는 확인하지 못했다): 기본 타임아웃 2초, 기본 블록 512, 재전송 간격이 `timeout + (1<<(backoff/2))` 로 늘고 전송 전체에 시간 상한이 있다

이 저장소의 ADR 0002(재접속 백오프, 지터 ±20%)와 ADR 0006(HELLO 재전송, 지터 ±25%)도 지수 백오프를 쓴다. 노트 06-02 의 서버는 6초 고정 타임아웃에 10번 재시도이고, 번호가 다른 ACK 를 받으면 현재 블록을 곧바로 다시 보내는 결함이 있다(노트에 정정이 이미 들어 있다).

## 선택지

### A. blksize 를 협상하고, 타임아웃을 1초에서 2배씩 늘려, 같은 블록을 최대 6번 보낸다

- 장점: RFC 1123 의 두 MUST(중복 ACK 에 재전송 금지, 지수 백오프)를 지키고, tftp-hpa 와 RFC 7440 의 예시값과 같다. blksize 협상으로 RTT 가 긴 구간의 처리량을 올린다.
- 단점: 옵션 협상(OACK)과 백오프 타이머를 구현해야 한다. RTT 를 재서 맞추는 완전한 적응형은 아니다.

### B. 노트 06-02 서버처럼 512바이트 고정, 6초 고정 타임아웃, 10번 재시도

- 장점: 구현이 가장 단순하다.
- 단점: 고정 타임아웃은 RFC 1123 §4.2.3.2 의 MUST 를 어긴다. RTT 150ms 구간에서 512바이트 블록은 초당 약 3.4KB 로 묶인다. 첫 재전송까지 6초 걸려 손실이 잦은 회선이 느리다.

### C. RTT 를 재서 타임아웃을 맞추는 완전한 적응형 (RFC 6298 방식)

- 장점: 회선마다 알맞은 대기를 스스로 고른다.
- 단점: 전송 하나가 보통 수 초라서 RTT 표본이 적고, 재전송된 블록의 표본을 버리는 규칙(Karn 알고리즘)까지 구현해야 한다. 부트로더용 단순 프로토콜에는 과하다.

## 결정

A 를 고른다.

- blksize: 클라이언트가 요청하면 협상하고, 요청이 없으면 512를 쓴다. 서버 상한 기본값은 1428이며 설정으로 바꿀 수 있다. RFC 한계는 65464이다. 서버는 요청값보다 큰 값으로 답하지 않는다.
- 타임아웃: 초기값은 1초이고(클라이언트가 timeout 옵션을 주고 서버가 받아들이면 그 값), 재전송할 때마다 2배로 늘린다. 이것이 RFC 1123 §4.2.3.2 가 요구하는 최소한의 지수 백오프이다.
- 재시도: 같은 블록을 최대 6번 보낸다. ACK 를 받으면 횟수를 새로 센다. 6번 모두 ACK 가 없으면 전송을 포기하고 `result=error` 로 로그를 남긴다. 초기값 1초일 때 최악 대기는 63초이다.
- 중복 ACK: 지난 블록의 ACK 는 버리고, 다시 보내지 않고, 재시도 횟수도 쓰지 않으며, 같은 데드라인 안에서 다시 읽는다. 이것은 선택이 아니라 RFC 1123 §4.2.3.1 의 요구이고, 리허설 T4 로 증명한다.
- 지터: 서버 재전송에는 넣지 않는다. ADR 0002·0006 의 지터는 장비 여러 대가 같은 순간에 몰리는 문제 때문이었다. TFTP 서버의 재전송 타이머는 전송 하나가 상대 하나에게 보내는 것이라 서로 겹치지 않는다.
- windowsize(RFC 7440)는 이 장에서 구현하지 않는다. 블록 하나에 RTT 하나가 걸리는 한계는 리허설 T3 에서 숫자로 보인다.

## 결과

- 쉬워지는 것: RTT 가 긴 지사에서 blksize 협상으로 처리량이 오르고, 손실이 잦아도 초반 재전송이 빠르며, 사라진 클라이언트를 최대 63초 안에 놓아준다.
- 어려워지는 것: 옵션 협상과 타이머 구현이 늘고, 서버 상한이 1428이라 점보 프레임 환경에서는 설정을 올려야 한다. blksize 가 MTU 를 넘으면 IP 단편화가 생기며, T3 에서 8192로 확인한다.
- 학습용으로 단순화한 것(프로덕션이면 더 필요한 것): RTT 를 재는 적응형 타임아웃, windowsize 로 한 번에 여러 블록 보내기, 경로 MTU 를 보고 blksize 를 고르기, 동시에 몰리는 요청의 속도 제한.
- 다시 볼 조건: T5 측정에서 초기 1초가 RTT 와 손실에 맞지 않거나, windowsize 가 필요한 회선이 확인되면.
