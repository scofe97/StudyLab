# 0006. UDP HELLO 는 ACK 를 기다리며 지수 백오프로 최대 5번 보낸다

- 상태: 채택
- 날짜: 2026-10-21
- 장: ch05

## 맥락

agent 는 부팅할 때 UDP 로 provd 에 HELLO 를 공지한다(이슈 #3). UDP 는 전달을 보장하지 않으므로 HELLO 한 번이 사라지면 provd 는 이 장비가 떴는지 모른다. 반대로 무한히 보내면 provd 가 죽었거나 느릴 때 부하만 키운다. 정전 뒤 장비 여러 대가 동시에 부팅하는 상황도 있어 재전송이 같은 순간에 몰리면 안 된다. 이 채널은 provd 한 곳으로 가는 unicast 라 provd 가 응답(ACK)을 돌려줄 수 있다.

같은 문제를 푼 실제 시스템(원문 확인).

- DHCP: 응답이 올 때까지 클라이언트가 재전송하며, 무작위 지수 백오프를 MUST 로 요구한다. 첫 간격은 4초 ±1초 무작위이고 매번 2배로 늘려 상한은 64초이다 (RFC 2131 §4.1)
- mDNS: 부팅 때 공지를 응답 확인 없이 최소 2번, 1초 간격으로 보낸다. 더 보내도 되지만(최대 8번) 간격은 매번 2배 이상이어야 하고, 주기적 공지는 금지이다. multicast 라 ACK 를 받을 상대가 없다 (RFC 6762 §8.3)
- hashicorp/memberlist (serf·consul): `ProbeTimeout` 500ms, `ProbeInterval` 1초, `RetransmitMult` 4, 메시지 재전송 횟수는 `RetransmitMult × ceil(log10(N+1))` (`config.go`, `util.go`)
- RFC 8085: 앱이 UDP 위에서 직접 신뢰성을 구현하면 재전송에 백오프와 지터를 쓰고 단편화는 피한다 (§3)

이 저장소의 ADR 0002 는 TCP 재접속에 같은 모양(지수 백오프, 지터)을 이미 쓴다.

## 선택지

### A. HELLO 에 번호(nonce)를 담고 ACK 를 기다리며 지수 백오프로 5번 보낸다

- 장점: 유실에는 빨리 복구하고, provd 가 느리거나 죽었을 때는 간격이 늘어 부하를 키우지 않는다. 무작위가 섞여 동시 부팅이 몰리지 않는다. DHCP 와 RFC 8085 와 같은 모양이다.
- 단점: ACK 형식, 재전송 루프, nonce 대조 세 가지를 구현해야 한다.

### B. ACK 없이 1·2·4초 간격으로 3번 보낸다 (mDNS 식)

- 장점: 구현이 가장 단순하다.
- 단점: agent 가 provd 의 수신 여부를 모른다. provd 는 중복 HELLO 를 걸러야 하고, 세 번 모두 유실되면 조용히 실패한다.

### C. ACK 가 올 때까지 계속 보낸다 (DHCP 식, 간격 상한 64초)

- 장점: 언젠가는 반드시 전달된다.
- 단점: 포기 기준이 없어 provd 가 영영 안 뜨는 환경에서도 영원히 보내고, TCP 재접속(ADR 0002)과 역할이 겹친다.

## 결정

A 를 고른다. 첫 대기는 1초이고 2배씩 늘려 1·2·4·8·16초로 최대 5번 보내며, 각 간격에는 ±25% 무작위를 섞는다. ACK 의 nonce 가 보낸 HELLO 와 같으면 재전송을 멈춘다. 5번 모두 ACK 가 없으면 경고 로그를 남기고 공지를 멈춘다. 공지는 보조 경로이고 등록의 정본은 TCP 제어 채널이므로, 공지가 실패해도 TCP 재접속(ADR 0002)은 따로 계속 돈다. 간격, 배수, 횟수, 지터는 상수로 두어 바꿀 수 있게 한다.

DHCP 와 mDNS 가 둘 다 지수 간격으로 늘리는 것은 실패가 계속될수록 같은 상대에게 보내는 속도를 낮추기 위해서이고, 무작위는 동시에 시작한 송신자가 계속 같은 순간에 몰리는 것을 깨기 위해서이다.

## 결과

- 쉬워지는 것: 한두 번의 유실은 몇 초 안에 복구되고, 총 시도는 5번으로 묶여 provd 부하가 예측된다. 성공과 실패가 agent 로그에 남는다.
- 어려워지는 것: HELLO 와 ACK 의 와이어 형식을 정해야 하고, provd 는 같은 nonce 의 중복 HELLO 에도 ACK 를 다시 보내야 한다(ACK 가 유실될 수 있기 때문이다).
- 프로덕션이면 더 필요한 것: 이 안은 provd 의 주소를 이미 안다고 가정한다. 실제 발견 시스템은 주소를 모르는 상대를 찾으려 broadcast·multicast 를 쓰고(DHCP, mDNS, SSDP), HELLO 위조를 막는 인증(서명·토큰), 공지 폭주를 막는 제한(rate limit), provd 쪽 재생(replay) 방어, 장비 수에 맞춰 재전송 횟수를 조정하는 방식(memberlist)이 더 필요하다. ±25% 지터는 ADR 0002 의 ±20% 와 다르며, 둘을 같은 값으로 맞출지는 나중에 다시 본다.
- 나중에 다시 볼 조건: 공지가 실패했을 때 TCP 만으로 등록이 충분하지 않은 요구가 생길 때, 장비 수가 늘어 provd 의 ACK 부하가 문제될 때.
