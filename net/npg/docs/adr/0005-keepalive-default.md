# 0005. TCP keepalive 는 Go 기본값을 그대로 두고 하트비트를 주 감지 수단으로 삼는다

- 상태: 채택
- 날짜: 2026-10-21
- 장: ch04

## 맥락

ADR 0003 이 애플리케이션 하트비트(ping·pong, 읽기 데드라인 15초)로 양쪽이 침묵을 감지하게 했고, TCP keepalive 와 `TCP_USER_TIMEOUT` 은 4장에서 따로 판단하기로 남겼다.

Go 의 `net.Dial`·`net.Listen` 으로 만든 TCP 연결은 따로 설정하지 않아도 keepalive 가 켜진다. `net.Dialer.KeepAlive` 가 0 이면 기본값을 쓰고(`go doc net.Dialer`), `net.KeepAliveConfig` 의 기본값은 Idle 15초, Interval 15초, Count 9 이다(`go doc net.KeepAliveConfig`, Go 1.25.1). 응답이 없으면 15 + 15 × 9 = 150초 뒤에 커널이 연결을 끊는다. 이 저장소의 `dial.go` 는 `net.Dialer{Timeout: ...}` 만, `cmd/provd` 는 `net.Listen` 만 쓰므로 양쪽 모두 기본값이 적용된다.

keepalive 는 커널이 빈 ACK 탐침으로 확인하므로 상대 프로세스가 멈춰도 커널이 응답해 잡지 못한다(노트 04-03 §2). 3장 리허설에서 provd 를 얼리자 agent 가 4분 52초 동안 몰랐던 경우가 이것이다. 이 경우는 하트비트가 잡는다.

## 선택지

### A. 기본값을 그대로 두고 ADR 로 기록한다

- 장점: 코드 변경이 없다. 하트비트가 돌지 않는 순간에도 커널이 반쪽 연결을 150초 안에 정리하는 안전망이 남는다.
- 단점: 기본값이 코드에 드러나지 않아 읽는 사람이 keepalive 없음으로 오해할 수 있다(이 ADR 이 그 기록을 맡는다). Go 가 기본값을 바꾸면 따라 바뀐다.

### B. 끈다 (`KeepAlive: -1`)

- 장점: 하트비트와 역할이 겹치지 않음이 코드에서 분명하다.
- 단점: 하트비트가 멈춘 경우의 안전망이 사라진다.

### C. `KeepAliveConfig` 로 값을 명시하고 조정한다

- 장점: 값이 코드에 남고 하트비트(15초)와 시간대를 맞출 수 있다.
- 단점: 설정이 늘어난다. 하트비트가 이미 15초에 잡으므로 값을 줄여도 얻는 것이 작고, 조정할 실측 근거(중간 장비의 유휴 타임아웃 등)가 이 저장소에는 없다.

## 결정

A 를 고른다. 침묵 감지의 주 수단은 ADR 0003 의 하트비트(15초)이고, TCP keepalive 는 Go 기본값(150초)으로 켜 둔 보조 안전망이다. 조정할 근거가 생기기 전에는 값을 코드에 넣지 않는다.

`TCP_USER_TIMEOUT` 은 이번에 도입하지 않는다. 리눅스 전용이라 맥 개발 환경과 달라지고, 응답이 없는 경우는 하트비트가 이미 잡기 때문이다.

## 결과

- 쉬워지는 것: 코드와 설정이 늘지 않는다. 하트비트가 못 잡는 드문 순간에도 커널이 정리한다.
- 어려워지는 것: 이 ADR 이 기본값의 유일한 기록이다. Go 기본값이 바뀌면 이 문서와 어긋난다.
- 남은 한계: 중간 장비(NAT·방화벽)가 유휴 연결을 15초보다 짧게 지우는 환경은 실측하지 않았다. 그런 환경이 확인되면 C 로 다시 판단한다.
