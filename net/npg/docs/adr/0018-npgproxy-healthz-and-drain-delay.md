# 0018. npgproxy 는 /healthz 를 내고, 종료 신호 뒤 -drain-delay 동안 503 draining 을 알린 뒤 닫는다

- 상태: 채택
- 날짜: 2026-11-04
- 장: ch10

## 맥락

ADR 0015 로 Caddy 가 npgproxy 앞단에 섰다. 이제 npgproxy 를 두 대로 늘려 Caddy 가 `round_robin` 으로 나눠 보내게 하면, 한 대씩 재시작하는 배포(롤링 배포)에서 502 가 찍힌다. 남은 한 대는 멀쩡한데도 그렇다.

이유는 `round_robin` 이 뒤쪽 서버의 상태를 묻지 않는 정책이기 때문이다. 순서가 돌아오면 그 서버가 내려가는 중이든 이미 닫혔든 요청을 보낸다. 지금 npgproxy 는 SIGTERM 을 받으면 곧바로 `Shutdown` 을 불러 듣는 소켓을 닫는다(ADR 0014 결정 3). 그래서 앞단 입장에서는 서버가 아무 예고 없이 사라진다. 이 문제는 Caddy 나 Go 만의 사정이 아니라, 앞단이 여러 뒤쪽 서버로 나눠 보내는 모든 구조가 만나는 일반 문제다.

### 개념 1. 능동 검사와 수동 검사

앞단이 뒤쪽 서버가 살아 있는지 아는 방법은 두 가지다.

| 방법 | 어떻게 아나 | 약점 |
|---|---|---|
| 능동 검사 | 앞단이 정해진 주기로 검사 요청을 따로 보낸다(예: 1초마다 `GET /healthz`). 기대한 응답이 아니면 그 서버를 후보에서 뺀다 | 주기만큼 늦게 안다. 검사 요청이 서버에 부하를 더한다 |
| 수동 검사 | 손님 요청을 보내 보다가 실패하면 그 실패를 센다. 일정 기간 안에 정해진 횟수를 넘으면 후보에서 뺀다 | 처음 몇 건은 손님이 실패를 맞아야 안다 |

능동 검사는 손님 요청이 오기 전에 알 수 있어서 좋지만, 서버가 "곧 내려간다"를 검사 응답으로 알려 줄 길이 있어야 쓸모가 있다. 그 길이 `/healthz` 다.

### 개념 2. 드레인

드레인은 내려가기 전에 "곧 내려간다"를 알리고, 그 알림이 앞단에 닿을 시간을 기다린 뒤 닫는 것이다. 순서는 이렇다.

1. 종료 신호를 받는다.
2. 듣는 소켓은 열어 둔 채 `/healthz` 를 503 `draining` 으로 바꾼다. 일반 요청은 계속 처리한다.
3. 앞단이 검사에서 503 을 보고 이 서버를 후보에서 뺀다. 이 시간이 `drain-delay` 다.
4. 시간이 지나면 `Shutdown` 을 부른다. 듣는 소켓을 닫고, 처리 중인 요청이 끝나기를 기다린다.

`drain-delay` 는 앞단의 검사 주기와 시간제한을 합친 것보다 길어야 한다. 짧으면 앞단이 알아채기 전에 소켓이 닫혀 드레인이 없는 것과 같아진다.

### 개념 3. 재시도

재시도는 실패한 요청을 다른 서버(또는 같은 서버)로 다시 보내는 것이다. 위험은 같은 요청이 두 번 실행될 수 있다는 점이다. 연결조차 못 맺은 실패(dial 실패)는 요청이 서버에 닿지 않았으므로 다시 보내도 안전하다. 연결이 맺힌 뒤의 실패는 서버가 요청을 받았을 수 있어서, 멱등성(ADR 0013)이 확실한 요청만 다시 보내야 한다.

## 선택지

### A. 지금처럼 즉시 종료를 유지한다

- 코드를 건드리지 않는다.
- 앞단의 검사가 볼 곳(`/healthz`)이 없다. 닫히는 순간 그 서버로 가던 요청은 앞단이 502 로 바꿔 손님에게 돌려준다. 앞단이 재시도를 설정해야만 줄일 수 있고, 그것도 요청 종류에 따라 한계가 있다.

### B. `/healthz` 와 드레인 지연을 더한다

- `-drain-delay` 플래그로 시간을 정한다. 기본 0 이면 A 와 똑같이 돈다.
- 앞단은 능동 검사로 "곧 내려간다"를 먼저 알 수 있다. 수동 검사와 재시도는 그대로 따로 쓸 수 있다.
- 종료가 `drain-delay` 만큼 늦어진다. 배포 시간이 서버 수 × 지연만큼 길어진다.
- 값이 앞단의 검사 주기에 묶인다. 한쪽을 바꾸면 다른 쪽도 다시 봐야 한다.

## 결정

창이 B 를 제안했고 학습자가 맡겼다(2026-11-04, "맡겨줘"). 다음 네 가지로 정했다.

1. npgproxy 는 손님 주소(`-addr`)에 `GET /healthz` 를 낸다. 평소에는 200 `ok`, 종료 신호를 받은 뒤에는 503 `draining` 이다. 이 경로는 업스트림으로 넘기지 않고 접근 로그에도 남기지 않는다. 검사 요청이 1초마다 와서 손님 요청 줄에 섞이면 읽기 어려워서다.
2. `-drain-delay` 기본값은 0 이다. 기본으로는 지금 동작(종료 신호 → 곧바로 `Shutdown`)이 바뀌지 않는다. 0 보다 크면 종료 신호 뒤 그 시간 동안 듣는 소켓을 연 채 계속 요청을 처리하고 `/healthz` 만 503 으로 바꾼 뒤, 지나면 지금처럼 `Shutdown` 을 부른다.
3. 실습에서는 npgwatch 가 두 npgproxy 에 `-drain-delay 5s` 를 넘긴다. 앞단의 능동 검사(주기 1초, 시간제한 500ms)가 503 을 보기에 충분하고, 화면에서 구간이 눈에 보일 만큼 길어서다. 이 값은 이 실습의 값이고 일반 권장값이 아니다.
4. 서버 오류(포트 충돌 등)로 내려갈 때는 드레인을 기다리지 않는다. 알릴 앞단이 없는 상황에서 종료만 늦추기 때문이다.

관리 주소(`-admin`)의 `/debug/vars` 는 드레인 동안에도 열려 있고, 지연이 끝나 `Shutdown` 을 부를 때 손님 주소와 함께 닫힌다.

## 결과

- 쉬워지는 것: 앞단이 `/healthz` 로 검사할 수 있다. 같은 두 대로 기본·능동 검사·재시도·둘 다의 네 판을 같은 부하에서 비교할 수 있다(리허설 E4).
- 어려워지는 것: 종료가 `drain-delay` 만큼 늦다. 쿠버네티스처럼 종료 유예가 정해진 환경에서는 `drain-delay` + 종료 대기(20초, ADR 0014)가 유예 안에 들어와야 한다.
- 학습용으로 단순화한 것: 드레인 동안 keep-alive 연결을 끊지 않는다. 연결을 재사용하는 앞단은 드레인 중에도 같은 연결로 요청을 보낸다. 실무에서는 드레인 시작 때 keep-alive 를 끄는 선택지도 있고, 이번에는 고르지 않았다.
- 참조 구현과 다른 점: 참조 api(`chapters/ch07-10-service/cmd/api/main.go` L317-345)는 드레인 중 1초마다 진행 로그를 남기고 `systemd` 알림(`STOPPING=1`)을 보내며, 두 번째 신호가 오면 바로 끝낸다. npgproxy 는 시작 로그 한 줄만 남기고 알림과 두 번째 신호 처리는 하지 않는다. `/healthz` 순서(503 로 바꾼 뒤 지연, 그다음 `Shutdown`)는 같다.
- 다시 볼 조건: E4 를 직접 돌린 뒤 `drain-delay` 와 검사 주기의 관계를 실행 결과로 다시 따진다. 이 문서는 아직 실행 결과가 없고, 위 개념은 소스를 읽어 정리한 것이다.
