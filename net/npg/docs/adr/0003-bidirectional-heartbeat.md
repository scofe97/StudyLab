# 0003. 제어 채널은 ping·pong 양방향 하트비트로 양쪽이 침묵을 감지한다

- 상태: 채택
- 날짜: 2026-10-21
- 장: ch03

## 맥락

처음에는 agent 가 5초마다 `ping\n` 을 쓰고 provd 만 읽기 데드라인(15초)으로 감시하는 단방향 구조였다. 메시지 경계(길이 접두 프레임)는 4장 몫이라 3장은 줄 단위 최소 형식을 쓴다.

장애 리허설(`docs/rehearsals/ch03-dead-connection.md`)에서 이 구조의 비대칭이 드러났다.

- 패킷이 버려지면 provd 는 13~14초 만에 알아챘지만, agent 는 `Write` 가 계속 성공해 약 1분 동안 몰랐다.
- provd 프로세스를 얼려도 커널이 ACK 를 하므로 agent 의 `Send-Q` 는 0 이었고, 4분 52초가 지나도 agent 는 알아채지 못했다. 연결(handshake)도 커널이 대신 완성하므로 `Dial` 은 계속 성공한다.

실제 시스템은 같은 문제를 응답을 요구하는 방식으로 푼다(각 문서 원문 확인).

- gRPC: 한쪽이 PING 을 보내고 `KEEPALIVE_TIMEOUT`(기본 20초) 안에 ACK 가 없으면 연결을 닫는다. 클라이언트와 서버 양쪽에 설정한다.
- MQTT 3.1.1: 클라이언트는 PINGRESP 로 "네트워크와 서버가 작동하는지" 판단하고, 서버는 Keep Alive 의 1.5배 동안 아무것도 못 받으면 끊는다.
- OpenSSH: `ServerAliveInterval` 동안 못 받으면 확인 메시지를 보내고 `ServerAliveCountMax` 번 응답이 없으면 끊는다. TCP keepalive 와는 별개다.

## 선택지

### A. 단방향 `ping` 으로 3장을 마치고 한계를 기록한다

- 장점: 가장 단순하다.
- 단점: agent 는 provd 의 침묵을 감지하지 못한다. 리허설에서 실측했다.

### B. 양방향 하트비트: provd 가 ping 마다 pong 으로 답하고 agent 도 읽기 데드라인을 둔다

- 장점: 양쪽이 15초 안에 침묵을 감지한다. 실제 시스템과 같은 구조다.
- 단점: agent 가 쓰기와 읽기를 동시에 해서 고루틴 두 개와 정리 순서가 필요하다. 줄 단위 형식에서는 `ping`/`pong` 을 줄 내용으로 구분하면 되므로 4장 프레임이 없어도 가능하다.

### C. TCP keepalive 나 `TCP_USER_TIMEOUT` 에 맡긴다

- 장점: 애플리케이션 코드가 필요 없다.
- 단점: 커널 수준만 확인한다. provd 프로세스가 멈춰도 커널은 응답하므로 잡지 못한다(리허설 2).

## 결정

B 를 고른다. 단방향의 비대칭이 리허설 두 가지 장애(패킷 단절, 프로세스 정지)에서 모두 실측되었고, 실제 시스템이 쓰는 요청-응답 구조가 이를 해결하기 때문이다. 데드라인 배수는 ADR 0001 의 3배를 양쪽에 그대로 쓰고(`DeadlineFactor`), 형식은 `ping\n` 과 `pong\n` 두 줄이다. 모르는 줄을 받으면 연결을 끊는다.

연결 성공은 서버 프로그램이 건강하다는 증거가 못 되므로, 재접속 백오프(ADR 0002)는 첫 pong 을 받았을 때 초기화한다.

## 결과

- 쉬워지는 것: agent 도 provd 의 침묵(프로세스 정지, 응답 불능)을 15초 안에 감지해 재접속한다. 서버가 응답이 없는 동안 재접속 간격이 지수로 늘어(0.82초 → 29.5초, 상한 30초 ±20%) 서버를 더 누르지 않는다.
- 어려워지는 것: 고루틴 두 개의 종료 순서를 지켜야 한다(`cancel` 후 `Close` 후 두 번째 결과 수신). 서버가 얼어 있는 동안 provd 쪽에는 `CLOSE-WAIT` 소켓과 accept 대기열이 쌓인다(관찰: 3분 35초에 13개). 4장 CLOSE_WAIT 주제와 이어진다.
- 남은 한계: 줄 단위 형식이라 메시지 길이와 종류가 늘면 한계가 있다. 4장에서 길이 접두 프레임을 도입할 때 이 하트비트를 같은 틀로 옮긴다. `TCP_USER_TIMEOUT` 은 4장의 keepalive 판단 때 보조 수단으로 검토한다.
