# 0013. 프록시는 재시도 층을 더하지 않는다 — GET 은 Go Transport 에 맡기고 POST 는 다시 보내지 않으며, 다시 보낸 횟수를 센다

- 상태: 채택
- 날짜: 2026-10-29
- 장: ch08

## 맥락

ADR 0012 뒤에도 I2 장면에서 POST 502(UC)가 남는다(v0 56/1,206, 재확인 약 21/318). 고객 신고는 "장비 등록이 가끔 502 로 실패한다"였다. 급한 핫픽스로 "502 면 3번 다시 보내자"를 고를 수 있었지만 운영자(학습자)는 고르지 않았다. GET 은 Go 가 이미 다시 보내고, POST 는 502 를 그대로 돌려주는 편이 맞다고 판단했다. 이 ADR 은 그 판단을 근거와 함께 굳힌다.

Go 1.25.1 Transport 가 이미 하는 재시도는 다음과 같다.

- `transport.go:582` `roundTrip` 은 횟수 상한 없는 반복문이고, 실패하면 `:716` 에서 `shouldRetryRequest` 로 다시 보낼지 묻는다.
- 새로 연 연결에서 실패하면 다시 보내지 않는다(`:822`). 풀에서 꺼낸 연결이 이미 닫혀 있었던 경우만 다시 보낸다. 그래서 대개 한 번, 쉬던 연결이 한꺼번에 죽었으면 그 수만큼 더 보낸다.
- 아무것도 쓰지 못했으면(`nothingWrittenError`) 메서드와 상관없이 다시 보낸다. 단 본문이 없거나 `GetBody` 로 되감을 수 있어야 한다(`:832-835`).
- 그 밖에는 `isReplayable` 이 참이어야 다시 보낸다(`:837`). `request.go` `isReplayable` 은 먼저 본문을 보고(없음·`NoBody`·`GetBody` 있음), 그다음 메서드(GET·HEAD·OPTIONS·TRACE)나 `Idempotency-Key`·`X-Idempotency-Key` 헤더를 본다.

프록시를 지나는 본문은 한 번 흐르는 스트림이다. `httputil.ReverseProxy` 는 `GetBody` 를 두지 않고, 본문 길이가 0 일 때만 `Body` 를 비운다(`reverseproxy.go:378`). 그래서 본문 있는 POST 는 키가 붙어 있어도 Go 가 다시 보내지 않는다. I2 v0 실측이 이를 보여 준다. GET 502 는 0/1,199 였고 POST UC 는 56 이었다.

같은 문제를 다룬 곳(원문 확인 2026-10-29).

| 출처 | 말하는 것 |
|---|---|
| RFC 9110 §9.2.2 | "A proxy MUST NOT automatically retry non-idempotent requests." 손님(user agent)은 요청이 멱등임을 알 수단이 있으면 예외지만 프록시에는 그런 예외가 없다 |
| nginx `proxy_next_upstream` (1.9.13 `non_idempotent`) | 기본 `error timeout` 으로 다음 서버에 넘기되, POST·LOCK·PATCH 는 업스트림에 이미 보냈으면 넘기지 않는다. 켜야만 다시 보낸다 |
| AWS Builders' Library "Timeouts, retries, and backoff with jitter" | 5층 호출에서 층마다 3번씩 다시 보내면 맨 아래 데이터베이스 부하가 243배가 된다. 저비용 호출은 스택의 한 지점에서만 재시도한다("retry at a single point in the stack") |

앞 장의 재시도 ADR 0002(agent 재접속 백오프·지터, 상한 30초), 0006(UDP HELLO 지수 백오프 최대 5번), 0009(TFTP 2배 타임아웃 최대 6번)는 다른 프로토콜의 재시도다. 이어받는 원칙은 "간격을 벌리고, 흩뜨리고, 상한을 둔다"이다.

재시도 증폭(I4)과 중복 등록(I5) 리허설은 이번 장에서 돌리지 않았다(사용자 선택). 운영자 판단이 재시도 핫픽스를 넣지 않는 쪽이라 장면이 생기지 않았다.

## 선택지

### 1. 프록시 자체 재시도 층

- 없음, Go Transport 재시도만 둔다. 다시 보내는 경우는 요청이 백엔드에 닿지 않았을 가능성이 큰 실패뿐이라 백엔드 일이 늘지 않는다.
- 502 면 3번(모든 메서드). 백엔드가 받았는지 모르는 실패까지 다시 보낸다. POST 는 두 번 등록되고(I5), 장애 중 요청이 곱으로 늘어 회복을 막는다(I4). RFC 9110 의 프록시 MUST NOT 에 어긋난다.
- UF(연결 실패)만 n 번. 요청이 나가지 않은 게 확실해 안전하다. 그러나 업스트림이 한 대라 같은 곳으로 같은 실패를 되풀이하고, 장애 중 연결 시도만 늘린다. 업스트림이 여럿이 되면 다시 볼 자리다.

### 2. `Idempotency-Key` 가 붙은 POST

- 본문을 담지 않고 헤더는 그대로 백엔드에 넘긴다. 프록시는 POST 를 다시 보내지 않는다. 같은 키로 다시 보낼지는 손님이 정하고, 중복을 막는 일은 백엔드가 키로 한다(fakeinv `idempotency=true`).
- 본문을 메모리에 담아 `GetBody` 를 단다. Go 가 키 붙은 POST 도 다시 보내게 된다. 요청마다 본문 크기만큼 메모리를 쓰므로 상한이 필요하고, 키가 진짜 멱등을 보장하는지 프록시는 모른다(RFC 9110 프록시 MUST NOT).
- 헤더를 지운다. Go 재시도와는 상관없고(본문 때문에 이미 안 보낸다), 백엔드 중복 방지까지 잃는다.

### 3. 층 사이 재시도 원칙

- 재시도는 손님 한 층에서만 백오프·지터·상한으로 한다. 프록시는 횟수를 늘리지 않는다.
- 층마다 각자 재시도한다. 층 수만큼 곱해진다.

### 4. 계측

- I2 기록의 알려진 한계에 "GET 이 실제로 다시 보내졌는지 직접 보지 않았다"가 있다. 지금 접근 로그는 마지막 `GotConn` 의 `reused`·`idle` 만 남긴다.
- Transport 는 다시 보낼 때마다 연결을 새로 얻으므로 `GotConn` 이 시도마다 한 번씩 불린다고 보고, 요청 하나의 `GotConn` 수에서 1 을 뺀 값을 다시 보낸 횟수로 센다. 이 가정은 시험으로 확인한다.

## 결정

| 자리 | 값 | 근거 |

| 1. 프록시 재시도 층 | 두지 않는다. Go Transport 재시도만 | 학습자 판단, RFC 9110 §9.2.2, nginx `non_idempotent` 기본 꺼짐 |
| 2. 키 붙은 POST | 본문을 담지 않는다. 헤더는 그대로 넘긴다 | RFC 9110 §9.2.2 프록시 MUST NOT, 메모리 상한을 새로 둘 필요 없음 |
| 3. 층 사이 원칙 | 재시도는 손님 한 층에서만, 백오프·지터·상한(ADR 0002 와 같은 원칙) | AWS Builders' Library 243배 예, "retry at a single point in the stack" |
| 4. 계측 | 요청마다 시도 수를 세어 접근 로그 `attempts`, 카운터 `retries`(다시 보낸 횟수 합)로 낸다 | I2 알려진 한계 |

## 결과

- POST 가 두 번 등록되는 길을 프록시가 만들지 않는다. 장애 중 프록시가 요청을 곱으로 늘리지 않는다.
- 대가로 쉬던 연결 경합에 걸린 POST 는 502(UC)로 손님에게 간다. I2 장면(백엔드 유휴 1초)에서는 v0 약 4.6%, ADR 0013 재확인 약 4.0% 가 그대로 남는다. 손님은 `Idempotency-Key` 를 붙여 다시 보내야 한다.
- 결정 4 로 GET 재시도가 접근 로그와 카운터에 보인다. I2 재확인(2026-10-29, 약 4분): GET 502 0/261 에 `attempts=2` 13 건 = `retries` 13, POST 502(UC) 10/248 모두 `attempts=1`. 같은 경합을 GET 은 Go 가 숨기고 POST 는 그대로 드러낸다.
- 한계: I4·I5 는 돌리지 않아 증폭·중복을 실측하지 못했다. HTTP/2 업스트림은 다른 재시도 경로(`http2shouldRetryRequest`)를 타는데 지금 프록시는 HTTP/1.1 만 쓴다. 업스트림이 여럿이 되면 선택지 1 의 UF 재시도를 다시 본다.
