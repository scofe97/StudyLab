# 0007. UDP 공지의 앱 데이터는 1232바이트 이하로 두고, 포트는 TCP 와 같은 7100 을 쓴다

- 상태: 채택
- 날짜: 2026-10-21
- 장: ch05

## 맥락

UDP 데이터그램이 경로 MTU 보다 크면 IP 계층이 조각으로 나눈다. 조각 하나만 잃어도 전체 데이터그램을 잃고, NAT·방화벽이 조각을 버리는 경우도 있다 (RFC 8085 §3.2). 공지는 ADR 0006 으로 최대 5번 재전송되지만, 단편화된 공지는 조각마다 유실 확률이 곱해져 더 자주 사라진다. 그래서 공지의 크기 상한을 MTU 아래로 정해 단편화를 피한다.

크기를 계산하는 근거(원문 확인).

- 앱 데이터 최대 = 링크 MTU − IP 헤더(IPv4 20, IPv6 40) − UDP 헤더 8 (RFC 6762 §17, RFC 8085 §3.2). 이더넷 MTU 1500 이면 IPv4 에서 1472, IPv6 에서 1452 이다
- IPv6 링크는 MTU 가 최소 1280 이어야 한다 (RFC 8200 §5). 1280 − 48 = 1232
- IPv4 의 기본 유효 송신 MTU `EMTU_S` 는 576, IPv6 는 1280 이다 (RFC 8085 §3.2)
- QUIC 은 모든 경로가 UDP 페이로드 1200바이트를 나른다고 가정한다 (RFC 9000 §14)
- hashicorp/memberlist 의 `UDPBufferSize` 기본값은 1400 이며 "안전한 값"이라고 적혀 있다 (`config.go`)
- mDNS 는 단편화된 데이터그램을 재조립하지 못하는 단순 장비가 많다며 큰 레코드를 피하라고 권고한다 (RFC 6762 §17)

HELLO 본문은 장비 id, nonce, 버전 정도라 실제로는 수십 바이트이다. 상한은 평소 크기가 아니라 나중에 필드가 늘어도 단편화되지 않는 선이다.

UDP 포트는 이슈 #3 에 7001 이 임시 값으로 적혀 있었다. 7001 은 `afs3-callback` 으로 등록된 번호이고, TCP 제어 채널은 7100 이다. memberlist 는 TCP 와 UDP 를 같은 포트(기본 7946)로 열고 DNS(53)·syslog(514)도 같은 번호를 쓴다.

## 선택지

### A. 앱 데이터 1232바이트

- 장점: IPv4·IPv6 어느 경로든, 터널이 있어도 단편화되지 않는다. QUIC 의 1200 과 가까운 선이다.
- 단점: 이더넷 최대(1472)보다 240바이트 작아, 큰 공지가 필요해지면 필드를 줄이거나 상한을 올려야 한다.

### B. 1400바이트 (memberlist 기본값)

- 장점: 실제 시스템에서 검증된 값이고 이더넷 위에서 여유가 있다.
- 단점: IPv6 최소 MTU 링크(1280)에서는 단편화된다. 근거가 경험적 안전성뿐이다.

### C. 1472바이트 (이더넷 최대)

- 장점: 이더넷에서 가장 많이 담는다.
- 단점: VPN·터널·PPPoE 처럼 MTU 가 작은 경로에서 바로 단편화된다.

## 결정

A 를 고른다. 공지 데이터그램의 앱 데이터(UDP 페이로드)는 `MaxAnnounceSize` = 1232바이트 이하로 한다. 송신 쪽은 이보다 크면 보내지 않고 오류를 돌려준다. 수신 쪽은 읽기 버퍼를 `MaxAnnounceSize + 1` 로 잡아, 상한을 넘어 도착한 데이터그램은 잘린 채 처리하지 않고 크기로 탐지해 버리고 로그를 남긴다. 1232 는 IPv6 최소 MTU 에서 헤더를 뺀 값이라 어떤 경로에서도 단편화되지 않기 때문이다.

UDP 포트는 TCP 제어 채널과 같은 7100 을 쓴다. provd 주소·포트 설정이 하나로 끝나고, 방화벽 규칙도 7100 tcp,udp 하나로 쓸 수 있다.

## 결과

- 쉬워지는 것: 단편화로 인한 유실 장면이 정상 경로에서 사라지고, 크기 초과는 송신에서 바로 드러난다. 설정이 하나 줄어든다.
- 어려워지는 것: 공지 필드를 늘릴 때 1232바이트를 넘지 않는지 따져야 한다. TCP 와 UDP 가 같은 번호라 `ss` 로 볼 때 프로토콜 열로 구분해야 한다.
- 프로덕션이면 더 필요한 것: 이 안은 고정 상한이다. 실제 시스템은 경로 MTU 를 실측하는 PLPMTUD(RFC 8085 권고)나 DF 비트 설정을 쓰고, `EMSGSIZE` 처리와 인터페이스 MTU 변화 감지가 더 필요하다. 터널이나 IPv6 최소 링크보다 작은 경로(MTU 1280 미만)는 다루지 않는다.
- 나중에 다시 볼 조건: 공지가 1232바이트를 넘는 필드를 요구할 때, 단편화가 없는 경로를 실측으로 확인해 상한을 올릴 근거가 생길 때.
