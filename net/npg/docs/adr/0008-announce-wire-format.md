# 0008. UDP 공지 본문은 길이 접두 없는 10바이트 고정 헤더를 쓴다

- 상태: 채택
- 날짜: 2026-10-21
- 장: ch05

## 맥락

ADR 0004 는 TCP 제어 채널에 `[4바이트 길이][본문]` 프레임을 정했다. TCP 는 경계 없는 바이트 흐름이라 길이 접두가 경계를 만들어 준다. UDP 는 데이터그램 하나가 곧 메시지 하나라서 경계가 이미 있다. 그래서 같은 프레임을 UDP 에 쓸지 따로 정해야 한다.

실제 시스템의 방식(원문 확인).

- DHCP: 고정 헤더에 4바이트 `xid` 를 두어 응답을 요청과 짝짓고, 가변 부분은 `options` 이다 (RFC 2131 §2, §4.1)
- hashicorp/memberlist: 데이터그램 첫 바이트가 `messageType`(uint8)이고 그 뒤가 본문이다. ACK 는 `SeqNo` 로 ping 과 짝짓는다 (`net.go`)

두 시스템 모두 길이 접두 없이 앞에 타입 또는 id 를 둔다.

## 선택지

### A. 길이 없는 고정 헤더

- 장점: 헤더가 고정이라 해석이 한 번에 끝난다. 길이 필드와 실제 크기가 어긋나는 위조가 생길 수 없다. 버전 바이트로 형식 변경에 대비한다.
- 단점: 필드가 늘면 형식을 직접 설계해야 하고, 4장 `frame.go` 를 재사용하지 못한다.

### B. 4장 프레임 재사용

- 장점: 코드 재사용, TCP 와 UDP 의 일관성.
- 단점: `ReadFrame` 은 스트림(`io.ReadFull`) 가정이라 데이터그램에 맞지 않는다. 길이가 데이터그램 크기와 다른 경우가 새로 생기고, 길이가 중복 정보이다.

### C. JSON

- 장점: 읽고 디버깅하기 쉽다.
- 단점: 크기가 가변이라 ADR 0007 의 1232바이트 상한 계산이 어렵고, 파싱 비용과 오류 경우가 늘어난다.

## 결정

A 를 고른다. 와이어 형식은 다음과 같다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 1 | 버전 (현재 1) |
| 1 | 1 | 타입 (HELLO = 1, ACK = 2) |
| 2 | 8 | nonce (빅엔디언 uint64, 송신자가 무작위로 고름) |
| 10 | 나머지 | 본문 |

HELLO 의 본문은 장비 id(UTF-8, 나머지 바이트 전부)이고 ACK 의 본문은 비어 있다. ACK 는 받은 HELLO 의 nonce 를 그대로 돌려 짝짓는다. 수신 쪽은 10바이트 미만, 알 수 없는 버전, 알 수 없는 타입을 모두 버리고 로그를 남긴다. 전체 크기는 ADR 0007 의 1232바이트 이하이다.

## 결과

- 쉬워지는 것: 해석이 단순하고 위조된 길이 문제가 없다. 크기 상한 검사는 데이터그램 전체 길이 하나로 끝난다.
- 어려워지는 것: 필드를 늘릴 때 형식을 직접 관리해야 한다. 4장 프레임과 형식이 달라 두 가지를 알아야 한다.
- 프로덕션이면 더 필요한 것: 필드 확장 규칙(타입-길이-값 옵션), 인증 태그(HMAC)와 재생 방어용 시각·카운터가 필요하다. 이 형식의 nonce 는 짝짓기용일 뿐 인증이 아니라서, 같은 망의 누구든 HELLO 를 위조할 수 있다.
- 나중에 다시 볼 조건: 공지에 장비 속성이 여러 개 붙을 때(옵션 형식이 필요), 12장에서 gRPC 로 옮길 때.
