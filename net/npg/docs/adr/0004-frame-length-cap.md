# 0004. 제어 채널 프레임은 4바이트 빅엔디언 길이 접두에 본문 상한 64 KiB 를 둔다

- 상태: 채택
- 날짜: 2026-10-21
- 장: ch04

## 맥락

TCP 는 경계 없는 바이트 흐름이라 읽는 쪽이 메시지를 직접 잘라야 한다. 3장은 줄 단위(`ping\n`, `pong\n`) 최소 형식을 썼고, ADR 0003 이 4장에서 길이 접두 프레임으로 옮기기로 약속했다. 줄 단위는 본문에 줄바꿈이 들어가면 깨지고, 읽는 쪽이 줄이 끝날 때까지 얼마든지 버퍼를 늘려야 한다.

길이 접두 프레임은 `[길이][본문]` 구조라 읽는 쪽이 길이를 읽고 그만큼 잡는다. 이때 길이를 믿으면 상대가 터무니없이 큰 값을 적어 읽는 쪽의 메모리를 바닥낼 수 있으므로 상한이 필요하다(노트 04-01 §4).

실제 시스템의 값(원문 확인).

- HTTP/2: 기본 `SETTINGS_MAX_FRAME_SIZE` 는 2^14(16,384)바이트이고 협상 상한은 2^24-1 이다. 넘으면 `FRAME_SIZE_ERROR` (RFC 9113 §4.2, §6.5.2)
- gRPC-go 서버: 수신 메시지 기본 4 MiB (`server.go` 의 `defaultServerMaxReceiveMessageSize`)
- 노트 04-01 TLV 예제: 10 MiB (`MaxPayloadSize`)

이 채널은 ping·pong 과 등록·명령 같은 제어 메시지만 싣고 큰 데이터를 나르지 않는다.

## 선택지

### A. 4바이트 `uint32` 길이 + 상한 65,536 을 코드로 검사한다

- 장점: 필드가 넓어 상한을 올려도 와이어 형식이 바뀌지 않는다. 상한 초과 길이를 실제로 만들 수 있어 리허설과 시험이 가능하다. 노트 04-01 구조와 같다.
- 단점: 매 프레임마다 길이 검사 코드가 필요하다. 검사를 빠뜨리면 4GB 할당이 가능해진다.

### B. 2바이트 `uint16` 길이(상한 65,535)

- 장점: 필드 최댓값이 곧 상한이라 검사 코드가 없다.
- 단점: 상한을 올리려면 와이어 형식을 바꿔야 한다. 상한을 넘는 위조 길이를 만들 수 없어 "상한 초과" 장면을 재현하지 못한다.

## 결정

A 를 고른다. 길이 필드는 4바이트 `uint32` 빅엔디언(네트워크 바이트 순서)이고, 본문 상한 `MaxFrameSize` 는 65,536(64 KiB)바이트이다. 읽는 쪽은 길이를 읽은 직후, 본문을 읽거나 버퍼를 잡기 전에 상한과 비교하고, 넘으면 연결을 끊는다. 제어 메시지는 작으므로 64 KiB 로 충분하고, 필요해지면 와이어 형식을 바꾸지 않고 상수만 올릴 수 있기 때문이다.

## 결과

- 쉬워지는 것: 본문에 어떤 바이트가 들어가도 경계가 깨지지 않는다. 위조된 큰 길이는 본문을 읽기 전에 막힌다.
- 어려워지는 것: 읽기 코드가 헤더 읽기, 상한 검사, 본문 읽기 세 단계로 늘고, 각 단계에서 `io.ReadFull` 로 정확한 바이트 수를 채워야 한다. 길이를 적은 만큼 본문이 오지 않고 멈추는 연결은 읽기 데드라인(ADR 0001)이 끊어 준다.
- 나중에 다시 볼 조건: 제어 메시지가 64 KiB 를 넘는 경우(예: 설정 묶음 전송), 연결 수가 많아 연결당 최대 버퍼 64 KiB 가 부담되는 경우.
