# Phase 4 계획 — Port Scanner

---

> `gonet scan` 한 명령으로 같은 포트를 CONNECT·SYN·UDP 세 방식으로 묻고, 커널이 무엇을 대신 해 주고 무엇을 숨기는지 패킷 수준에서 비교합니다. 참고 구현은 projectdiscovery/naabu 입니다.

## 무엇을 확인하려는가

Phase 0~3 은 모두 `net.Dial`·`net.Listen` 위에서 진행했습니다. 그래서 SYN 을 보내고 SYN-ACK 를 받고 RST 로 끊는 일은 늘 커널이 대신 했고, 코드에서는 "연결됐다" 또는 "거부됐다"라는 결과만 보였습니다. 포트 스캐너는 이 결과를 뒤집어서 봐야 하는 프로그램입니다. 포트 하나의 상태를 판정하려면 커널이 숨겨 온 패킷 하나하나를 증거로 읽어야 하기 때문입니다.

세 방식은 쓸 수 있는 증거가 다릅니다. 그래서 이 Phase 의 핵심 질문은 **"응답이 없다"는 닫힘인가, 필터인가, 손실인가?** 입니다.

```text
CONNECT  net.Dial       → 연결 성공=open / ECONNREFUSED=closed / timeout=filtered
SYN      raw ip4:tcp    → SYN-ACK=open / RST=closed / 무응답=filtered
UDP      datagram       → 응답=open / ICMP port unreachable=closed / 무응답=open|filtered
```

대상은 자기 소유 호스트, 즉 OrbStack `ubuntu` 머신과 `lo` 로만 한정합니다.



## 구현 범위 (세 단)

세 단은 이 순서로 쌓습니다. 앞 단의 판정표가 뒤 단의 정답지가 되기 때문입니다.

| 단 | 파일 (예정) | 내용 |
|---|---|---|
| 1 CONNECT | `internal/scan/connect.go` | `net.DialTimeout` 결과를 `errors.Is(err, syscall.ECONNREFUSED)` 와 timeout 으로 가릅니다. worker pool 과 token bucket rate limit 을 여기서 처음 붙이고, 세 단이 같이 씁니다 |
| 2 SYN | `internal/scan/syn.go`, `internal/scan/tcphdr.go` | `net.ListenPacket("ip4:tcp", ...)` 로 TCP 헤더 20바이트와 pseudo-header 체크섬을 직접 만들어 보냅니다. 같은 소켓에서 응답을 읽고 (응답의 출발지 포트 = 스캔한 포트, ACK 번호 = 보낸 seq+1) 로 짝을 맞춥니다. Phase 3 DNS 의 ID 대조와 같은 문제입니다 |
| 3 UDP | `internal/scan/udp.go` | 빈 페이로드와 DNS 질의 페이로드(Phase 3 인코더 재사용)를 보냅니다. 응답이 오면 open, ICMP port unreachable 이면 closed, 무응답이면 open\|filtered 입니다. `connect` 한 UDP 소켓에서 같은 ICMP 가 `ECONNREFUSED` 로 올라오는 경로도 비교합니다 |

외부 의존은 넣지 않습니다(`AGENTS.md` 원칙). naabu 는 gopacket 과 libpcap 을 쓰지만, 여기서는 헤더를 직접 짜서 Phase 3 에서 익힌 빅엔디언 필드 인코딩을 TCP 에 이어 씁니다. 결과는 `tcpdump -X` 로 대조합니다.

SYN 단은 Linux 에서만 돕니다. macOS(BSD 계열)의 raw 소켓에는 들어오는 TCP 세그먼트가 전달되지 않아 응답을 읽을 수 없기 때문입니다. 따라서 이 단은 OrbStack 머신에서 `sudo` 로 실행하거나, `setcap cap_net_raw+ep` 를 준 바이너리로 실행합니다.



## 장애 주입 실험

정상 동작 실험과 장애 주입 실험을 짝으로 둡니다. 각 실험은 실행 전에 예측을 적고, 끝나면 결과와 대조합니다.

| 실험 | 확인할 것 | 이어지는 앞 Phase |
|---|---|---|
| iptables `DROP` vs `REJECT --reject-with tcp-reset` | 같은 포트의 분류가 filtered 와 closed 로 갈리는지, CONNECT 에서는 각각 어떤 에러로 보이는지 | Phase 0 connect |
| SYN 스캔 중 캡처 | 스캐너는 SYN-ACK 를 받고 아무것도 안 했는데 RST 가 나가는지 확인합니다. 그 포트에 소켓이 없으니 커널이 RST 로 답합니다 | Phase 0 소켓 검색 |
| CONNECT 고속 스캔 | TIME-WAIT 누적, ephemeral port(`ip_local_port_range`) 고갈, EMFILE 가운데 무엇이 먼저 오는지 | Phase 1 FD 한도 |
| netem loss 20% | retry 0·1·3 에서 open 포트가 filtered 로 잘못 분류되는 비율 | Phase 2 손실 |
| ICMP rate limit | `net.ipv4.icmp_ratelimit` 때문에 UDP closed 가 open\|filtered 로 뒤바뀌는지 | Phase 2 UDP |
| rate 올리기 | 수신 쪽에서 버퍼 드롭(`nstat` UdpRcvbufErrors, 소켓 drops)이 시작되는 지점 | Phase 2 수신 버퍼 |
| 대상 서버 쪽 관측 | SYN 스캔이 서버 `ss` 에 SYN-RECV 로만 잠깐 남고 accept 대기열에는 오르지 않는지 | Phase 0 accept queue |



## 관측 명령

```bash
sudo tcpdump -i lo -nn -X 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'   # SYN·SYN-ACK·RST 와 헤더 바이트
sudo tcpdump -i lo -nn icmp                                          # port unreachable
ss -tan state time-wait | wc -l                                      # CONNECT 스캔의 흔적
ss -tan state syn-recv                                               # 대상 쪽 half-open
nstat -az | grep -E 'TcpOutRsts|TcpActiveOpens|IcmpOutDestUnreachs|UdpNoPorts|UdpRcvbufErrors'
strace -f -e trace=socket,sendto,recvfrom,connect ./bin/gonet scan ...
getcap ./bin/gonet
```



## 배울 개념

이 Phase 를 4-Phase 로 돌 때 개념 이해(Phase 1) 질문의 후보입니다. 앞 Phase 와 이어지는 지점을 함께 적습니다.

- **TCP 헤더 필드와 플래그, pseudo-header 체크섬.** Phase 3 에서 DNS 헤더 12바이트를 빅엔디언으로 짠 일의 연장입니다. TCP 체크섬에 IP 주소가 들어가는 이유(pseudo-header)가 새로 나옵니다.
- **half-open 과 SYN cookie.** SYN 만 보내고 끝까지 가지 않은 연결이 대상 서버에 무엇을 남기는지 봅니다. Phase 0 의 accept 대기열과 SYN 대기열을 구분하게 됩니다.
- **커널 자동 RST.** 소켓 검색에 실패한 세그먼트에 커널이 어떻게 답하는지 봅니다. Phase 0 의 4-tuple 소켓 검색을 반대쪽에서 보는 셈입니다.
- **raw socket 과 CAP_NET_RAW.** SYN 스캔은 권한이 필요하고 CONNECT 스캔은 필요 없는 이유를 설명합니다.
- **ICMP 오류 메시지의 전달 경로.** 같은 port unreachable 이 unconnected UDP 에서는 보이지 않고, connected UDP 에서는 `ECONNREFUSED` 로 올라옵니다. Phase 2 의 connected UDP 실험과 이어집니다.
- **판정의 비대칭.** 응답이 있으면 증거가 되지만, 응답이 없는 것은 증거가 아닙니다. filtered, 손실, rate limit 이 모두 무응답으로 보입니다.
- **rate limit(token bucket)과 worker pool.** retry·timeout·rate 를 조정하면 정확도와 속도를 서로 맞바꾸게 됩니다. Phase 13 retry storm 의 예고편입니다.
- **ephemeral port 와 TIME-WAIT.** 클라이언트 쪽에서 먼저 바닥나는 자원이 무엇인지 봅니다. Phase 1 은 서버 쪽 FD 를 봤습니다.



## naabu 대응표

| naabu | 뜻 | 우리 구현 |
|---|---|---|
| `-s c` (기본) | CONNECT 스캔 | 1단 |
| `-s s` | SYN 스캔, root 와 libpcap 필요 | 2단 (raw socket, libpcap 없음) |
| `-uP`, `-cp` | UDP 프로토콜별 페이로드, 사용자 페이로드 | 3단 DNS 페이로드 |
| `-rate` (기본 1000) | 초당 패킷 수 | token bucket |
| `-c` (기본 25) | worker 수 | worker pool |
| `-retries` (기본 3), `-timeout` (기본 1000ms) | 재시도와 응답 대기 | netem 실험의 변수 |
| `-warm-up-time` (기본 2s) | 단계 사이 대기 | 마지막 SYN 뒤 늦은 응답을 기다리는 창 |
| `-verify` | 찾은 포트를 TCP 로 다시 확인 | SYN 결과를 1단 CONNECT 로 재확인 |

넣지 않는 기능과 이유는 이렇습니다.

- host discovery(`-pe -pp -pm -ps -pa -arp -nd`): L2·L3 계층까지 넓어지고, OrbStack 은 VM 하나라서 ARP 실험이 제한됩니다.
- `-exclude-cdn`, `-passive`(Shodan), `-nmap-cli`, `-ss`: 정찰 운영 기능이라 primitive 학습과 관계가 적습니다.

나머지 비교는 구현을 마친 뒤에 합니다. naabu 의 `pkg/scan` 이 SYN 응답의 짝을 어떻게 맞추는지, rate 를 어디서 제어하는지를 우리 구현과 나란히 읽습니다.
