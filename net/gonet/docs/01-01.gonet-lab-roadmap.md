# Go Network Lab

> Go로 네트워크 primitive를 직접 구현하고, 실패시키고, 관측하면서 TCP/UDP에서 Reverse Tunnel, P2P Overlay, Linux Networking, eBPF/Cilium까지 단계적으로 내려가는 장기 학습 프로젝트.

## Metadata

- Status: High Priority / Planned
- Domain: Networking / Linux / Distributed Systems / Observability / Kubernetes
- Primary Language: Go
- Working Name: `gonet-lab`
- Goal: 제품 완성보다 네트워크 primitive의 직접 구현과 관측

  - grpc/grpc-go (Phase 7·9·10·14·15 비교용)
  - wireguard-go `tun` (Phase 13 비교용)

## Why This Project

네트워크 기술을 제품 이름 중심으로 외우지 않고 다음 연결을 직접 확인하는 것이 목적이다.

```text
Go net API
→ socket
→ file descriptor
→ TCP / UDP
→ application protocol
→ proxy
→ tunnel
→ multiplexing
→ discovery
→ P2P routing / relay
→ Linux routing / NAT
→ eBPF
→ CNI
→ Cilium
```

각 단계는 반드시 다음 사이클을 따른다.

```text
구현 → 정상 동작 → 장애 주입 → 관측 → 원인 설명 → 문서화
```

단순히 라이브러리를 사용해 기능을 만드는 것이 아니라 다음 질문에 답할 수 있어야 한다.

- resource owner는 누구인가?
- connection lifecycle은 누가 관리하는가?
- blocking/non-blocking은 어디에서 발생하는가?
- timeout은 어느 계층이 책임지는가?
- backpressure가 발생하면 어디에 queue가 쌓이는가?
- peer/server가 사라지면 어떤 상태가 남는가?
- application 코드 아래에서 kernel은 무엇을 하는가?
- 해당 동작을 packet/syscall/metric으로 직접 확인할 수 있는가?

## Phase 4 - Port Scanner

같은 포트 하나를 CONNECT·SYN·UDP 세 방식으로 물어보고, 커널이 무엇을 대신 해 주고 무엇을 숨기는지 비교한다. 대상은 자기 소유 호스트(OrbStack 머신, `lo`)로 한정한다.

```bash
gonet scan --mode connect|syn|udp --ports 1-1024 --rate 500 <host>
```

```text
CONNECT  net.Dial        → open / closed(ECONNREFUSED) / filtered(timeout)
SYN      raw ip4:tcp     → SYN-ACK=open / RST=closed / 무응답=filtered
UDP      datagram        → 응답=open / ICMP port unreachable=closed / 무응답=open|filtered
```

### Primitive

- 3-way handshake, SYN / SYN-ACK / RST
- half-open, 커널 자동 RST
- ECONNREFUSED
- raw socket (`net.ListenPacket("ip4:tcp")`), CAP_NET_RAW
- TCP 헤더 직접 인코딩, pseudo-header 체크섬
- ICMP port unreachable (type 3 code 3)
- open|filtered
- worker pool, token bucket rate limit
- retry / timeout
- ephemeral port, TIME-WAIT

### 실험

- iptables `DROP` vs `REJECT --reject-with tcp-reset` 에서 분류가 어떻게 바뀌는가
- SYN 스캔 중 커널이 스스로 보내는 RST 를 tcpdump 로 확인
- CONNECT 고속 스캔으로 TIME-WAIT 누적·ephemeral port 고갈·EMFILE 관찰
- netem loss 20% 에서 retry 유무에 따른 filtered 오판율
- ICMP rate limit 으로 UDP closed 가 open|filtered 로 뒤바뀌는지
- rate 를 올리며 수신 버퍼 드롭 관측

### 핵심 설계 질문

**"응답이 없다"는 닫힘인가, 필터인가, 손실인가?**

무응답은 증거가 아니다. retry·timeout·rate 를 바꾸며 정확도와 속도를 무엇과 맞바꾸는지 직접 측정한다.

### Reference

- projectdiscovery/naabu — `pkg/scan`, `pkg/runner` (gopacket + libpcap 방식). 직접 짠 뒤 "naabu 는 응답 짝 맞추기와 rate 제어를 어디서 하는가"를 비교한다
- 상세 계획: `docs/03-02.gonet-lab-phase4-plan.md`

## Phase 11 - P2P Overlay

중앙 server만 바라보던 구조에서 peer 간 overlay를 만든다.

```text

       /      \

```

### 최소 Peer Model

```go
type Peer struct {
    ID       string
    Address  string
    LastSeen time.Time
}
```

### 단계

```text
peer discovery
→ peer table
→ direct connection
→ routing
→ relay
```

### 핵심 문제

- peer identity와 network location 분리
- unreachable peer
- peer churn
- route selection
- relay fallback
- bootstrap node 역할

### 선택 실험 — UDP hole punching

relay 는 늘 통하지만 모든 바이트가 제3의 노드를 지난다. 실제 P2P 시스템은 먼저 NAT 에 구멍을 뚫어 직접 연결을 시도하고, 실패할 때만 relay 로 물러난다. Phase 2 UDP 위에 쌓는 실험이다.

```text
[A] ── [NAT-A] ──┐                  ┌── [NAT-B] ── [B]
                 ├── 공인망 bridge ──┤
                 └── [bootstrap] ───┘
1. A·B 가 bootstrap 에 UDP 로 등록 → bootstrap 이 본 공인 주소(NAT 바깥 주소:포트)를 서로에게 알려 줌
2. A·B 가 동시에 상대 공인 주소로 UDP 송신 → 양쪽 NAT 에 매핑이 생겨 직접 통로가 열림
3. 정해 둔 시간 안에 응답이 없으면 relay fallback
```

- OrbStack `ubuntu` 안에 netns 다섯(A, NAT-A, B, NAT-B, bootstrap)과 공인망 역할의 bridge 하나를 만든다. NAT-A·NAT-B 는 `ip_forward` 를 켜고 바깥쪽 인터페이스에 iptables `MASQUERADE` 를 건다
- 같은 실험을 `MASQUERADE --random` 으로 다시 돌린다. 목적지마다 바깥 포트가 바뀌는 NAT 에서는 bootstrap 이 본 주소와 상대가 보게 될 주소가 달라지므로 구멍이 열리지 않고 relay 로 물러나야 한다
- 관측: 각 NAT netns 에서 `conntrack -L -p udp` 로 매핑을 본다. 상대의 펀칭 패킷이 내 첫 송신보다 먼저 NAT 에 닿으면 conntrack 항목이 먼저 생겨, 나가는 쪽 SNAT 가 다른 포트를 고를 수 있다. 평범한 `MASQUERADE` 에서도 펀칭이 실패하면 이 경합부터 의심한다
- 학습 질문: 왜 UDP 는 뚫리고 TCP 는 어려운가? NAT 매핑은 얼마 동안 살아 있고, keepalive 를 얼마나 자주 보내야 하는가?
- Reference: RFC 4787 (NAT 의 UDP 동작 요구사항 — 매핑·필터링 유형 용어), RFC 5128 (NAT 를 건너는 P2P 통신 현황), Tailscale "How NAT traversal works"

### Reference

Tor 는 relay 를 도달성이 아니라 익명성에 쓰는 오버레이다. relay fallback 을 직접 짠 뒤 읽는다.
- Tor 명세 `tor-spec` (spec.torproject.org) — CREATE2·EXTEND2 로 서킷을 한 홉씩 늘리고, relay cell 을 홉마다 한 겹씩 암호화해 각 릴레이가 바로 앞뒤 홉만 알게 하는 구조. 비교 질문: 내 relay 는 보내는 peer 와 받는 peer 를 둘 다 아는데, 어느 홉도 둘을 함께 알지 못하게 하려면 무엇이 더 필요한가? 홉을 하나에서 셋으로 늘리면 지연과 노출은 각각 어떻게 바뀌는가?
- Tor 앱 쪽 입구가 SOCKS5 라는 점은 Phase 6 Reference 에 적었다.
- Tor 는 TCP 스트림만 실어 나르는 오버레이다. IP 패킷을 통째로 실어 나르는 오버레이는 Phase 13 에서 만든다.

## Phase 13 - IP Overlay (TUN)

Phase 11 까지의 오버레이는 TCP 스트림을 옮기는 애플리케이션 수준 오버레이다. 여기서는 IP 패킷을 통째로 옮겨, 커널 라우팅 테이블이 일반 프로그램의 트래픽을 오버레이로 보내게 만든다. WireGuard·Tailscale, 그리고 K8s CNI 오버레이(Flannel VXLAN 등)가 사는 계층이다. 로드맵 앞머리의 `P2P routing / relay → Linux routing / NAT` 사이를 잇는 Phase 다.

선행은 Phase 2(UDP), 8(터널), 11(peer·relay)이다. Phase 12 DHT 와는 직접 이어지지 않는다.

```text
curl 10.99.0.2                      (일반 프로그램, 오버레이를 모름)
→ 커널 라우팅: 10.99.0.0/24 dev gonet0
→ TUN 장치 gonet0
→ gonet-agent 가 IP 패킷 하나를 read
→ UDP 데이터그램 하나에 담아 상대 peer 에 전달 (캡슐화)
→ 상대 gonet-agent 가 꺼내 자기 TUN 에 write
→ 상대 커널이 받아 목적지 프로그램에 전달
```

바깥 전송은 "IP 패킷 하나 = UDP 데이터그램 하나"를 기본으로 하고, 이 UDP 터널이 이 Phase 의 산출물이다. 가능하면 Phase 11 에서 뚫은 UDP 경로를 그대로 바깥 계층으로 쓴다. 그러면 TUN + 뚫은 UDP 구멍 + relay fallback 이라는 Tailscale 의 뼈대가 완성된다. Phase 8·9 의 TCP 터널에 같은 패킷을 길이 접두로 싣는 방식은 아래 비교 실험으로만 쓴다.

### 학습

- TUN 과 TAP (L3 패킷 vs L2 프레임)
- `/dev/net/tun` 과 TUNSETIFF ioctl (`golang.org/x/sys/unix` 의 `TUNSETIFF`·`IFF_TUN`·`IFF_NO_PI`)
- 권한: TUN 생성에는 `CAP_NET_ADMIN` 이 필요하다. `sudo ip tuntap add dev gonet0 mode tun user $USER` 로 미리 만들어 두면 agent 를 root 없이 띄울 수 있다
- `ip route` 로 오버레이 대역을 TUN 으로 보내기, netns 둘로 두 노드를 한 VM 안에 재현
- 캡슐화 오버헤드와 MTU — 바깥 IPv4·UDP 헤더 28바이트에 자기 프로토콜 헤더가 더해진다. TUN MTU 를 그만큼 낮추는 이유(WireGuard 기본 1420)
- TCP-over-TCP 문제 — 바깥 터널이 TCP 면 안쪽 TCP 재전송과 바깥 TCP 재전송이 겹쳐 지연이 폭증한다. WireGuard 가 UDP 를 쓰는 이유
- (선택) `net.ipv4.ip_forward` 와 `MASQUERADE` 로 한 peer 를 exit node 로 만들기

### 장애 주입

- MTU 블랙홀: 두 peer 사이에 중간 netns 를 두고 그 링크 MTU 를 1400 으로 낮춘다. TUN MTU 는 1500 으로 두고, 바깥 UDP 소켓에 `IP_MTU_DISCOVER = IP_PMTUDISC_DO` 를 걸어 커널이 조각내지 못하게 한다. 그러면 큰 바깥 데이터그램은 중간에서 버려지거나 송신 때 `EMSGSIZE` 로 실패한다. 안쪽에서는 작은 요청은 통하고 큰 응답만 멈추는 증상을 관측한다. 이 옵션 없이 veth 로만 이으면 커널이 조각내고 상대가 다시 조립해 증상이 나타나지 않는다
- 해결 둘을 비교한다: TUN MTU 를 낮추기(1400 − 28 − 자기 헤더), 또는 iptables mangle 의 `TCPMSS --set-mss` 로 TUN 으로 나가는 SYN 의 MSS 를 줄이기. `--clamp-mss-to-pmtu` 는 나가는 경로(TUN)의 MTU 를 기준으로 잡으므로 TUN MTU 를 1500 으로 둔 채로는 효과가 없다
- TCP-over-TCP: 바깥을 Phase 8 TCP 터널로 바꾸고 `tc netem` 손실을 주입 → UDP 바깥과 안쪽 TCP 지연·처리량 비교

### Reference

- wireguard-go `tun` 패키지 (golang.zx2c4.com/wireguard/tun) — Linux·macOS·Windows TUN 을 같은 인터페이스로 감싼 구현. 비교 질문: 패킷 하나마다 커널과 유저 공간을 오가는 비용을 어떻게 줄이는가?
- Linux 커널 `Documentation/networking/tuntap.rst`
- Flannel 옛 `udp` backend — `flannel0` TUN 으로 유저 공간에서 캡슐화하던, 이 Phase 와 같은 구조다. 지금 문서는 디버깅용으로만 권한다. 비교 질문: 왜 성능 때문에 밀려났는가?
- Flannel VXLAN backend — 같은 IP 오버레이를 커널 안의 VXLAN 장치로 캡슐화한다. 비교 질문: 내 TUN 오버레이와 VXLAN 은 캡슐화를 어디서 하며, 그 차이가 성능과 관측(Phase 16 eBPF)에 무엇을 바꾸는가?
