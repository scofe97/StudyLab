# 포인터로 "없음"을 표현하기
---

## 왜 값 타입으로는 "없음"을 말할 수 없는가

> Go 의 값 타입에는 **"값이 아직 없는 상태"가 없습니다.** 선언하면 즉시 zero value 가 들어차기 때문입니다.

`Result` 에서 이 문제를 만났습니다. 단계별 상세를 "그 단계가 정보를 남겼을 때만" 내보내야 하는데, 값 타입으로 두면 그게 안 됩니다.

```go
type Result struct {
	DNS DNSInfo `json:"dns,omitempty"`   // IP 직접 지정이면 DNS 를 안 거친다
}
```

IP 를 직접 지정해 DNS 를 거치지 않았어도 `r.DNS` 는 존재합니다. `DNSInfo{}` 라는 빈 구조체가 들어 있습니다. **"없다"가 아니라 "비어 있다"** 입니다. 그리고 JSON 은 이렇게 나갑니다.

```json
{"dns":{"addresses":null}}
```

읽는 쪽에서는 "DNS 를 거쳤는데 주소를 못 받았다"로 보입니다. 실제로는 거치지도 않았습니다. **사실이 뒤바뀌었습니다.**



## zero value — 선언만 하면 채워지는 값

> Go 는 초기화하지 않은 변수를 그대로 두지 않습니다. 타입마다 정해진 값으로 채웁니다.

```go
var s string    // ""
var n int       // 0
var b bool      // false
var p *DNSInfo  // nil
var xs []string // nil
var m map[string]int // nil
type T struct{ A int; B string }
var t T         // T{A: 0, B: ""}
```

C 처럼 쓰레기 값이 들어가지 않는다는 점은 안전합니다. 그런데 부작용이 있습니다. **"값이 없다"를 표현할 자리가 사라집니다.** `n` 이 0 일 때 "0 이 들어왔다"인지 "아무것도 안 넣었다"인지 구분되지 않습니다.

`encoding/json` 의 `omitempty` 가 이 문제를 그대로 물려받습니다. 비었다고 판정하는 대상이 정해져 있습니다.

```text
false · 0 · nil 포인터 · nil 인터페이스 · 길이 0 인 array·slice·map·string
```

**struct 가 이 목록에 없습니다.** 모든 필드가 zero value 인 구조체도 "비었다"로 보지 않습니다. 그래서 `omitempty` 가 아무 일도 하지 않습니다.



## 포인터는 "가리키는 곳이 없음"을 가질 수 있습니다

> 포인터의 zero value 는 `nil` 이고, `nil` 은 **값이 아니라 값의 부재**를 뜻합니다.

```go
type Result struct {
	DNS *DNSInfo `json:"dns,omitempty"`
}
```

이제 세 상태가 구분됩니다.

| 코드 | 뜻 | JSON |
|---|---|---|
| `r.DNS == nil` | DNS 단계를 거치지 않았다 | 키가 **없다** |
| `r.DNS = &DNSInfo{}` | 거쳤는데 주소를 못 얻었다 | `"dns":{"addresses":null}` |
| `r.DNS = &DNSInfo{Addresses: []string{"1.2.3.4"}}` | 거쳐서 주소를 얻었다 | `"dns":{"addresses":["1.2.3.4"]}` |

값 타입에서는 첫 줄과 둘째 줄이 같았습니다. 포인터로 바꾸니 **한 층이 늘어난 것**입니다. `nil` 은 `DNSInfo` 가 가질 수 있는 어떤 값과도 겹치지 않아서, "없음"을 안전하게 표현합니다.

이것이 `StatusSkipped` 와 같은 사상입니다. `ok`/`failed` 둘로는 "실행되지 않았다"를 말할 수 없어서 세 번째 상태를 만들었습니다. 표현할 수 없는 사실이 있으면 **표현할 자리를 만듭니다.**



## 언제 포인터로 두는가

> "없음"이 의미 있는 상태일 때만입니다. 그 외에는 값 타입이 낫습니다.

판단 기준을 셋으로 정리할 수 있습니다.

**하나, 부재와 zero value 가 다른 사실인가.** `Result.DNS` 는 다릅니다. 반면 `StageResult.Duration` 은 다르지 않습니다 — skipped 일 때 0 이고, 그 사실은 `Status` 가 이미 말합니다. 그래서 포인터로 두지 않았습니다.

**둘, 그 구분이 읽는 쪽의 판단을 바꾸는가.** `reused` 는 `bool` 값 타입입니다. `false` 가 "재사용 안 했다"라는 **의미 있는 정보**라서 `omitempty` 조차 붙이지 않았습니다. 없어지면 확인할 수 없게 됩니다.

**셋, 크기가 커서 복사를 피해야 하는가.** 이건 성능 축이고, 여기서는 해당하지 않습니다. 구조체 몇 필드를 복사하는 비용은 무시할 수준입니다. **크기 때문에 포인터를 쓰는 것과 의미 때문에 쓰는 것을 섞지 않는 편이 좋습니다** — 섞으면 나중에 `nil` 검사를 빼먹게 됩니다.



## 대가 — `nil` 을 역참조하면 프로그램이 죽습니다

> 포인터를 쓰면 "없음"을 표현할 수 있게 되지만, 매번 확인해야 하는 부담이 생깁니다.

```go
fmt.Println(r.DNS.Addresses)   // r.DNS 가 nil 이면 panic
```

컴파일은 통과합니다. 실행할 때 죽습니다. 그래서 쓰는 쪽마다 확인이 붙습니다.

```go
if r.DNS != nil {
	fmt.Println(r.DNS.Addresses)
}
```

값 타입이면 이 확인이 필요 없습니다. **"없음을 표현하는 능력"과 "확인 부담"을 맞바꾸는 것**이고, 그래서 아무 데나 포인터를 쓰지 않습니다.

7단계에서 waterfall 을 찍을 때 이 확인이 실제로 나옵니다. `nil` 인 단계는 상세를 못 찍으니 건너뛰어야 합니다. 그리고 그게 화면에 "실행되지 않음"으로 나오는 것이니, **확인 부담이 곧 기능**이 되는 자리이기도 합니다.



## 다른 언어에서는

> 같은 문제를 다르게 풉니다. 비교해 두면 Go 의 선택이 무엇을 포기한 것인지 보입니다.

| 언어 | "없음"을 표현하는 법 | 컴파일러가 막아 주나 |
|---|---|---|
| Go | 포인터의 `nil` | **안 막는다.** 역참조하면 런타임 패닉 |
| Java | 참조의 `null`, `Optional<T>` | `null` 은 안 막는다. `Optional` 은 `get()` 을 강제해 인지시킨다 |
| Kotlin·Swift | `T?` 타입 | **막는다.** 확인 없이 접근하면 컴파일 에러 |
| Rust | `Option<T>` | **막는다.** `match` 로 두 경우를 다 다뤄야 한다 |

Go 는 표현은 되게 하고 검사는 안 합니다. 문법이 단순해지는 대신 `nil` 확인이 프로그래머 책임으로 남습니다.

Java 를 주로 쓰셨다면 `Optional<DNSInfo>` 를 떠올리실 만한 자리입니다. Go 에는 그런 래퍼 타입이 표준으로 없고, **포인터가 그 역할을 겸합니다.** 제네릭이 들어온 뒤 `Option[T]` 를 직접 만드는 시도가 있지만, 표준 라이브러리와 `encoding/json` 이 포인터를 전제하므로 이 프로젝트에서는 포인터로 갑니다.
