# goroutine 과 데이터 레이스
---

## 왜 훅을 적는 데 동시성이 끼어드는가

> 우리는 `client.Do(req)` 한 줄을 부를 뿐인데, 훅은 **우리가 만들지 않은 여러 실행 흐름에서** 불립니다.

`net/http/httptrace` 문서가 이렇게 경고합니다.

> Functions may be called **concurrently from different goroutines** and some may be called **after the request has completed or failed.**

두 문장이 각각 다른 위험입니다. 앞은 "훅끼리 동시에", 뒤는 "요청이 끝난 뒤에도" 입니다. 뒷문장이 특히 까다로운데, `Do()` 가 반환됐으니 다 끝났다고 믿고 결과를 읽는 그 순간에도 훅이 살아서 쓰고 있을 수 있다는 뜻이기 때문입니다.

```go
resp, err := client.Do(req)   // 반환됐다
span := tracer.conn           // 읽는 중
                              //   ↑ 이 순간 훅이 tracer.conn 에 쓰고 있을 수 있다
```



## goroutine — Go 의 실행 단위

> `go f()` 라고 쓰면 `f` 가 떨어져 나가 동시에 돕니다. OS 스레드보다 훨씬 가벼워서 수천 개를 만들어도 됩니다.

```go
go doSomething()   // 이 줄은 기다리지 않고 즉시 다음 줄로 간다
```

직접 `go` 를 쓰지 않아도 goroutine 을 만나게 됩니다. **표준 라이브러리가 내부적으로 여럿 쓰기 때문**입니다. `http.Transport` 는 연결마다 읽기·쓰기 goroutine 을 두고, DNS 조회는 또 다른 흐름에서 돕니다.

그래서 훅이 불리는 곳은 **우리가 `Do()` 를 호출한 그 흐름이 아닙니다.** DNS 를 조회하는 goroutine 이 `DNSDone` 을 부르고, 연결을 세우는 goroutine 이 `ConnectDone` 을 부릅니다. 우리 `tracer` 구조체 하나를 그 여럿이 함께 씁니다.



## 데이터 레이스 — 조건 셋이 모일 때

> 둘 이상의 goroutine 이 **같은 메모리**에 접근하고, 그중 **적어도 하나가 쓰기**이며, 접근 순서를 정하는 **동기화가 없을 때** 데이터 레이스입니다.

셋이 다 모여야 합니다. 둘 다 읽기만 하면 안전하고, 락으로 순서가 정해져 있어도 안전합니다.

**"적어도 하나가 쓰기"** 라는 조건을 놓치기 쉽습니다. 쓰는 쪽만 보호하면 소용없습니다 — 읽기와 쓰기가 부딪혀도 레이스입니다. 그래서 읽는 경로에도 락이 필요합니다.

### "값이 좀 깨지는" 수준이 아닙니다

Go 메모리 모델에서 데이터 레이스가 있는 프로그램은 **동작이 정의되지 않습니다.** 컴파일러가 레이스가 없다고 가정하고 최적화하기 때문에, 읽기가 통째로 사라지거나 명령 순서가 뒤집히는 일이 실제로 일어납니다.

`time.Time` 처럼 내부에 여러 워드를 가진 값은 **절반만 쓰인 상태**로 읽힐 수도 있습니다. 우리가 훅에서 다루는 게 정확히 그 타입입니다.

### 재현이 어려운 것이 더 나쁩니다

데이터 레이스는 대개 **평소엔 멀쩡하다가 부하가 걸리면 터집니다.** 타이밍이 맞아야 드러나기 때문입니다. 개발 중에는 한 번도 안 보이다가 운영에서 간헐적으로 이상한 값이 나오는 종류라, 버그로 인지되기까지도 오래 걸립니다.



## `sync.Mutex` 로 막습니다

> 한 번에 하나만 들어가게 하는 자물쇠입니다. `Lock()` 으로 잠그고 `Unlock()` 으로 엽니다.

```go
type tracer struct {
	mu sync.Mutex      // 아래 전 필드를 이 하나가 지킨다
	dns, conn, tlsh stageSpan
	// ...
}

DNSStart: func(httptrace.DNSStartInfo) {
	t.mu.Lock()
	defer t.mu.Unlock()
	t.dns.start = time.Now()
},
```

`defer` 는 **함수가 끝날 때 실행을 예약**하는 문법입니다. 중간에 `return` 하든 panic 이 나든 반드시 불립니다. `Lock()` 바로 아래에 `defer Unlock()` 을 두는 것이 Go 의 관용구인데, **해제를 빼먹으면 다음에 `Lock()` 하는 쪽이 영원히 기다려** 프로그램이 그 자리에서 멈추기 때문입니다.

### 읽기는 한 번에 통째로 베낍니다

읽는 쪽도 락을 잡아야 하지만, 호출자에게 매번 락을 잡으라고 요구하면 빼먹기 쉽습니다. 그래서 **한 번 잡고 전부 복사해 주는 메서드**를 둡니다.

```go
func (t *tracer) snapshot() traceSnapshot {
	t.mu.Lock()
	defer t.mu.Unlock()

	addrs := make([]string, len(t.addresses))
	copy(addrs, t.addresses)     // 슬라이스는 따로 떠야 한다
	// ... 전 필드를 복사해 돌려준다
}
```

슬라이스를 `copy` 로 뜨는 이유가 있습니다. 그냥 대입하면 **내부 배열을 공유**해서 복사본이 아니게 됩니다. 락을 풀고 나서 훅이 `append` 하면 그 배열이 바뀔 수 있습니다.



## 락의 성능 비용은 얼마나 되는가

> 비용은 분명히 있습니다. 다만 **무엇과 견주는가**가 판단을 가릅니다.

경합이 없을 때 `sync.Mutex` 의 `Lock`/`Unlock` 은 원자적 연산 한두 번입니다. **나노초 단위**입니다. 우리가 재는 대상과 견주면 이렇습니다.

| | 규모 |
|---|---|
| 락 한 번 (비경합) | 수십 ns |
| 요청당 훅 호출 | 8번 안팎 |
| 재는 대상 (DNS·TCP·TLS) | 3ms · 12ms · 45ms = **수천만 ns** |

측정 대상의 **백만분의 1** 수준이라 결과에 드러나지 않습니다.

락이 실제로 문제가 되는 조건은 둘입니다. 하나는 **경합이 심할 때**입니다 — 여러 goroutine 이 같은 락을 두고 계속 다투는 경우입니다. 다른 하나는 **락 안에서 오래 걸리는 일을 할 때**입니다. I/O 나 시스템 콜이 여기 해당합니다.

우리는 둘 다 아닙니다. 훅 하나가 하는 일이 필드 대입 한두 개이고, 한 요청의 훅들은 대체로 순차적으로 옵니다.

### 대안과 왜 안 쓰는가

| 대안 | 왜 여기서는 안 쓰나 |
|---|---|
| `sync/atomic` | 원자적으로 다룰 수 있는 건 워드 하나다. `time.Time` 여러 개를 한 묶음으로 못 바꾼다 |
| `sync.RWMutex` | 읽기가 많을 때 유리한데, 우리는 쓰기가 대부분이고 읽기는 `snapshot()` 한 번입니다. 오히려 오버헤드가 큽니다 |
| 채널로 이벤트를 모으기 | goroutine 과 select 루프가 늘어난다. 얻는 게 없이 복잡도만 는다 |

**재 보지 않고 최적화하지 않는다**는 원칙이 여기 적용됩니다. 측정 대상이 밀리초인데 나노초를 아끼려 구조를 비트는 것은 값이 안 맞습니다.



## Go 에는 레이스 탐지기가 있습니다

> 재현이 어려운 버그를 **실행 중 접근 패턴만으로** 잡아 줍니다. Go 의 강점 중 하나입니다.

```bash
go test -race ./...     # Makefile 의 test 타깃
go run -race main.go
go build -race
```

런타임이 모든 메모리 접근을 추적해, 동기화 없이 같은 주소에 접근한 goroutine 쌍을 찾으면 보고합니다. **실제로 값이 깨지지 않아도** 잡습니다. 타이밍이 맞아떨어지길 기다릴 필요가 없다는 뜻입니다.

대가는 속도와 메모리입니다. 실행이 몇 배 느려지고 메모리도 더 씁니다. 그래서 운영 빌드가 아니라 **테스트에서** 켭니다.

이 프로젝트에서는 `make check` 가 `go test -race ./...` 를 돌립니다. 훅에서 락을 빼면 4단계 테스트가 실패하므로, **문서에 적은 약속을 기계가 검사하는 자리**입니다.
