# NetPath Lab 방향성
---

## 이 순서를 잡은 기준

> 요청 하나가 목적지에 닿기까지 네 번 실패할 수 있습니다. 이름을 못 찾거나, 연결이 안 되거나, 신원 확인이 깨지거나, 응답이 잘못 오거나. 이 프로젝트는 **그 넷을 갈라서 재는 것**에서 시작해 관측 파이프라인과 클러스터로 넓혀 갑니다.

순서를 잡은 규칙은 둘입니다.

첫째, **측정 모델 → 관측 신호 → 클러스터 환경 → 프록시 비교** 로 갑니다. 뒤 국면이 앞 국면의 어휘로 설명되도록 놓았습니다. OpenTelemetry span 을 나누려면 단계가 먼저 나뉘어 있어야 하고, "노드마다 결과가 다르다"를 말하려면 한 노드에서 재는 법이 먼저 있어야 합니다.

둘째, **코어가 바깥을 모르는 상태를 유지**합니다. `probe/` 가 Kubernetes 나 OpenTelemetry 를 알기 시작하면 뒤 국면에서 계층을 갈아끼울 수 없습니다. 이 경계는 문서의 약속이 아니라 `make lint` 가 강제합니다. Phase 5 에서 Istio 를 얹었다 뺐다 할 수 있는 것이 이 제약의 값입니다.

배지는 셋입니다. **필수**는 빼면 그 국면이 성립하지 않는 것, **확장**은 빼도 굴러가지만 넣으면 값이 커지는 것, **선택**은 목표가 생겼을 때만 여는 것입니다. 국면을 다 밟아야 하는 것은 아닙니다. **4국면까지가 완결**이고 5국면은 그 위에 얹는 비교층입니다. 1.5국면(TLS)은 소수점을 달았는데, **2국면 이후가 이 국면에 기대지 않아서** 건너뛰어도 성립하기 때문입니다.

실제로 뒤가 막히는 선행은 셋입니다.

1. 1국면의 오류 분류가 없으면 2국면의 span attribute 가 문자열 뭉치가 됩니다. `tcp_refused` 와 `tcp_timeout` 을 값으로 갈라 두었기 때문에 대시보드에서 나눠 셀 수 있습니다.
2. 2국면을 건너뛰고 3국면에 가면 노드가 여럿이 된 순간 결과를 모을 곳이 없습니다. 터미널 출력은 한 곳에서 재는 동안만 읽힙니다.
3. 4국면 없이 5국면을 열면 Istio 가 무엇을 해결했는지 알 수 없습니다. 비교하려면 비교 대상이 먼저 있어야 하고, 그것이 4국면의 장애 카탈로그입니다.



## 무엇을 만들고 무엇을 안 만드는가

> 이미 있는 도구와 겹치는 자리를 먼저 긋습니다. 비슷한 것을 다시 만드는 데 시간을 쓰지 않기 위해서입니다.

| 도구 | 하는 일 | NetPath Lab 과의 관계 |
|---|---|---|
| Prometheus Blackbox Exporter | HTTP·DNS·TCP·ICMP·gRPC 프로빙 | **가장 가까움.** 단계를 나누지 않고 한 지점에서만 잼 |
| Hubble (Cilium) | eBPF 로 패킷 흐름·DROP 관측 | 커널에서 봄. 이쪽은 애플리케이션에서 봄 |
| Istio · Kiali | 서비스 간 요청·지연·정책 | 프록시가 본 것. 프록시 이전은 못 봄 |
| Grafana Beyla | eBPF 자동 계측 | 트래픽을 관측. 트래픽을 만들지는 않음 |
| k6 · vegeta | 부하 생성 | 성능 측정용. 실패 원인 분해는 안 함 |

**차별점은 넷입니다.** 다중 관측 지점, 단계별 trace, 장애 재현, 근거 기반 진단. 이 넷이 아니면 Blackbox Exporter 를 쓰는 게 맞습니다.

**직접 만들지 않는 것**도 정해 둡니다. eBPF 프로그램, CNI, Operator/CRD, 메트릭 저장소, AI 기반 RCA, 프로덕션 HA. 앞의 둘은 `~/study/podwire` 가 맡고, 나머지는 이미 있는 것을 쓰거나 학습 목표 밖입니다.



## 낡음 점검

> 기준일 2026-09-10. 표준 라이브러리에 기대는 부분은 오래가고, 생태계에 기대는 부분은 짧습니다.

`net/http/httptrace` 는 Go 1.7(2016) 에 들어온 뒤 훅 구성이 거의 그대로입니다. 이 프로젝트의 코어가 여기에만 기대는 이유이기도 합니다 — 10년째 안 바뀐 API 위에 세우면 낡을 일이 적습니다.

반대로 짧게 보는 것이 셋입니다. **OpenTelemetry Go** 는 trace 와 metric 이 안정화됐지만 log 는 아직 움직입니다. **Istio Ambient** 는 ztunnel/waypoint 구성이 계속 바뀌고 있어 5국면의 세부는 그때 다시 확인해야 합니다. **EndpointSlice** 는 v1 이 됐지만 토폴로지 힌트 필드는 아직 변합니다.

셋 다 코어가 아니라 어댑터 자리에 있어서, 바뀌어도 `types.Result` 는 그대로입니다. 그게 경계를 그은 이유입니다.



## 손으로 확인하는 실습

> 각 국면이 끝났다는 것을 무엇으로 아는가. 문서가 아니라 명령으로 적습니다.

| 국면 | 확인 명령 | 무엇이 보이면 통과인가 |
|---|---|---|
| 1 | `netpath http://127.0.0.1:9` | `tcp_refused`, 이후 단계 "실행되지 않음" |
| 1 | `netpath --timeout 3s http://10.255.255.1:8080` | `tcp_timeout` — **`http_timeout` 이 아님** |
| 1 | `netpath --count 2 http://example.com` | 두 번 다 3단계가 측정됨 |
| 1.5 | `netpath https://expired.badssl.com` | `tls_cert_expired` — 앞 두 단계는 성공 |
| 2 | Grafana 에서 느린 요청 하나 클릭 | metric → trace → log 3단 점프 |
| 3 | `kubectl apply -k deploy/` | 노드별로 같은 대상의 성공률이 갈림 |
| 4 | `make scenario-3` | NetworkPolicy 를 걸면 `tcp_timeout`, 풀면 복구 |
| 5 | sidecar 주입 전후 비교 | 같은 장애가 두 창에서 다르게 보임 |

1국면의 두 번째 줄이 이 프로젝트에서 가장 값진 한 줄입니다. dial 이 타임아웃되면 `ConnectDone` 훅이 발화하지 않아 에러가 HTTP 단계로 흘러갑니다. 그대로 두면 "애플리케이션이 느리다"고 보고하는데 실제로는 패킷이 도착조차 못 한 것입니다.



## 측정 모델 · 1국면

> 여기서 만든 계약 위에 나머지 넷이 전부 올라갑니다. 여기가 흔들리면 뒤가 다 흔들립니다.

### 단계 분해와 오류 분류  `필수`

요청 하나를 DNS·TCP·HTTP 셋으로 갈라 재고, 실패를 **값으로** 분류합니다. TLS 는 1.5국면이 맡습니다. 메시지 문자열은 어느 패키지의 계약도 아니라서 Go 버전이 바뀌면 조용히 깨집니다. `errors.Is`·`errors.As` 만 씁니다.

가장 중요한 결정은 `tcp_refused` 와 `tcp_timeout` 을 절대 합치지 않는 것입니다. 전자는 호스트가 RST 로 답한 것이고 후자는 아무 답이 없는 것인데, Kubernetes 에서 전자는 "앱이 포트를 안 열었다", 후자는 "NetworkPolicy 가 DROP" 입니다. 뭉치면 진단이 반대를 가리킵니다.

| 개념 | 무엇을 알게 되는가 |
|---|---|
| `httptrace` 훅 | 표준 클라이언트 안에서 단계 경계가 어디인가 |
| 실행되지 않은 단계 | "0ms 성공"과 "안 돌았음"은 다른 사실이다 |
| Transport 커넥션 재사용 | 재사용되면 훅이 아예 안 불린다 |
| 잔여 타임아웃 합성 | 단계 예산이 전체 데드라인을 넘으면 안 되는 이유 |
| 에러를 값으로 분류 | 메시지가 계약이 아닌 이유 |

| 확장 여지 | 무엇이 열리는가 |
|---|---|
| worker pool 다중 대상 | 대상 수십 개를 한 번에. `errgroup` 쓸 자리 |
| ICMP·gRPC·QUIC probe | HTTP 밖의 경로. 5국면 이후 |

### 출력 계약  `필수`

`types.Result` 하나가 유일한 산출물이고, 터미널·JSON·OpenTelemetry 가 전부 이것만 읽습니다. 스키마는 [`result-schema.md`](result-schema.md) 가 맡습니다.

**프로버는 재시도하지 않습니다.** 재시도하면 "1회 시도의 진실" 이 흐려집니다. 재시도는 5국면에서 Istio 가 하는 것을 *관측할 대상*이지 프로버의 기능이 아닙니다.



## TLS 계층 · 1.5국면

> 1국면이 평문 경로를 다 재고 난 뒤에 얹습니다. 소수점을 단 이유는 **뒤 국면 어느 것도 이 국면을 요구하지 않기** 때문입니다.

### 왜 떼어 두는가

TLS 는 앞 세 단계와 성격이 다릅니다. DNS·TCP·HTTP 는 **상대가 준 답을 해석**하는 일입니다 — RST 가 왔는지, RCODE 가 무엇인지, 상태 코드가 몇 번인지. 반면 TLS 는 **우리가 직접 검증**하는 일입니다. 인증서 체인을 따라 올라가고, 이름을 대조하고, 유효기간을 계산하는 것이 전부 클라이언트 쪽에서 일어납니다.

그래서 다루는 지식이 갈립니다. 앞 셋은 소켓과 errno 의 세계이고, TLS 는 x509 와 신뢰 모델의 세계입니다. 한 국면에 묶으면 한 번에 배울 것이 두 배가 되는데, **2국면(OpenTelemetry)도 3국면(클러스터)도 TLS 없이 성립**합니다. 그래서 갈라 두고 필요할 때 얹습니다.

### TLS 단계 추가  `필수`

1국면이 만든 자리에 단계 하나와 오류 분류 다섯을 더합니다. 계약은 추가만 하므로 2국면 exporter 가 깨지지 않습니다.

| 더할 것 | 어디에 |
|---|---|
| `tls_cert_invalid`·`tls_cert_expired`·`tls_hostname_match`·`tls_handshake`·`tls_timeout` | `types/error.go` |
| `StageTLS`, `TLSInfo`(version·alpn·server_name·cert_chain_length) | `types/result.go` |
| `TLSHandshakeStart`/`TLSHandshakeDone` 훅 | `probe/trace.go` |
| x509 에러 분류 | `probe/classify.go` |
| 함수형 옵션(`--insecure`, `--http1.1`) | `utils/http.go` |

마지막 줄이 딸려 옵니다. 1국면은 조정할 것이 없어 `NewTransport()` 가 인자를 받지 않는데, TLS 가 들어오면 검증 우회와 프로토콜 선택이라는 **정당한 선택지**가 생겨 함수형 옵션이 값을 갖습니다.

| 개념 | 무엇을 알게 되는가 |
|---|---|
| x509 검증 체인 | 브라우저는 되는데 Go 는 실패하는 구성이 왜 생기는가 (중간 인증서 누락) |
| 값 receiver 에러 타입 | `errors.As` 에 넘기는 타입이 정확해야 하는 이유 |
| ALPN | HTTP/2 협상이 TLS handshake 안에서 일어난다 |
| 애플리케이션 TLS 와 메시 mTLS | 5국면에서 둘을 합치면 안 되는 이유 |

| 확장 여지 | 무엇이 열리는가 |
|---|---|
| `--insecure` 대조 프로브 | 실패 원인이 인증서 체인인지 경로인지 가름 |
| 인증서 만료일·SAN 검사 | "3일 뒤 만료" 를 장애 전에 잡음 |
| `--http1.1` 대조 | HTTP/2 협상이 단계 경계에 미치는 영향 |
| 클라이언트 인증서 | Istio STRICT mTLS 환경. 5국면과 이어짐 |



## 관측 신호 · 2국면

> 아직 클러스터는 없습니다. docker-compose 로 LGTM 을 띄우고 한 대에서 신호를 흘려 봅니다.

### OpenTelemetry 어댑터  `필수`

1국면의 `Result` 를 trace·metric·log 셋으로 바꿉니다. 1 probe = 1 trace 이고 단계가 각각 child span 이 됩니다. 오류 분류는 `netpath.error_kind` attribute 로 올라가는데, 1국면에서 값으로 갈라 뒀기 때문에 대시보드에서 그대로 나눠 셀 수 있습니다.

latency 는 반드시 histogram 입니다. gauge 로 두면 p95 를 못 냅니다.

| 개념 | 무엇을 알게 되는가 |
|---|---|
| span 계층 | 부모-자식으로 단계 포함 관계를 표현하기 |
| histogram vs gauge | 분포를 재는 것과 순간을 재는 것의 차이 |
| Collector 경유 | 앱이 백엔드를 모르게 하면 무엇이 쉬워지는가 |
| trace_id 로그 상관 | 로그에서 trace 로 건너뛰는 최소 조건 |

| 확장 여지 | 무엇이 열리는가 |
|---|---|
| exemplar | 느린 p99 를 클릭하면 그 trace 가 열림 |
| Alertmanager 규칙 | 성공률이 꺾이면 알림. 4국면 이후가 자연스러움 |
| 결과 장기 보관 | "지난주 대비" 비교. Prometheus 보존기간 설정 |



## 클러스터 환경 · 3국면

> 여기서 처음 Kubernetes 가 나옵니다. 핵심은 **같은 목적지를 여러 위치에서 재는 것**입니다.

### 다중 관측 지점  `필수`

DaemonSet 으로 노드마다 프로브를 하나씩 둡니다. 같은 대상에 대해 node-a 는 성공하고 node-b 는 실패하는 그림이 나오면, 그것만으로 "앱 문제가 아니라 경로 문제" 가 증명됩니다. 한 지점에서 재는 도구로는 못 하는 말입니다.

RBAC 는 `get`/`list`/`watch` 만 요구합니다. 쓰기 verb 가 0개라는 사실이 이 도구를 클러스터에 넣기 쉽게 만듭니다.

| 개념 | 무엇을 알게 되는가 |
|---|---|
| DaemonSet | node-local 기능을 배치하는 정석 |
| Downward API | Pod 가 자기 노드·네임스페이스를 아는 법 |
| EndpointSlice | Service 뒤에 실제로 무엇이 있는가 |
| 최소 권한 RBAC | 읽기 전용이 구조로 보장된다는 뜻 |

| 확장 여지 | 무엇이 열리는가 |
|---|---|
| `hostNetwork` 대조 | CNI 가 개입하는 지점이 드러남 |
| ClusterIP vs Pod IP 직접 | kube-proxy 가 개입하는지 가름 |
| 네임스페이스·라벨 필터 | 대형 클러스터에서 관측 범위 좁히기 |
| ConfigMap 으로 대상 관리 | Operator/CRD 없이도 충분한 자리 |
| Pod 로그 프록시 | 실패한 대상의 로그를 같은 화면에 |



## 장애 카탈로그 · 4국면

> 여기가 이 프로젝트의 심장입니다. 코드보다 이 문서들이 더 강합니다.

### 재현 가능한 장애 여섯  `필수`

각 시나리오를 같은 포맷으로 적습니다: **가설 → 주입 → 예상 신호 → 실제 신호 → 증거 → 복구**.

| 시나리오 | 주입 | 기대 신호 |
|---|---|---|
| CoreDNS 장애 | CoreDNS scale 0 | `dns_timeout` |
| 포트 미수신 | 안 듣는 컨테이너 | `tcp_refused` — 즉시 |
| NetworkPolicy DROP | deny-all 적용 | `tcp_timeout` — 전체 소진 |
| 인증서 불일치 | 잘못된 호스트명 | `tls_hostname_match` — 1.5국면 선행 |
| 지연·손실 | `tc netem` | latency 분포 변화 |
| 느린 응답·5xx | 의도적 지연 | `http_status`, 앞 3단계는 성공 |

2번과 3번을 **신호만 보고 구분할 수 있으면 이 프로젝트는 성공**입니다. 나머지는 그 위의 응용입니다.

### 진단 계층  `필수`

신호 조합을 추정 원인으로 옮기는 규칙을 순수 함수로 만듭니다. "TCP timeout + 해당 네임스페이스에 NetworkPolicy 존재" → "정책 DROP 가능성". 추정만 내놓지 않고 **왜 그렇게 봤는지 근거를 함께** 출력합니다.

규칙 기반으로 갑니다. LLM 을 붙이면 근거가 흐려지고, 이 도구의 값은 근거에 있습니다.

| 확장 여지 | 무엇이 열리는가 |
|---|---|
| MTU 불일치 시나리오 | 대용량 응답만 hang 하는 유형 |
| Endpoint 0개 Service | scale 0 상태를 K8s 근거와 함께 |
| kind E2E 테스트 | 주입 → 기대 신호를 CI 에서 검증 |
| 상태 전이 타임라인 | "5분 전에 무슨 일이" 에 답하는 최소 시간축 |
| Grafana 링크 생성 | 대상별 대시보드로 한 번에 건너뛰기 |



## 프록시 비교 · 5국면

> 확장입니다. 4국면에서 멈춰도 완결이고, 여기는 그 위에 얹는 층입니다.

### 세 창으로 같은 장애 보기  `확장`

맨눈으로 네트워크를 이해한 **뒤에** 프록시가 보여주는 세계를 겹칩니다. 순서를 뒤집으면 Istio 사용법만 남습니다.

| 관측 계층 | 보이는 것 |
|---|---|
| NetPath Probe | DNS, TCP, 애플리케이션 TLS, TTFB |
| Istio | 서비스 간 요청·지연·재시도, mTLS, 정책 |
| Hubble | 패킷 흐름, DROP, 실제 노드 경로 |

**"Istio 에 기록이 없다" 도 신호입니다.** DNS 실패는 프록시에 닿기 전이라 아무 기록이 없고, upstream 실패는 access log 에 남습니다. 이 차이가 실패 지점을 가릅니다.

애플리케이션 TLS 와 메시 mTLS 를 절대 하나로 합치지 않습니다. 앱은 평문 HTTP 를 쓰는데 프록시 사이는 mTLS 인 구성이 흔해서, 뭉치면 "TLS 성공" 이 무엇을 뜻하는지 알 수 없게 됩니다.

| 확장 여지 | 무엇이 열리는가 |
|---|---|
| AuthorizationPolicy 실험 | 403 이 어느 층에서 나오는가 |
| retry·circuit breaking | 재시도가 최종 지연에 미치는 영향 |
| Ambient mode 비교 | ztunnel(L4) 과 waypoint(L7) 의 관측 차이 |
| Hubble flow 대조 | 자기 측정과 eBPF 관측을 교차 검증 |
| Kiali 토폴로지 | 서비스 그래프 위에 프로브 결과 얹기 |

## 경계

> 비슷한 것을 다루는 프로젝트가 옆에 있어서 무엇을 어디서 하는지 갈라 둡니다.

`~/study/podwire` 와 이 프로젝트는 같은 층을 다루지만 방향이 반대입니다. **podwire 는 데이터 플레인을 만들고**(CNI·Service·Policy 를 직접 구현), **NetPath Lab 은 경로를 잽니다.** podwire 로 만든 클러스터에 NetPath Lab 을 띄우면 자기가 만든 데이터 플레인을 자기가 만든 프로브로 검증하게 되는데, 4국면의 장애 주입과 podwire 의 층 on/off 가 바로 겹치는 자리입니다.

책을 고르고 학습 순서를 정하는 일은 이 문서가 맡지 않습니다. Go 언어 자체는 [`go-roadmap.md`](~/runners-high/write/roadmap/go-roadmap.md) 가, 패킷 경로와 Kubernetes 네트워크는 [`network-roadmap.md`](~/runners-high/write/roadmap/network-roadmap.md) 가 맡습니다. 이 문서는 **그 지식을 이 프로젝트의 어느 자리에 쓰는가**만 적습니다.

go-roadmap 기준으로 이 프로젝트가 걸치는 곳은 넷입니다. 2단계(에러를 값으로), 4단계(`context`), 7단계(고루틴·채널·`select`), 11단계(소켓과 네트워크 프로그래밍). 1국면을 손으로 짜 보면 이 넷이 한꺼번에 걸립니다.
