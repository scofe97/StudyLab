# 코드리뷰 실습 과제
---

## 왜 이 과제들인가

> 리뷰는 "읽고 의견을 말하는 일"이 아니라 **주장을 실행으로 확정하는 일**입니다. 이 과제들은 전부 코드를 읽는 데서 끝나지 않고, 실행해서 답을 받아내는 형태로 만들었습니다.

2026-09-16 검증에서 집중 지점 넷(분기 순서·동시성·경계값·경계 강제)이 전부 무결로 나왔습니다. 결함이 없다는 사실 자체보다, **어떻게 그걸 확정했는가**가 배울 거리입니다. 아래 과제는 그 확정 절차를 직접 밟아 보는 것이고, 마지막 두 개는 실제로 남아 있는 빈틈을 메우는 일입니다.

각 과제에 **예상 시간**과 **막혔을 때 볼 곳**을 달았습니다. 순서대로 할 필요는 없지만, 1번은 나머지의 전제라 먼저 하시길 권합니다.

### 진행 방식 — 예측이 먼저입니다

이 문서는 혼자 읽는 워크북이 아니라 **대화형 실습**으로 씁니다. `learning-method` 의 Phase 3 계약을 따릅니다.

```
예측 → 실행 → 관찰 → 차이 해석
```

**명령을 보기 전에 결과를 먼저 예측해 적습니다.** 예측 없이 실행하면 화면에 뜬 것을 그냥 받아들이게 되고, 그건 관찰이지 학습이 아닙니다. 예측이 빗나갔을 때 그 간극이 배울 거리입니다 — 실제로 이 저장소를 검증하던 AI 도 과제 5 에서 "grep 기반이라 뚫릴 것"이라고 예측했다가 틀렸고, 그 대목이 가장 많은 것을 알려줬습니다.

각 과제는 세 블록으로 되어 있습니다.

| 블록 | 하는 일 |
|---|---|
| **예측** | 명령을 보기 전에 답을 적는다. 틀려도 됩니다 — 틀리는 게 재료입니다 |
| **실행** | 터미널에서 직접 친다. 대신 쳐 주지 않습니다 |
| **해석** | 예측과 결과가 갈렸다면 왜 갈렸는지 말한다 |

한 번에 **과제 하나씩** 갑니다. 해석 블록까지 마쳐야 다음 과제로 넘어갑니다.



## 과제 1 — 커버리지가 가장 낮은 곳을 찾아 이유를 말하기 (20분)

> 숫자를 보는 게 목적이 아니라, **낮은 게 문제인 곳과 문제가 아닌 곳을 가르는 눈**을 만드는 게 목적입니다.

### 예측 — 숫자를 보기 전에

이 저장소의 파일 목록은 이미 봤습니다. 테스트는 `types`·`utils`·`probe` 세 패키지에 있고 `cmd/netpath` 에는 없습니다.

세 가지를 먼저 적습니다.

1. 커버리지가 **가장 낮을** 파일 또는 함수는 어디일 것 같나요? 이유는요?
2. `probe/classify.go` 는 이 도구의 분류 핵심입니다. 몇 % 쯤 나올 것 같나요? (범위로 답해도 됩니다 — "90% 이상", "절반쯤")
3. 커버리지가 **낮아도 괜찮은** 함수가 이 저장소에 있을까요? 있다면 어떤 성격의 함수일까요?

### 실행

```bash
cd ~/study/netpath-lab
make cover
go tool cover -func=coverage.out | grep -v '100.0%$'
```

어느 **줄**이 안 밟혔는지는 브라우저로 보면 빠릅니다.

```bash
go tool cover -html=coverage.out
```

### 해석

- 예측 1·2 가 맞았나요? 빗나갔다면 무엇을 잘못 가정했나요?
- 0% 인 함수들을 **두 부류로 갈라** 보세요 — "문제인 것"과 "문제가 아닌 것". 가르는 기준이 무엇인가요?
- 가장 낮은 분류 함수에 대해: 테스트가 **안 짜여서** 낮은 건가요, 그 경로에 **도달하기 어려워서** 낮은 건가요? 둘은 다른 문제입니다.

**막혔을 때** — `probe/classify.go` 에서 `otherFor` 를 부르는 자리가 둘 있습니다. 각각 어떤 에러가 와야 거기 도달하는지 위쪽 분기를 거꾸로 읽어 보세요.



## 과제 2 — 분기 순서가 왜 저 순서인지 실행으로 확인하기 (30분)

> 리뷰에서 "이 순서 틀린 것 같은데요"는 추측입니다. **순서를 바꿔 보고 무엇이 깨지는지 보는 것**이 확정입니다.

`classify.go` 에서 `errors.Is(err, syscall.ECONNREFUSED)` 블록(45~48줄 근처)을 `net.Error` 검사(62~65줄) **뒤로** 옮겨 보세요. 그리고 돌립니다.

```bash
go test ./probe/ -v 2>&1 | head -30
```

답해 보세요.

1. 테스트가 깨지나요? 깨진다면 어느 케이스가 무엇을 기대했는데 무엇을 받았나요?
2. 안 깨진다면 — 그게 더 무서운 결과입니다. **왜 안 깨졌을까요?** 테스트가 그 조합을 안 보고 있다는 뜻일까요, 아니면 순서를 바꿔도 결과가 같은 걸까요?
3. 실제 `ECONNREFUSED` 에러는 `net.Error` 인터페이스를 만족할까요? 확인하는 코드를 세 줄로 써 보세요.

확인을 마쳤으면 반드시 **원래대로 되돌리고** `make check` 로 복구를 확정합니다.

**막혔을 때** — 3번은 `errors.As(err, &netErr)` 로 꺼낸 뒤 `netErr.Timeout()` 을 찍어 보면 됩니다. 실제 dial 에러 체인을 만들려면 `&net.OpError{Op:"dial", Err: os.NewSyscallError("connect", syscall.ECONNREFUSED)}` 형태로 조립하세요.



## 과제 3 — 훅이 안 불리는 상황을 직접 만들기 (40분)

> `trace.go` 의 설계 판단 — duration 이 아니라 시각 둘을 저장한 것 — 은 "훅이 안 불리는 경우가 있다"는 사실 위에 서 있습니다. 그 사실을 남의 주석이 아니라 **내 화면에서** 보는 과제입니다.

`ConnectStart` 는 불리는데 `ConnectDone` 은 안 불리는 상황을 만듭니다. 라우팅되지 않는 주소로 짧은 타임아웃을 걸면 됩니다.

```bash
make build
./bin/netpath --timeout 2s http://10.255.255.1:8080
```

답해 보세요.

1. TCP 단계의 시간 자리에 무엇이 찍혔나요? `0.0ms` 인가요, `-` 인가요? 그 차이가 왜 중요한가요?
2. `--json` 으로 같은 걸 돌리면 `stages[1].status` 와 `duration_ns` 가 각각 무엇인가요?
3. `trace.go` 의 `hung()` 이 이 상황에서 `true` 를 돌려주는 이유를 한 문장으로 적어 보세요.
4. 만약 `stageSpan` 이 `start`/`end` 대신 `duration time.Duration` 하나만 들고 있었다면, 이 출력이 어떻게 달라졌을까요?

**막혔을 때** — 2분을 기다려도 안 끝나면 커널 타임아웃(`tcp_syn_retries`) 쪽으로 간 것입니다. `--timeout` 을 꼭 주세요. 4번은 `docs/concepts/network/network-signal-to-error-value.md` 의 "두 종류의 타임아웃" 절과 이어집니다.



## 과제 4 — `otherFor` 에 테스트를 붙이기 (40분) · 실제 기여

> 여기부터는 연습이 아니라 **실제로 비어 있는 자리를 메우는 일**입니다. 커버리지 0% 함수에 테스트를 붙입니다.

`otherFor` 로 가는 경로는 둘입니다.

| 경로 | 조건 | 기대 결과 |
|---|---|---|
| `classify.go:48` | `ECONNRESET` — 연결이 세워진 뒤 끊김 | 단계별 `_other` (HTTP 면 `http_protocol`) |
| `classify.go:63` | 위 어느 분기에도 안 걸리는 미지의 에러 | 단계별 `_other` |

`probe/classify_test.go` 의 기존 테스트 스타일을 그대로 따라 케이스를 더하세요. 테스트 본문에는 `// Given`, `// When`, `// Then` 세 구획 주석을 답니다(전역 규칙 `~/claude/.claude/rules/testing-style.md`).

붙이고 나서 확인합니다.

```bash
go test ./probe/ -coverprofile=/tmp/c.out
go tool cover -func=/tmp/c.out | grep otherFor   # 0% 가 아니어야 한다
make check
```

답해 보세요.

1. `otherFor` 가 0% 였다는 사실이 **결함**인가요, 아니면 **아직 안 한 일**인가요? 둘의 차이는 무엇인가요?
2. 세 단계(`dns`·`tcp`·`http`) 전부에 케이스를 만들어야 할까요, 하나면 충분할까요? 판단 근거는요?

**막혔을 때** — `ECONNRESET` 체인 조립은 과제 2의 힌트와 같은 형태입니다. `syscall.ECONNRESET` 으로 바꾸면 됩니다.



## 과제 5 — `make lint` 의 경계 강제가 진짜인지 뚫어 보기 (30분) · 파괴적

> `AGENTS.md` 가 두 번 주장합니다 — "`make lint` 가 강제한다". 주장을 믿지 말고 **깨뜨려 보는** 과제입니다. 이 프로젝트의 가장 중요한 설계 규칙이 실제로 지켜지는지 보는 일입니다.

이 과제는 코드와 `go.mod` 를 함께 더럽힙니다. **사본에서 하세요** — 되돌리기가 확실합니다.

```bash
cp -r ~/study/netpath-lab /tmp/lintcheck && cd /tmp/lintcheck
```

`probe/probe.go` 의 import 블록에 `"go.opentelemetry.io/otel"` 을 더하고 함수 안에서 한 번 씁니다(`_ = otel.GetTracerProvider()`). 그리고 돌립니다.

```bash
gofmt -w .     # 포맷이 틀어지면 lint 가 경계 검사까지 못 간다
go mod tidy    # 의존이 실제로 들어온다
make lint      # 여기서 막혀야 한다
```

> `gofmt -w .` 를 빠뜨리면 `make lint` 가 **gofmt 단계에서 먼저 죽습니다.** 그러면 경계 검사가 돌지 않았는데 "막혔다"고 오독하게 됩니다 — 무엇이 막았는지 출력을 읽으세요.

답해 보세요.

1. `make lint` 가 실제로 막았나요? 출력이 무엇이었나요?
2. `Makefile:39` 의 검사는 `go list -deps` 를 씁니다. 이게 `grep "otel" *.go` 같은 **텍스트 검색**보다 나은 이유가 무엇인가요? 텍스트 검색이었다면 어떤 방식으로 우회될 수 있었을까요?
3. **간접 의존**은 어떨까요? `probe/` 가 직접 import 하지 않고, `utils/` 가 OTel 을 import 하고 `probe/` 가 `utils/` 를 쓰면 — 이 검사가 잡을까요? 실제로 해 보세요.

끝나면 사본을 지우고, **원본이 안 더러워졌는지** 확인합니다.

```bash
cd /tmp && rm -rf lintcheck
cd ~/study/netpath-lab
grep -rc 'opentelemetry' probe/ utils/ | grep -v ':0'   # 아무것도 안 나와야 한다
cat go.mod                                              # require 블록이 없어야 한다
make check
```

> 이 저장소는 아직 `git init` 이 안 돼 있어 `git checkout` 으로 되돌릴 수 없습니다. 사본에서 하라고 한 이유가 이것입니다. 원본에서 직접 하고 싶다면 먼저 `git init && git add -A && git commit -m "before exercise"` 를 해 두세요.

**막혔을 때** — 3번이 이 과제의 핵심입니다. `go list -deps` 는 **전이 의존까지 전부** 펼치므로 간접 경로도 잡힙니다. 직접 확인해 보고, 잡힌다면 그게 왜 중요한 성질인지 한 문장으로 적어 보세요.



## 과제 6 — 알려진 한계를 직접 재현하기 (20분)

> `README.md` 의 "알려진 한계"에 적힌 것이 **진짜 그렇게 동작하는지** 확인합니다. 문서의 주장도 검증 대상입니다.

README 는 이렇게 적었습니다 — `--count 3` 에서 한 번만 실패하면 종료 코드가 0 이다.

```bash
./bin/netpath --count 3 http://example.com; echo "exit=$?"
```

양 끝은 직접 볼 수 있습니다.

```bash
./bin/netpath --count 3 http://example.com  >/dev/null 2>&1; echo "전부 성공 exit=$?"
./bin/netpath --count 3 http://127.0.0.1:9  >/dev/null 2>&1; echo "전부 실패 exit=$?"
```

> 종료 코드를 잴 때 `| head` 같은 파이프를 붙이지 마세요. `$?` 가 **파이프 맨 끝 명령의 코드**를 받아서 엉뚱한 값을 읽게 됩니다. 실제로 이 검증 중에 그 함정을 밟아 DNS 실패를 0 으로 오독한 적이 있습니다.

가운데(3회 중 1회만 실패)는 간헐적 실패라 만들기 어려우니, **규칙 자체**를 코드에서 확인하고 답해 보세요 (`cmd/netpath/main.go:88` 근처).

1. `succeeded == 0` 일 때만 1 을 돌려주는 규칙이 `ping` 과 같다는 서술이 맞나요? macOS `man ping` 에는 EXIT STATUS 절이 없으니 리눅스 쪽 문서나 `ping -c 3` 을 직접 돌려 확인하세요.
2. 이 규칙이 **사람에게는 맞고 스크립트에게는 틀린** 이유를 한 문장으로 적어 보세요.
3. `--fail-on-any` 를 더한다면 `run()` 의 어느 줄을 어떻게 고쳐야 할까요? 코드를 쓰지 말고 **고칠 자리와 조건만** 적어 보세요.

**막혔을 때** — 3번은 구현 과제가 아니라 설계 판단 과제입니다. 플래그 하나와 `if` 조건 하나로 끝나는지, 아니면 더 손댈 곳이 있는지만 판단하면 됩니다.
