## 묶음 A (2026-09-20)

1. **핸드셰이크 도식의 묶음 표시** — `04-01.tls-handshake.svg` 가 메시지마다 화살표를 따로 그려 각각 따로 도착하는 것처럼 읽힙니다.
   같은 차례에 몰아 보내는 메시지(ServerHello·Certificate·ServerKeyExchange·ServerHelloDone 등)를 한 묶음으로 표시해
   "왕복은 두 번, 덩어리는 넷"이 보이게 고칩니다. 근거는 실습 캡처 `pcap/a1-handshake.pcap` 의 프레임 7(레코드 넷이 한 세그먼트).
2. **인증서·키 교환 상세 흐름 도식** — 클라이언트·서버 두 기둥 사이에 무엇이 실려 가는지(인증서 안의 공개키와 CA 서명,
   서버 DH 공개 값과 서버 서명, 클라이언트 DH 공개 값)를 자세히 그린 도식을 04-01 §4 에 추가합니다.
3. **두 서명의 구분** — 인증서 안의 CA 서명(공개키의 주인이 누구인가, 발급 때 한 번, 복사 가능)과
   ServerKeyExchange 의 서버 서명(그 개인키를 지금 쥐고 있는가, 핸드셰이크마다 새로, 재사용 불가)을 표로 가릅니다.
   학습자가 가장 오래 머문 자리입니다. "인증서 안에는 소유 증명이 없다"를 본문 문장으로 씁니다.
4. **ServerKeyExchange 에 서명이 필요한 이유** — CA 서명은 RSA 공개키만 보증하고 DH 공개 값은 연결마다 새로 뽑혀 인증서에 없습니다.
   서명이 없으면 중간자가 인증서는 통과시키고 DH 값만 바꿔치기할 수 있다는 시나리오로 적습니다.
5. **표에 없는 `NewSessionTicket`(종류 4)** — 실제 캡처에 나오는데 04-01 §2 의 열 가지 표에 없습니다. 한 줄 설명을 붙입니다.
   `Finished` 가 핸드셰이크 전체 해시의 검산이라는 설명도 §5 에서 더 분명히 합니다.
6. **openssl 로 CA 와 서버 인증서를 만드는 과정** — 키 생성 → CSR → CA 서명 세 걸음과 `.crt`·`.key`·`ca.crt` 각 파일의 역할.
   실습 랩의 `make-certs.sh` 가 재료입니다. X.509 라는 이름의 유래(ITU-T X.500 시리즈의 509번 문서)도 한 구절로.
7. **실습 명령의 옵션 풀이** — `s_server` 의 `-cert`·`-key`(읽는 옵션이지 만드는 옵션이 아님)·`-servername`/`-cert2`·`-www`,
   `s_client` 의 `-CAfile`(신뢰할 CA 를 알려 주는 입력)·`-servername`, `openssl x509 -in … -noout -text`.
8. **길어지면 새 문서로 분리** — 위 3·4·6 은 분량이 커질 수 있습니다. 기존 편에 밀어 넣지 말고 인증서와 서명을 다루는 편을
   따로 세워도 된다는 것이 학습자 방침입니다. 4장 실습 편(`04-03.실습 — …`)도 함께 검토합니다.

## 묶음 B (2026-09-20)

9. **데이터 암호화는 대칭 키가 한다** — 학습자는 "서버 → 클라이언트 방향은 클라이언트의 공개키로 암호화할 것"이라 예측했습니다.
   공개키 암호는 핸드셰이크에서 비밀 값을 나르는 데 한 번만 쓰이고, 그 뒤 데이터는 양쪽 방향 모두 같은 대칭 키로 암호화된다는 것,
   이 핸드셰이크에서 클라이언트는 키 쌍조차 없다는 것을 04-02 §1 또는 §2 앞머리에 명시합니다.
10. **cipher suite 이름의 `WITH` 앞뒤 역할 분담** — 04-01 §3 의 네 조각 분해표에 "언제 쓰이는가" 축을 더합니다.
    `WITH` 앞(키 교환·인증)은 핸드셰이크에서 양쪽이 같은 비밀 값을 갖게 되는 방법, 뒤(대칭 암호·해시)는 그 뒤 데이터를 암호화·검사하는 방법.
    정적 RSA 와 ECDHE 는 도착점(같은 비밀 값 → 같은 대칭 키)이 같고 비밀 값이 생기는 경로만 다르다는 비교표도 함께.
11. **장기 키와 세션 키의 구분** — 인증서·개인키(`-cert`·`-key`, 몇 달~1년 고정, 신원과 서명)와 세션 키(연결마다 새로 계산, 데이터 암호화, 끝나면 폐기).
    학습자가 "서버를 띄울 때마다 같은 키 파일을 쓰는데 매번 새 키라는 말과 어긋나지 않나"로 헷갈렸습니다.
12. **키 로그 파일의 구조와 매칭 방식** — 04-02 심화 학습. 한 줄이 `CLIENT_RANDOM <클라이언트 난수> <master secret>` 이고,
    첫 값은 ClientHello 에 평문으로 실린 난수라 "어느 연결의 키인가"를 찾는 색인이라는 것, 그래서 다른 연결의 캡처는 같은 파일로 열리지 않는다는 것.
13. **(확인 필요) RSA 키 등록 경로** — 04-02 §2 는 `Preferences → Protocols → TLS` 에서 RSA 키를 추가한다고 적습니다.
    실습에서 tshark 는 `-o uat:rsa_keys:…` 로 동작했습니다. 현행 4.6 GUI 에서 이 설정이 `Preferences → RSA Keys` 로 옮겨졌는지 공식 문서로 확인해 반영합니다.

## 묶음 C (2026-09-20)

14. **Alert 가 캡처에 찍히는 모습** — 04-01 §6. 레코드 종류 21, 길이 2바이트(수준 1 + 번호 1), 평문. 실패는 ChangeCipherSpec 보다 앞에서 나므로 암호화 전이라는 것.
    성공(`ClientHello → 2,11,12,14`)과 실패(`ClientHello → 21`)를 나란히 놓은 대비를 넣습니다. 학습자는 표에서 21 을 보고도 "에러가 명시적으로 안 보인다"고 했습니다.
15. **OpenSSL 표기와 IANA 표기의 대응** — `TLS_` 와 `WITH` 를 빼고 하이픈으로 잇는 자기 표기, 키 교환이 RSA 면 이름에서 생략(`AES256-SHA256` = `TLS_RSA_WITH_AES_256_CBC_SHA256`).
    `openssl ciphers -stdname` 출력의 `Kx`·`Au`·`Enc`·`Mac` 열 읽기와 `Mac=AEAD` 의 뜻. 04-01 §3 또는 04-02 §3.
16. **서버 지원 목록을 훑는 원리** — 04-02 §3 의 `nmap ssl-enum-ciphers` 설명에 한 문단. 서버는 자기 목록을 말하지 않고 하나만 고르므로,
    묶음을 하나씩만 제안해 붙어 보고 Alert 40 이면 넘어가는 반복이 곧 표준 방법이라는 것. 학습자는 "가능은 하지만 일반적인 방법은 아니다"라고 예측했습니다.
17. **정적 RSA 도 연결마다 새 비밀 값을 만든다** — 학습자 오개념: "키 교환과 인증 칸이 나뉘면 매번 새 대칭 키, 아니면 안 만든다".
    갈리는 곳은 새로 만드느냐가 아니라 그 값이 장기 키로 잠긴 채 선 위를 지나가느냐라는 것을 04-02 §1 전방 비밀성 절에 표로.
    판별은 칸 개수가 아니라 `DHE`·`ECDHE` 의 끝 글자 E(ephemeral) 또는 `Kx=` 열로.
18. **TLS 1.3 실측** — 04-01 심화 학습. 키 없이는 핸드셰이크 종류가 1·2 뿐이고 인증서 이름 검색 0건, SNI 와 고른 묶음은 평문.
    키 로그를 물리면 프레임 7 에서 `2, 8, 11, 15, 20` 이 나타남. 묶음 이름에 키 교환·인증 칸이 없음(`TLS_AES_256_GCM_SHA384`, 0x1302).
    DH 공개 값이 ClientHello·ServerHello 의 확장에 실려 ServerHello 직후부터 암호화가 시작된다는 것.
19. **점검 관점의 결론** — 서버가 ECDHE 묶음을 받더라도 `Kx=RSA` 묶음이 하나라도 열려 있으면 그것만 제안하는 클라이언트와의 연결은 나중에 열릴 수 있다는 것. 04-02 결정 치트시트에 한 줄.
20. **TLS 1.3 에서 평문으로 남는 것의 목록** — 학습자는 "1.3 은 무조건 DH 인데 ECDHE 인지는 모른다"고 했습니다. 키 교환 그룹은 ServerHello 의 `key_share` 확장에 평문으로 실립니다
    (실습 캡처 `c10-tls13.pcap` 프레임 7: 그룹 29 = x25519, `supported_versions` 0x0304). 가려지는 것은 인증 쪽(인증서, 서명 알고리즘의 실제 선택)입니다. 18번과 같은 자리에 표로.
21. **실패 진단은 복호화가 필요 없다** — 출구 게이트에서 학습자는 "접속 실패 원인 좁히기"를 "복호화할 수 있는가"로 답했습니다. 실패는 암호화 경계 앞에서 나므로
    Alert 번호 → ClientHello 의 제안(버전·묶음) → 서버 지원 목록 훑기 순서로 키 없이 좁힌다는 것을 04-02 결정 치트시트 또는 04-01 §6 끝에 순서도로.

## 묶음 C 에서 확인한 사실 (실습 편 재료)

- 서버를 TLS 1.2 + `AES128-SHA` 하나로 못박고: cipher 불일치 → 서버(4433)가 level 2, desc 40. 버전 불일치(`-tls1_1`) → level 2, desc 70.
  클라이언트 출력은 각각 `sslv3 alert handshake failure … alert number 40`, `tlsv1 alert protocol version … alert number 70`. `curl` 은 exit 35.
- OpenSSL 3.0.13 은 기본 보안 수준에서 TLS 1.1 을 내보내지 않아 클라이언트에 `-cipher "DEFAULT:@SECLEVEL=0"` 이 필요.
- 지원 목록 훑기: `openssl ciphers "ALL:@SECLEVEL=0"` 의 140개를 하나씩 제안해 약 2초. 숨겨 둔 서버 설정(묶음 셋, TLS 1.2 만)을 그대로 복원.
- TLS 1.3: ClientHello 512바이트, 제안 목록 맨 앞에 0x1302·0x1303·0x1301. 서버 선택 0x1302. 키 로그 파일 라벨은 `CLIENT_HANDSHAKE_TRAFFIC_SECRET` 등 다섯 종.
- `look-tls.sh` 에 Alert 수준·번호 열 추가.

## 묶음 B 에서 확인한 사실 (실습 편 재료)

- 정적 RSA(`AES128-SHA` = `TLS_RSA_WITH_AES_128_CBC_SHA`, 0x002f)로 붙으면 서버의 핸드셰이크가 `2, 11, 14` — ServerKeyExchange(12) 가 없음.
- ClientKeyExchange 레코드 길이: ECDHE 37바이트(x25519 공개 값 32) 대 정적 RSA 262바이트(2048비트 RSA 로 잠근 비밀 값 256).
- 정적 RSA 캡처: 키 없이 `follow,tls` 는 빈 결과(`Node 0: :0`), 서버 개인키를 물리면 요청(74바이트)과 응답(1989바이트) 양방향이 모두 평문으로 나옴.
- 같은 개인키로 ECDHE 캡처(`a1-handshake.pcap`)는 열리지 않음 — 전방 비밀성.
- `SSLKEYLOGFILE` 로 남긴 키 파일로는 그 연결의 ECDHE 캡처가 열리고, 같은 파일로 다른 연결의 옛 캡처는 열리지 않음.
- 컨테이너의 OpenSSL 3.0.13 은 정적 RSA 묶음을 별도 SECLEVEL 조정 없이 받아 줌. `curl 8.5.0` 은 `SSLKEYLOGFILE` 지원.
- `look-tls.sh` 결함: `column -t` 가 빈 필드를 건너뛰어 열이 밀림 → 빈 칸을 `-` 로 채워 고침.

## 묶음 A 에서 확인한 사실 (실습 편 재료)

- 클라이언트(OpenSSL 3.0.13 `s_client`)의 ClientHello 는 cipher suite 28줄 — ECDHE_ECDSA·ECDHE_RSA·DHE_RSA 세 종 × 암호 일곱 종 21개,
  정적 RSA 6개, SCSV 1개. 전방 비밀성 있는 것이 앞, 정적 RSA 가 맨 뒤.
- 서버는 RSA 인증서라 1순위 `ECDHE_ECDSA`(0xc02c)를 건너뛰고 `0xc030` 을 고름.
- ServerKeyExchange: x25519 공개 값 32바이트(평문) + `rsa_pss_rsae_sha256` 서명 256바이트.
- 프레임 9: 레코드 22·20·22 중 핸드셰이크 종류는 16 하나만 읽힘 — 세 번째가 암호화된 Finished. 암호화 경계.
- SNI 만 바꿔 두 번 접속: cipher suite 동일, SNI·인증서 주체 다름, ServerHello 길이 65 대 69(서버가 SNI 반영을 4바이트로 알림).
- 학습자 오개념: "서버가 1순위를 고른다", "SNI 가 바뀌면 인증 칸이 바뀐다", "인증서는 암호화돼 못 본다".

## 04-02 「인증서와 두 서명」 Phase 1(예측→채점, 2026-09-20)에서 나온 보강 후보

- §1 에 "서버가 자기 인증서에 스스로 서명하면 왜 안 되는가"가 없음. 학습자는 대조에서 노트 문장을 본 뒤에도 `a.test.crt` 의 서명을 서버 개인키로 찍었다고 답했고, "그러면 가짜 서버도 이름만 a.test 로 적어 똑같이 만든다"는 되묻기에서야 CA 의 필요를 스스로 냄. 이 반례를 §1 첫 절에 문제로 세울 후보.
- §1 에 인증서와 서버 서명의 *종류* 차이가 없음 — 인증서는 `이름 + 공개키 + CA 서명`을 담은 문서, 서버 서명은 값 하나에 찍은 도장. 학습자가 서버 서명을 끝까지 "서버 인증서"라 부름. 이 구분을 준 뒤 "미리 못 만든다·서버 개인키로 찍는다"가 바로 나옴.
- 낱말 겹침: 학습자가 DH 공개값을 "퍼블릭 키"라 부름. 인증서의 공개키(장기, 안 바뀜)와 DH 공개값(연결마다 새로)을 나란히 놓는 한 줄 후보 — §4 장기 키·세션 키 표 곁.
- §3 에 CA 가 요청자를 확인하는 절차가 없음(학습자 질문: "새 서버인지 해킹 서버인지 어떻게 가리나"). 도메인 검증(ACME, RFC 8555 의 HTTP-01·DNS-01)과 실습의 사설 CA 는 확인 없이 서명한다는 대비. 세션에서는 AI 일반 지식으로 답했으므로 RFC 8555 원문 대조 후 반영.
- §1·§2 에 서버 서명이 덮는 범위가 "이번 연결에서만 쓰는 값"으로만 적힘. 학습자 의문: "평문으로 지나가는 그 순간 가져다 바로 보내면 인증되지 않나". 서명 대상에 양쪽 random 이 들어가는지 RFC 5246 §7.4.3·RFC 8422 §5.4 원문 대조 후 반영(미확인).
- §3 파일 표: 학습자가 ".crt 나 .key 는 공개키가 아닐 텐데 공개키는 어떤 형식으로 오나"를 물음. 표에 "공개키와 이름에 CA 서명이 붙은 문서"는 있으나 *공개키가 .crt 안에 실려 간다*·*.key 에서 공개키를 계산할 수 있다*가 문장으로 없음.
- 학습자 오개념(이 편): "CA 서명 검증이 끝나면 비밀값이 이미 공유된 상태", "DH 공개값은 인증서 안에 있어야 위조를 가린다", "클라이언트는 미리 가진 파일이 없다"(→ OS·브라우저 CA 목록으로 자가 정정), "사설 CA 면 ca.crt 를 서버가 보내 준다", "CSR 에 발급자 서명이 담긴다"(이름은 빠뜨림).

## 4장 Phase 4 자답(2026-09-20)에서 나온 보강 후보

- 데이터에 대칭 키를 쓰는 *이유*가 네 편 어디에도 없음(`느리|성능|연산 비용` 전수 조회 — 04-01·04-02·04-04 0건, 04-03 은 곡선 파라미터 길이 문장 1건뿐). 학습자는 "성능 때문에 일부러 대칭 키로 바꾼다"로 알고 있었고, 세션에서 AI 가 "클라이언트에 키 쌍이 없어서"를 앞세우는 바람에 "mTLS 면 대칭 키가 필요 없다"로 잘못 넘어갔다가 고침. 04-02 §4 장기 키·세션 키 표 곁에 넣을 후보 — 비대칭 연산은 느리고 한 번에 다룰 크기가 작다는 것, **mTLS 에서도 클라이언트 키 쌍은 서명(CertificateVerify)에만 쓰이고 데이터는 대칭 세션 키가 맡는다**는 것. 근거는 1차 자료 대조 후(미확인 — 세션에서는 AI 일반 지식).
- 비대칭 키의 방향 표가 없음 — 숨기기는 공개키로 잠그고 개인키로 열며, 서명은 개인키로 찍고 공개키로 확인. 학습자가 Phase 4 문항 4 에서 "방향별로 개인키로 잠근다"·"서버 개인키로 비밀값을 잠근다"·"이후에는 서버 공개키로 잠근다"로 답함(묶음 B 오개념의 재발). "개인키로 처리한 것은 누구나 열 수 있어 아무것도 숨기지 못한다"를 학습자가 스스로 짚었으므로 그 추론을 문제로 세울 수 있음.
- 세션 키가 선을 지나가지 않는다는 것은 04-02 §4 표에 있으나, *선을 지나가는 것은 공개키로 잠근 비밀값 하나이고 공개키 암호화는 그 한 번뿐*이라는 문장이 없음. 학습자 질문: "대칭 키는 뭘로 암호화돼서 가나", "매번 보낼 때마다 공개키로 암호화하나".
- 04-01 §4 「Certificate — 체인째 옵니다」: 학습자가 "중간 CA 가 뭐지"를 물음. `서버 인증서 ← 중간 CA ← 루트 CA` 를 한 줄로 푼 문장이 소절에 있는지 확인 필요(세션에서는 소절 일부만 읽음 — 도식 certificate-chain 은 있음).
- 학습자가 Certificate 메시지로 오는 것을 "CA 인증서"라 부름 — 뜻한 것은 CA 서명이 붙은 서버 인증서. "CA 서명이 붙어 있어도 주인이 서버라 서버 인증서, CA 인증서는 ca.crt 쪽"이라는 이름 구분 한 줄 후보(04-02 §3 파일 표 곁).
