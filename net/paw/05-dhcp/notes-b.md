# 묶음 B 실측 메모 (학습자 실행) — 05-03 실습 편에 채울 값

## B1 서버 두 대 (2026-09-22 캡처, 2026-09-23 게이트)
- pcap/b1-server2.pcap 5줄: DISCOVER 둘(3.009초 간격, ICMP 확인 대기 중 재전송) · OFFER 둘(자기 캡처 중복, 선 위 1) .21→.207 · REQUEST 브로드캐스트(옵션54 .20, 옵션50 .137). 서버1 OFFER 는 유니캐스트라 없음.
- 로그: 서버1(PID115) DISCOVER/OFFER .137 ×2 → REQUEST → ACK. 서버2(PID21) DISCOVER/OFFER .207 ×2 뿐.
- 장부: 서버1 `.137` 한 줄, 서버2 빈 칸.
- 학습자: 실행 전 예측 없음. DISCOVER 둘을 "서버가 둘이라서"로 오해 → A1 과 같은 재전송이라고 설명. 로그 두 파일을 한 흐름으로 읽음 → 정정.
- 게이트: 옵션54 가 자기 아님 → 선택 안 됨 → ACK 안 보냄 → .207 은 대여 가능으로 남음. 도움 없이 도달. 장부가 OFFER 때 안 적힌다는 보충은 AI 설명.

## B2 NAK (2026-09-23, pcap/b2-neighbor.pcap — 표는 학습자가 안 붙임, 문서화 때 다시 읽을 것)
- 학습자 서술: 첫 DORA 정상 → 범위 .160~.170 로 옮겨 재기동 → dhclient 가 옛 주소 REQUEST → NAK → DISCOVER 부터 다시 → .166.
- 학습자 예측: 서버가 거절, 클라이언트는 새 임대 요청 — 맞음. NAK 이유를 "대여한 적 없어서"로 봄 → 실제는 범위 밖(`address not available`) + dhcp-authoritative 라서 적극 거절(없으면 침묵)이라고 보충.
- 질문: 반납 없이 서버 재기동 가능한가 → 가능, 운영에서는 leases 파일로 기억, 랩은 serve.sh 가 일부러 지움.
- 게이트: NAK 무시하면 서버가 그 주소를 남에게 빌려줘 중복 IP — 도움 없이 도달. Phase 1 잘못 알던 인과("REQUEST 뒤 바로 써도 된다") 닫힘.

## B3 풀 소진 (2026-09-23, pcap/b3-neighbor.pcap)
- client(c6:68:75:04:f6:c1) 가 .100 하나를 먼저 받음(로그 6줄: DISCOVER/OFFER ×2 → REQUEST → ACK).
- client2(b2:19:84:90:96:fa): DISCOVER 3개, 2초 간격, xid 0x7452e355 셋 다 같음. 선 위 응답 없음. 로그에만 `no address available` ×3.
- 학습자 예측: 서버가 무시(침묵) — 맞음. 이유로 "서버가 여럿이면 못 주는 서버마다 NAK 보내는 건 비용" 제시.
- 로그 오독: 앞 6줄을 client1·2 두 대로 읽음 → MAC 으로 한 대임을 정정.
- 정리: B2 는 REQUEST 단계 NAK, B3 는 DISCOVER 단계 침묵. 캡처만으로 A3(서버 꺼짐)와 구분 불가 → 서버 로그 필요.

## B4 주소 충돌 (2026-09-23, pcap/b4a-server.pcap · b4b-neighbor.pcap)
- 옆자리에 `ip addr add 10.55.0.137/24` 로 수동 설정.
- B4a(확인 켬): 1 DISCOVER → 2 서버 .20→.137 ICMP → 3 .137(옆자리 MAC 9e:62:0b:21:94:67) 응답(0.3ms) → 4 DISCOVER 재전송 3.006초 → 5 .138 ICMP(응답 없음) → 6 OFFER .138 (ping 뒤 0.2ms) → 8 REQUEST → 9 ACK .138.
- B4b(--no-ping, udhcpc -a): 1 DISCOVER → 2 REQUEST .137 (ACK 는 유니캐스트라 없음) → 3 ARP 요청 0.0.0.0→.137 브로드캐스트 → 4 ARP 응답 .137 → 클라이언트 MAC → 5 DECLINE(종류4, 새 xid 0xf5ce5e18) → 20.02초 뒤 6 DISCOVER → 7 REQUEST .138 → 8 ARP 요청 .138(응답 없음). udhcpc: `offered address is in use (got ARP reply), declining`.
- 학습자: 예측 없음. 무엇을 봐야 할지 몰라 AI 가 두 확인의 이유 설명 + B4a 해석 예시 제공(도움받은 응답). B4b 에서 종류 4 를 ACK 로 읽음 → DECLINE 정정. ARP 요청·응답의 목적지 MAC 차이를 물음. 20초는 모름 → RFC 2131 최소 10초 휴지 설명.
- 게이트: DECLINE 으로 서버가 .137 을 후보에서 뺐다 — 도움 없이 도달.
- 발견: LAB.md·05-03 의 "dnsmasq 가 ICMP 뒤 3초쯤 기다린다"는 캡처와 어긋남(3초는 클라이언트 재전송 간격). 문서 확인 필요.

## B5 릴레이 (2026-09-23, pcap/b5-router-segb.pcap · b5-router-sega.pcap)
- 라우터 eth0=10.55.0.30(seg-a, 서버 쪽), eth1=10.56.0.30(seg-b, 클라이언트 쪽). 로그 `DHCP relay from 10.56.0.30 to 10.55.0.20`.
- seg-b: 1·2 DISCOVER 브로드캐스트(giaddr 0), 3·4 OFFER 10.56.0.30→10.56.0.138(giaddr .30, 자기 캡처 중복), 5 REQUEST 브로드캐스트, 6 ACK. xid 0x3a2b9b57.
- seg-a: 1·2·5 10.56.0.30→10.55.0.20 유니캐스트, eth.dst 서버 MAC 9e:62:0b:21:94:67, giaddr 10.56.0.30. 3·4·6 서버→10.56.0.30. 같은 xid. 받은 주소 10.56.0.138.
- 학습자 예측: 1 "브로드캐스트로는 도달 못함"(절반 — 라우터까지는 닿음), 2 유니캐스트(맞음, 목적지 몰랐음), 3 "릴레이 열이 없는 쪽 우선"(반대 — giaddr 가 범위 선택 근거).
- 오독: 양쪽 표의 .138 을 두 주소로 읽음 → 한 교환을 두 쪽에서 본 것, 10.56.0.138 하나.
- 질문: relay 가 두 곳으로 보내나(아님, 앞=자기 수신·giaddr 값, 뒤=서버), 사람이 설정하나(예, ip helper-address), giaddr=dhcp.ip.relay 인가(예), eth0/eth1 이 내부·외부인가(이쪽·저쪽).
- 게이트: 네 칸 변화는 절반(ip.dst·relay)만 짚음 → 표 제공. "왜 seg-b 쪽 주소" 힌트 두 번 뒤 모름 → 정답 공개, 재진술 대기.
- 재진술: 학습자 요청으로 AI 가 두 경우 ASCII 흐름도 제공(도움받은 응답). 학습자 "자기 서브넷이면 직접, 아니면 게이트웨이" 맞음 / "10.55 는 라우터 거쳐 seg-a 로 통한다" 어긋남 — 게이트웨이 10.56.0.30 자체가 자기 서브넷 밖이라 첫 홉부터 막힘. **미정착 — Phase 4 출제 축**(서브넷·게이트웨이 도달 조건, giaddr 가 클라이언트 쪽 다리인 이유).

## 묶음 B 요약
- 닫힌 Phase 1 예측: REQUEST 가 거절 겸함(B1), REQUEST 뒤 바로 쓰면 안 됨 — NAK·중복 IP(B2, 잘못 알던 인과), 풀 소진은 거절 아닌 침묵(B3), ICMP 확인은 서버 쪽·클라이언트는 ACK 뒤 ARP(B4), 게이트웨이를 거치나 → 릴레이(B5).
- 막힌 축: B4 읽는 법(예시 제공), B5 giaddr 이유(정답 공개·재진술 미완), 서브넷 밖 게이트웨이 도달 불가.
