## 반영할 내용 (후보 번호는 위 파일 기준)
1·3. ACK 가 왜 필요한가 — OFFER 는 예약이 아니고 서버 장부(바인딩)는 REQUEST 뒤에 적힌다. 두 클라이언트가 같은 주소를 제안받고 먼저 온 쪽만 ACK 받는 흐름. 치트시트의 "REQUEST 뒤 응답 없음" 행이 이 절을 가리키게 해.
4. 거절 메시지 — DHCPv4 의 DHCPNAK, DHCPv6 의 REPLY 상태 코드. 풀이 빈 서버가 DISCOVER 단계에서는 제안 자체를 안 보낸다는 것과 구분해서. 치트시트에 NAK 행 추가.
2. 네트워크 세그먼트 정의 — 라우터를 거치지 않고 닿는 범위 = 브로드캐스트가 닿는 범위. TCP 세그먼트와 다른 말이라는 한 문장. 처음 등장하는 자리보다 앞에.
7. IPv4 릴레이 — 라우터에 서버 주소를 설정해 두고 브로드캐스트를 유니캐스트로 대신 전달. 문서는 지금 DHCPv6 릴레이만 다뤄.
8. §4 끝 "ARP 로 다시 확인" 앞에 ARP 요청이 MAC 브로드캐스트라는 전제 한 줄(또는 01-01 링크).
9. 확인의 분담 — 서버는 OFFER 전에 ICMP 로, 클라이언트는 ACK 뒤에 ARP 로. 그리고 ACK(장부끼리의 충돌)와 ARP(서버가 모르는 수동 설정)가 서로 다른 문제를 막는다는 것.
5. DISCOVER 의 출발지 주소 0.0.0.0.
6. REQUEST 의 yiaddr — "값이 채워졌으면 제안 이후입니다" 문장이 REQUEST 에서도 성립하는지 점검하고 필요하면 고쳐.
10. 핵심 요약의 산문 대응을 3열 표(역할 · IPv4 · IPv6)로.

## 도식 — 적극적으로 추가해
흐름·범위·분기가 있는 자리마다 도식을 둬. 아래는 최소 목록이고, 쓰다가 흐름이 보이는 ### 가 더 있으면 더 그려.
- 세그먼트 범위도 — 스위치·라우터·브로드캐스트가 닿는 범위와 멈추는 경계
- 릴레이 흐름 — 브로드캐스트가 라우터에서 멈추고 릴레이가 서버에 유니캐스트로 대신 전달, 응답이 돌아오는 길
- OFFER 는 예약이 아니다 — 클라이언트 A·B 와 서버의 시퀀스(같은 주소 제안 → 둘 다 REQUEST → A 는 ACK, B 는 NAK 또는 무응답)
- REQUEST 한 번의 브로드캐스트가 선택과 거절을 겸한다 — 서버 둘 시퀀스. 기존 05-01.dora.svg 가 이미 담고 있으면 그 도식을 확장해
- ACK 뒤 ARP 확인 → DECLINE → 1 찾기부터 재시작
- 진단 분기도 — 치트시트 표를 "어느 메시지까지 갔나"로 갈라지는 결정 흐름으로
- 같은 스위치에서 남의 DHCP 는 보이고 남의 유니캐스트는 안 보이는 이유(01-01.address-reach.svg 재사용 가능 여부 먼저 확인)
