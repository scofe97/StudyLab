# 실습 1 — traceroute 와 ICMP

## 1-1. 예측 (실행 전에 적습니다)

> 실행하기 전에 적고, 실행한 뒤에도 **고치지 않습니다.** 어긋난 자리가 배움입니다.

**대상**: `1.1.1.1`

| 물음 | 예측 |
|---|---|
| 홉이 몇 개쯤 나올까 | **모르겠다** — 감이 안 잡힌다 |
| 한 줄에 `ms` 값이 몇 개 찍힐까 | **3개.** 다만 "한 홉당 응답이 하나 아닌가?" 하는 의심이 남았다 |
| 첫 줄에 나올 IP 는 무엇일까 | **기본 게이트웨이 (집 공유기)** |
| 마지막 줄은 어떻게 끝날까 | **목적지(`1.1.1.1`) 자신이 마지막 줄에 나올 것** |

> 첫 시도에서 `traceroute to 1.1.1.1` 을 쳐서 `bad value for packet length` 가 났다.
> 예시로 보여 준 **출력의 첫 줄**을 명령으로 읽은 것. `to` 가 호스트로, `1.1.1.1` 이
> 패킷 길이 인자로 파싱됐다. 올바른 명령은 `traceroute 1.1.1.1`.

**홉 4 의 갈림이 첫 실행과 다르다.**

```
1차 :  1.213.15.45  가 두 번 ,  1.208.12.205 가 한 번
2차 :  1.213.15.45  가 한 번 ,  1.208.12.205 가 두 번
```

같은 명령을 두 번 쳤는데 **탐침이 배분된 비율이 달라졌다.** 경로가 고정돼 있지 않고
**매번 갈린다**는 증거다. 같은 비용 경로 여럿이 실제로 돌아가고 있다는 것을,
한 번이 아니라 두 번 재서 확인한 셈이다.

### `tcpdump` 첫 시도는 0건 — 원인 둘

```
sudo tcpdump -n -i en0 'icmp or (udp and dst portrange 33434-33434)'
…
0 packets captured
154 packets received by filter
```

- **순서를 틀렸다.** `tcpdump` 를 켠 뒤 **같은 창에서 `^C` 로 끄고** `traceroute` 를 쳤다.
  잡는 동안 트래픽이 없었으니 0건이 나온 것. 두 창에서 **동시에** 돌려야 한다.
- **필터 범위도 한 포트뿐이었다.** `33434-33434` 는 33434 하나만 덮는데,
  첫 탐침이 33435 부터 시작하므로 어차피 하나도 안 걸린다.

`154 packets received by filter` 는 **필터를 거친 후보가 154개였고 그중 0개가 조건에 맞았다**는 뜻이다.
잡을 것이 아예 없었다는 뜻은 아니다.


세 번 실행한 결과를 나란히 놓으면 —

| 홉 | 1차 | 2차 | 3차 |
|---|---|---|---|
| 3 | `10.204.127.17` | `10.204.127.17` | **`10.204.127.21`** |
| 4 | `1.213.15.45` · `1.208.12.205` | `1.213.15.45` · `1.208.12.205` | **`1.208.15.45`** 하나만 |

**매 실행마다 지나는 라우터가 바뀐다.** 3차에서는 홉 4 가 셋 다 같은 라우터라
갈림이 아예 안 보였다. 한 번만 재고 끝냈다면 "이 자리엔 라우터가 하나" 라고 잘못 결론지었을 것이다.

### 탐침 셋의 한계 — 스스로 짚은 것

"다른 라우터 셋이 한 번씩 답했다면, 각 라우터의 변동은 어떻게 아느냐"고 물었다.
**맞는 지적이고, 답은 「알 수 없다」다.**

탐침 셋은 **자원 하나를 두 목적에 나눠 쓰는 것**이다.

| 상황 | 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| 같은 라우터가 셋 다 답 | 그 자리의 **시간 변동** | 다른 경로가 있는지 |
| 다른 라우터가 하나씩 답 | 경로가 **여럿이라는 사실** | 각 라우터의 **변동** |

경로가 갈리는 순간 **둘 다 어중간해진다.** 게다가 셋을 보내 셋이 다 달랐다면
**그게 전부인지도 알 수 없다** — 넷째 경로가 있는데 안 걸렸을 수 있다.

제대로 재려면 탐침을 계속 보내야 하고, 그 일을 하는 도구가 **`mtr`** 이다.
traceroute 를 한 번이 아니라 **끊임없이 반복**하면서 홉마다 통계를 쌓는다.

## 1-3. 관찰 — traceroute 출력에서 읽은 것

| 확인할 것 | 실제 | 예측과 같았나 |
|---|---|---|
| 홉 수 | **13** | 예측이 "모르겠다"였으니 대조 불가 |
| 첫 줄의 IP | **192.168.0.1 — 기본 게이트웨이** | **맞음** |
| 마지막 줄 | **`one.one.one.one (1.1.1.1)` — 목적지 자신** | **맞음** |
| 한 줄에 `ms` 값이 몇 개 | **전 홉 예외 없이 3개** | **맞음.** 의심했던 "하나 아닌가"는 틀렸다 |
| TTL 이 1부터 하나씩 오르는가 | **오른다. 홉마다 1씩** | 노트 주장대로 |
| 목적지 포트가 탐침마다 오르는가 | **탐침마다 오른다. 홉마다가 아니다** | 노트 주장대로 |

### 출력에서 스스로 발견한 것 — 줄이 갈라진다

처음 읽었을 때 "항상 3번 보내는 게 아닌 것 같다. 어떤 홉은 2번, 어떤 홉은 3번"이라고 읽었다.
**세어 보니 모든 홉이 정확히 3개였다.** 갈린 것은 횟수가 아니라 **응답한 라우터**다.

```
 4  1.213.15.45   2.782 ms  2.704 ms     ← 탐침 1·2 는 이 라우터가 답
    1.208.12.205  2.417 ms               ← 탐침 3 은 다른 라우터가 답
                                            합치면 3개
 5  100.76.9.5    4.236 ms
    100.76.10.1   2.584 ms               ← 셋이 전부 다른 라우터
    100.76.1.5    3.891 ms
```

같은 홉 자리에 **라우터가 여럿** 있고, 탐침 셋이 **서로 다른 길**로 갔다는 뜻이다.

**이것이 `05-02` §2 가 적은 OSPF 의 진전 넷 중 하나다.**

> **같은 비용 경로 여럿**: 목적지까지 비용이 같은 경로가 여럿이면 하나만 고르지 않고 여럿을 함께 쓸 수 있습니다.

홉 5~8·10~12 에서 그것이 실제로 일어나고 있다. 노트가 한 줄로 적고 지나간 것을 눈으로 본 셈이다.

**그리고 이것이 "왜 세 번 보내는가"의 진짜 답이기도 하다.** 한 번만 쟀다면 경로가 여럿이라는 사실을
아예 몰랐을 것이다. 세 번이 서로 다른 라우터를 지나면서 **경로 다중성이 드러났다.**

### 홉 2 가 `* * *` 인 것

탐침 셋이 다 나갔는데 **아무 응답도 안 왔다.** 그 자리의 장비가 `ICMP time exceeded` 를
보내지 않도록 설정됐거나 중간에서 걸러진 것이다.

**traceroute 는 라우터의 협조에 전적으로 의존한다.** 라우터가 입을 다물면 그 자리는 영영 안 보인다.
`05-01` §1 에서 본 "인터넷은 라우터를 최대한 멍청하게 두기로 했다"의 다른 얼굴이다 —
알려 줄 의무가 없으니 안 알려 줘도 그만이다.

## 1-4. tcpdump — 인터페이스를 잘못 짚어 두 번 헛돌았다

**`en0` 으로 잡으면 0건이 나온다.** 이 기계의 기본 경로가 `en0` 이 아니기 때문이다.

```bash
route -n get 1.1.1.1 | grep -E "interface|gateway"
#   gateway: 192.168.0.1
# interface: en5        ← 여기로 나간다
```

```
en0 : 172.16.1.236     ← 다른 망. 기본 경로가 아니다
en5 : 192.168.0.184    ← 기본 게이트웨이 192.168.0.1 로 나가는 인터페이스
```

**인터페이스 이름을 외우지 말고 매번 `route -n get <목적지>` 로 확인한다.**
`en0` 이 Wi-Fi 라는 관례는 기기와 시점에 따라 어긋난다.

### 잡힌 것 — 포트는 탐침마다, TTL 은 홉마다

### 덤 — ICMP 길이가 라우터마다 다르다

```
192.168.0.1     → length 48
10.204.127.21   → length 36
```

노트 §5 의 "노트의 읽기"가 정확히 이 자리를 다뤘다.

> 잡은 ICMP 메시지의 길이는 48바이트인데, ICMP 헤더 8 에 인용된 원본 40 을 더한 값이다.
> 원본 UDP 데이터그램이 IP 헤더 20 + UDP 헤더 8 + 데이터 12 로 딱 40 이니,
> **이 라우터는 원본을 통째로 돌려보냈다.** 원문의 "헤더와 앞 8바이트"는 RFC 792 의
> 최소치이고, RFC 1812 는 576바이트를 넘지 않는 선에서 가능한 한 많이 담으라고 권한다.

`36 = 8 + 28` 이고 `28 = IP 헤더 20 + UDP 헤더 8` 이니, **통신사 라우터는 RFC 792 최소치만**
돌려보낸다. **같은 트레이스 한 번에 두 정책이 동시에 보인다** — 공유기는 통째로, 통신사는 최소치로.
"최소치를 규칙으로 읽으면 실제와 어긋난다"는 노트의 경고가 눈앞에서 확인됐다.

### 출발지 포트가 실행 회차를 가른다

```
1회차 : 192.168.0.184.54087 > …
2회차 : 192.168.0.184.54143 > …
```

목적지 포트는 회차마다 다시 `33435` 부터 시작하고, **출발지 포트가 달라져** 회차가 갈린다.

### 직접 실행해 재확인 — 세 홉이 깔끔하게 갈렸다

```
ttl 1 → 33435 · 33436 · 33437
ttl 2 → 33438 · 33439 · 33440
ttl 3 → 33441 · 33442 · 33443
```

`id` 필드도 36268 부터 패킷마다 1씩 오른다. 출발지 포트는 36267 로 회차 내내 고정.

### 새 발견 — 침묵하던 홉 2 가 이번엔 답했다

```
 1  192.168.0.1 (192.168.0.1)      1.462 ms  1.108 ms  0.605 ms
 2  1.223.246.73 (1.223.246.73)    3.190 ms  2.905 ms  *      ← 앞선 네 번은 * * * 였다
 3  10.204.127.17 (10.204.127.17)  3.167 ms  2.243 ms  1.774 ms
```

앞선 실행에서 홉 2 는 **네 번 연속 `* * *`** 이었다. 그래서 "이 라우터는 ICMP 를 안 보내도록
설정됐다"고 읽었는데, **이번에 두 번 답했다.** 그리고 세 번째 탐침만 `*` 다.

**설정으로 막힌 것이 아니라 속도 제한에 걸렸던 것으로 읽힌다.** 많은 라우터가 ICMP 응답 생성에
초당 몇 개 같은 상한을 둔다. 앞선 실행들에서 연달아 쏘는 동안 상한을 넘겼고, 시간을 두고 다시
치니 여유가 생겨 답한 것이다. 같은 줄에서 두 번은 답하고 한 번은 `*` 인 것도 그 해석에 맞는다.

**한 번 관찰로 "이 라우터는 안 답한다"고 결론 내렸다면 틀렸을 것이다.**
`* * *` 은 "응답하지 않도록 설정됨"일 수도 있고 "지금 바빠서 못 답함"일 수도 있는데,
traceroute 출력만으로는 둘이 구별되지 않는다.

그리고 위상은 일관됐다 — 홉 3 은 이전 실행들과 같은 `10.204.127.17` 이다.
**홉 2 가 새로 생긴 게 아니라 원래 있었는데 안 보였던 것**이다.

## 1-5. 변형 — 탐침 수를 하나로 줄이면

```bash
traceroute -m 3 -w 1 -q 1 1.1.1.1
```

```
ttl 1 → 33435
ttl 2 → 33436
ttl 3 → 33437
```

**포트가 홉마다 1씩만 오른다.** 탐침 셋일 때는 홉마다 셋씩 올랐다.

두 실험을 합치면 규칙이 하나로 좁혀진다.

| | 홉당 탐침 | 홉당 포트 소비 |
|---|---|---|
| `-q 3` (기본) | 3 | **3** |
| `-q 1` | 1 | **1** |

**포트를 정하는 것은 홉이 아니라 탐침이다.** 노트의 "홉마다가 아니라 탐침마다 오른다"가
반증 시도를 통과했다. 한 번만 봤으면 "홉마다 오른다"로 읽어도 구별이 안 됐을 자리다.

## 1-6. 양방향 캡처에서 더 나온 것

`'icmp or (udp and dst host 1.1.1.1)'` 로 양쪽을 다 잡으니 세 가지가 더 보였다.

### (가) ICMP 안에 원본이 통째로 들어 있다

```
192.168.0.1 > 192.168.0.184: ICMP time exceeded in-transit, length 48
    IP (tos 0x0, ttl 1, id 47845, offset 0, flags [none], proto UDP (17), length 40)
    192.168.0.184.47844 > 1.1.1.1.33435: UDP, length 12      ← 인용된 원본
```

노트 §5 가 적은 **"그 메시지를 만들게 한 IP 데이터그램의 헤더와 앞 8바이트를 담는다"** 가
눈에 보인다. tcpdump 가 그 인용분까지 풀어서 들여쓰기로 보여 준다.

**"IP 데이터그램의 헤더와 앞 8바이트"가 무엇인지** 그림으로 놓으면 이렇다.

```
문제가 된 원본 데이터그램
┌──────────────────┬──────────────────────────────────┐
│   IP 헤더 20B    │  적재량 — UDP 또는 TCP 세그먼트    │
└──────────────────┴──────────────────────────────────┘

ICMP 가 담는 최소치 (RFC 792)
┌──────────────────┬────────┐
│   IP 헤더 전체    │  앞 8B  │
└──────────────────┴────────┘
                      └─ UDP 면 : 헤더가 딱 8B 라 헤더 전체
                         TCP 면 : 출발지 포트 2 + 목적지 포트 2 + 순서 번호 4
```

**어느 경우든 포트 둘이 반드시 들어간다.** 그것이 8 이라는 수의 이유다.
포트가 있어야 보낸 쪽이 **"내 어느 소켓의 문제였나"** 를 알 수 있다.

캡처의 길이 둘이 정확히 이 계산과 맞는다.

| 보낸 라우터 | ICMP length | 계산 | 무엇을 담았나 |
|---|---|---|---|
| `10.204.127.21` | **36** | 8 + (IP 20 + UDP 8) | **RFC 792 최소치 그대로** |
| `192.168.0.1` | **48** | 8 + (IP 20 + UDP 8 + 데이터 12) | **원본을 통째로** |

앞의 8 은 ICMP 자신의 헤더(타입·코드 등)다.

### (나) 인용된 TTL 이 "몇 홉을 지나왔는지"를 말한다

```
나간 것   : ttl 3 , id 47851 , 포트 33441
인용된 것 : ttl 1 , id 47851 , 포트 33441      ← id 는 같은데 ttl 이 다르다
```

`id` 가 같으니 **같은 패킷**이다. 그런데 TTL 이 3 이 아니라 1 이다.

**인용은 그 라우터에 도착했을 때의 상태**이기 때문이다. 3 으로 출발해 홉 둘을 지나며
3 → 2 → 1 로 깎였고, 세 번째 라우터가 1 을 받아 0 으로 만들고 폐기하면서
**받은 그대로** 인용했다. TTL 이 "얼마나 남았나"가 아니라 **"얼마나 왔나"** 를 거꾸로 알려 준다.

### (다) 돌아오는 ICMP 자신의 TTL 도 거리를 말한다

```
192.168.0.1     가 보낸 ICMP : ttl 64
10.204.127.21  가 보낸 ICMP : ttl 253
```

`10.204.127.21` 것은 255 에서 출발해 두 홉을 지나 253 이 됐다. **그 라우터가 두 홉 거리**라는 뜻이다.
공유기는 바로 옆이라 64 가 그대로다(출발값이 64).

## 1-7. 우연히 잡힌 장면 — 종료 신호와 똑같은 메커니즘

traceroute 와 무관한 패킷 한 쌍이 중간에 끼어들었는데, 하필 이 절의 핵심을 보여 준다.

```
17:18:40  IP 192.168.0.184 > 192.168.0.1: ICMP 192.168.0.184 udp port 14212 unreachable
              IP 192.168.0.1.53 > 192.168.0.184.14212:  [|domain]
```

읽으면 이렇다.

```
[1] 내 맥의 어떤 프로그램이 DNS 질의를 보냄  (공유기의 53 번 포트로)
[2] 그 프로그램이 응답을 기다리다 포기하고 소켓을 닫음
[3] 뒤늦게 DNS 응답이 14212 번 포트로 도착
[4] 그 포트를 듣는 소켓이 없음  →  내 맥이 ICMP port unreachable 을 돌려보냄
```

**traceroute 가 "이제 멈춰도 된다"고 판단하는 그 신호와 정확히 같은 메커니즘**이다.
목적지 포트에 소켓이 없으면 `port unreachable` 이 돌아온다는 것 말이다.

다만 **방향이 반대다.** 여기서는 **내 맥이 ICMP 를 만들어 보냈다.**
ICMP 는 라우터만 쓰는 게 아니라 **호스트도 쓴다.** 노트 §5 첫 문장이
"호스트와 라우터가 네트워크 계층 정보를 서로 주고받는 데 쓰인다"고 적은 그대로다.

## 1-8. 실습 1 정리

### 노트의 주장 — 넷 다 확인됐다

| 주장 | 확인 방법 | 결과 |
|---|---|---|
| TTL 을 1씩 올려 가며 탐침을 보낸다 | `tcpdump -v` 의 `ttl` 필드 | **확인.** 홉마다 1씩 |
| 라우터가 `ICMP 타입 11` 로 신원을 알린다 | 돌아온 ICMP 의 출발지 IP | **확인.** `time exceeded in-transit` |
| 포트는 **홉마다가 아니라 탐침마다** 오른다 | `-q 3` 과 `-q 1` 대조 | **확인.** 3개↔1개로 갈렸다 |
| ICMP 는 원본의 헤더와 앞 8바이트를 담는다 | 인용분과 `length` 계산 | **확인.** 36 = 최소치, 48 = 통째로 |

### 노트에 없던 것 셋

1. **인용된 TTL 은 "몇 홉 왔는지"를 거꾸로 말한다.** `id` 가 같은데 TTL 이 3 → 1 로 찍힌다.
   인용이 *도착 시점의 상태*이기 때문이다.
2. **돌아오는 ICMP 자신의 TTL 로도 거리가 읽힌다.** `ttl 253` = 255 에서 두 홉.
3. **호스트도 ICMP 를 만든다.** DNS 응답이 닫힌 소켓에 도착해 내 맥이
   `port unreachable` 을 보낸 장면이 우연히 잡혔다 — traceroute 의 종료 신호와 같은 메커니즘,
   방향만 반대.

### 관찰 방법에 대해 배운 것

- **인터페이스는 외우지 않는다.** `route -n get <목적지>` 로 매번 확인한다.
  이 기계는 `en0` 이 아니라 `en5` 였고, 그걸 몰라 두 번 헛돌았다.
- **한 번의 관찰은 잠정값이다.** 홉 2 가 네 번 연속 `* * *` 여서 "설정으로 막혔다"고 읽었는데,
  다섯 번째에 답했다. `* * *` 은 "안 답하도록 설정됨"과 "지금 못 답함"을 구별해 주지 않는다.
- **변수를 바꿔 봐야 규칙이 갈린다.** `-q 3` 만 봤으면 "홉마다 오른다"와
  "탐침마다 오른다"가 구별되지 않았다.
- **필터가 무엇을 거르는지 알고 써야 한다.** `udp and dst host 1.1.1.1` 은
  나가는 쪽만 잡아서 라우터 IP 가 안 보였다.

### 노트 보강 후보 (5장 보강 프롬프트 6번에 이미 반영)

- §5 가 `tcpdump` 세 줄만 싣고 **`traceroute` 명령과 그 출력이 없다**
- 위 "노트에 없던 것 셋"은 원서에도 없는 관찰이므로 넣는다면 **"노트의 읽기"** 로 표시한다

# 실습 2 — Open vSwitch 흐름 표

## 2-1. 준비

OrbStack 우분투 머신에 설치한다. 맥에서는 커널 모듈이 필요해 VM 안에서만 돈다.

```bash
orb list
# ubuntu   running  ubuntu  resolute  arm64  13.0 GB   192.168.139.208
# ubuntu2  running  ubuntu  resolute  arm64  776.1 MB  192.168.139.238
```

설치 전에 커널에 모듈이 있는지 먼저 확인한다. 없으면 실습이 아예 성립하지 않는다.

```bash
orb -m ubuntu2 bash -lc 'uname -r; find /lib/modules/$(uname -r) -name "openvswitch*"'
# 7.0.14-orbstack-00380-ga7e0a2dc9535
# /lib/modules/7.0.14-.../kernel/net/openvswitch
```

설치.

```bash
orb -m ubuntu2 bash -lc 'sudo apt-get update -qq && sudo DEBIAN_FRONTEND=noninteractive apt-get install -y openvswitch-switch'
ovs-vsctl --version          # ovs-vsctl (Open vSwitch) 3.7.1
systemctl is-active ovs-vswitchd openvswitch-switch   # active / active
lsmod | grep openvswitch     # openvswitch 151552 4
```

`apt` 목록이 15일 지났고 디스크 여유는 123G, `sudo` 는 무암호다.

## 2-2. 무대 만들기

```bash
sudo ovs-vsctl add-br br0
sudo ip link set br0 up

for n in 1 2; do
  sudo ip netns add ns$n
  sudo ip link add veth$n type veth peer name ovs$n
  sudo ip link set veth$n netns ns$n
  sudo ovs-vsctl add-port br0 ovs$n
  sudo ip link set ovs$n up
  sudo ip netns exec ns$n ip link set lo up
  sudo ip netns exec ns$n ip link set veth$n up
  sudo ip netns exec ns$n ip addr add 10.10.0.$n/24 dev veth$n
done
```

포트 번호를 확인한다. 규칙에 쓸 이름이다.

```bash
sudo ovs-ofctl show br0
#  1(ovs1): addr:02:a2:9a:03:d3:b7
#  2(ovs2): addr:72:16:0e:b9:d1:e2
#  LOCAL(br0): addr:ca:dd:7a:9d:14:48
```

## 2-3. 예측 — 흐름 표가 비어 있으면 ping 이 통할까

학습자 예측: **통한다.** "가상 스위치가 정확히 무슨 역할을 하는지는 모르지만, 이것들이 브리지로 연결되니 가능하지 않을까."

결론부터 적으면 예측이 맞았고 기전이 한 겹 더 있었다.

## 2-4. 관찰

```bash
sudo ovs-ofctl dump-flows br0
#  cookie=0x0, duration=515.509s, table=0, n_packets=37, n_bytes=2878, priority=0 actions=NORMAL

sudo ip netns exec ns1 ping -c 2 10.10.0.2
# 2 packets transmitted, 2 received, 0% packet loss
# rtt min/avg/max/mdev = 0.091/0.966/1.842/0.875 ms
```

표가 비어 있지 않았다. `add-br` 가 브리지를 만들 때 `priority=0 actions=NORMAL` 한 줄을 함께 깐다. 통한 이유는 표가 없어서가 아니라 그 줄이 맞아서다.

TTL 64 가 출발값 그대로 도착했다. 라우터를 하나도 안 거쳤다는 뜻이고, 스위치는 링크 계층이라 TTL 을 안 만진다.

학습자가 모른다고 한 필드들: `cookie`(규칙 꼬리표), `duration`(줄이 올라온 뒤 흐른 시간), `table`(흐름 표는 여러 장이고 그중 0번), `n_packets`·`n_bytes`(그 줄에 맞은 누적 — 포트별이 아니다), `priority`(여러 줄이 맞을 때 승자), `actions`(맞았을 때 할 일).

## 2-5. 규칙 심기

표를 비우고 한 방향만 넣는다.

```bash
sudo ovs-ofctl del-flows br0
sudo ovs-ofctl dump-flows br0          # 아무것도 없음
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
# 2 packets transmitted, 0 received, 100% packet loss
```

표가 비면 폐기다. 컨트롤러가 없으니 Packet-in 이 갈 곳이 없다.

```bash
sudo ovs-ofctl add-flow br0 "in_port=1,actions=output:2"
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
# 100% packet loss

sudo ip netns exec ns1 ip neigh show
# 10.10.0.2 dev veth1 FAILED

sudo ovs-ofctl dump-flows br0
#  ... n_packets=6, n_bytes=336, in_port=ovs1 actions=output:ovs2
```

끊긴 층이 ICMP 가 아니라 ARP 였다. 그 답이 포트 2 로 돌아오다 죽었고 ping 은 시작조차 못 했다.

`336 / 6 = 56` 을 프레임 크기로 읽으면 안 된다. 여섯 개가 다 ARP 라는 보장이 없어 평균이 아무것도 못 가른다. 균질한 조건에서 다시 쟀다.

```bash
sudo ovs-ofctl del-flows br0
sudo ovs-ofctl add-flow br0 "in_port=1,actions=output:2"
sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
sudo ovs-ofctl dump-flows br0
#  ... n_packets=3, n_bytes=126, in_port=1 actions=output:2
```

`126 / 3 = 42` 다. 이더넷 14 + ARP 28. 이제 나간 것이 ARP 요청이라고 말할 수 있다.

`FAILED` 는 "없음"과 다르다. 물어본 적이 없으면 항목이 아예 안 생긴다. 이웃 표는 `ns1` 의 커널이 자기 행동을 적는 수첩이라 답이 없어도 물어봤다는 사실을 안다.

양방향을 채워 출발선을 박는다.

```bash
sudo ovs-ofctl add-flow br0 "in_port=2,actions=output:1"
sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
# 2 packets transmitted, 2 received, 0% packet loss

sudo ovs-ofctl dump-flows br0
#  ... n_packets=12, n_bytes=672, in_port=ovs1 actions=output:ovs2
#  ... n_packets=3,  n_bytes=210, in_port=ovs2 actions=output:ovs1
sudo ip netns exec ns1 ip neigh show
# 10.10.0.2 dev veth1 lladdr 02:bd:9e:51:30:d9 REACHABLE
```

## 2-6. L4 매칭

**미실시.** 포트 번호 대신 TCP 포트로 일치를 거는 실험은 하지 않았다. Packet-in 관측이 5장 축에 더 가까워 그쪽으로 갔다.

다음에 이을 때 쓸 명령만 남긴다.

```bash
sudo ovs-ofctl add-flow br0 "in_port=1,tcp,tp_dst=22,actions=drop"
sudo ovs-ofctl add-flow br0 "in_port=1,actions=output:2"     # priority 기본 32768 로 동률
```

## 2-7. 폐기 규칙

돌아오는 방향만 `drop` 으로 바꾼다. 버리더라도 맞은 것은 세어지는지가 물음이다.

```bash
sudo ovs-ofctl add-flow br0 "in_port=2,actions=drop"
sudo ovs-ofctl dump-flows br0
#  ... n_packets=15, n_bytes=882, in_port=ovs1 actions=output:ovs2
#  ... duration=0.017s, n_packets=0, n_bytes=0, in_port=ovs2 actions=drop

sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
# 100% packet loss

sudo ovs-ofctl dump-flows br0
#  ... n_packets=17, n_bytes=966, in_port=ovs1 actions=output:ovs2
#  ... n_packets=2,  n_bytes=84,  in_port=ovs2 actions=drop
sudo ip netns exec ns1 ip neigh show
# 10.10.0.2 dev veth1 INCOMPLETE
```

두 가지가 동시에 나왔다.

첫째, `84 / 2 = 42` 다. 이더넷 14 + ARP 28. **ARP 응답 두 개가 도착했고 스위치가 죽였다.** `ns2` 가 없었다면 이 계수기는 0 이다. "없는 기계"와 "죽은 응답"이 숫자 하나로 갈렸다. 들어가는 쪽도 `882 → 966` 으로 84, 역시 42 바이트짜리 둘이라 오간 것이 처음부터 ARP 였다.

둘째, 줄이 둘로 늘지 않았다. `duration=0.017s` 와 `n_packets=0` 이 리셋의 증거다. **같은 일치·같은 우선순위면 새 줄이 아니라 같은 줄로 덮어쓴다.** 학습자 예측은 "줄이 두 개 되고 뒤가 이기려나"였고, 뒤가 이기는 건 맞았지만 줄 수가 달랐다.

## 2-8. 해석

마지막으로 동작을 `CONTROLLER` 로 바꿔 Packet-in 을 실제로 본다. 받을 상대는 `ovs-ofctl monitor` 가 대신한다. 듣기만 하는 귀다.

```bash
nohup sudo ovs-ofctl monitor br0 65535 >/tmp/pktin.log 2>&1 &
sleep 1
sudo ovs-ofctl add-flow br0 "in_port=1,actions=CONTROLLER:65535"
sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 1 -W 1 10.10.0.2
# 1 packets transmitted, 0 received, 100% packet loss
sleep 1 && sudo pkill -f "ovs-ofctl monitor"
cat /tmp/pktin.log
```

```
NXT_PACKET_IN2 (xid=0x0): cookie=0x0 total_len=42 in_port=1 (via action) data_len=42 (unbuffered)
arp,vlan_tci=0x0000,dl_src=26:d0:95:30:bd:f5,dl_dst=ff:ff:ff:ff:ff:ff,
    arp_spa=10.10.0.1,arp_tpa=10.10.0.2,arp_op=1,arp_sha=26:d0:95:30:bd:f5,
    arp_tha=00:00:00:00:00:00
```

올라간 것은 IP 주소가 아니라 **패킷 그 자체**다. `data_len=42` 가 통째로 올렸다고 말하고 둘째 줄이 그 디코드다. `(via action)` 은 표 미스가 아니라 `CONTROLLER` 동작에 맞아 올라갔다는 표시다. `dl_dst=ff:ff:ff:ff:ff:ff` 는 플러딩이 아니라 보낸 쪽이 적은 브로드캐스트다.

그런데 ping 은 여전히 100% 손실이었다. **Packet-in 만으로는 아무 일도 일어나지 않는다.** 진짜 컨트롤러라면 Packet-out 으로 이 패킷을 어디로 보낼지 지시하거나 Modify-State 로 규칙을 내려보낸다. 대개 둘 다 한다.

그래서 노트의 서술에 조건이 하나 빠져 있었다. `05-03` §3 은 "일치하지 않은 패킷은 컨트롤러로 올라간다"고 단정하는데, **컨트롤러가 붙어 있을 때만** 그렇다. 없으면 OpenFlow 기본값대로 버려지고, 표를 비웠을 때 나온 100% 손실이 그것이다.
