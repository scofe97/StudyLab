# gateway-lab

HTTP 리버스 프록시에서 시작해 API 게이트웨이까지, raw Netty 위에 단계별로 짓는 학습 랩입니다.

## 무엇을 확인하려는 랩인가

프레임워크가 감춰 주던 것을 손으로 만집니다. 요청 하나가 클라이언트 채널과 백엔드 채널 두 파이프라인을 어떻게 지나는지, 버퍼는 누가 갖고 있다가 누가 놓는지, 백엔드가 죽거나 느릴 때 무엇이 어디서 실패하는지를 코드와 실행 로그로 확인합니다. 제품 수준 게이트웨이를 복제하지 않습니다. 인증·보안 필터·캐시·변환은 범위 밖입니다.

## 스택

| 항목 | 값 |
|---|---|
| Java | 25 (Gradle toolchain 으로 지정) |
| Spring Boot | 4.1.1 — 설정·관리 API 에만 쓰고 웹 서버는 띄우지 않음 |
| Netty | Boot BOM 이 관리하는 4.2.x, ChannelPipeline 직접 구성 |
| 이력 저장 | Spring Data JDBC (Phase 6 부터) |
| 빌드 | Gradle 9.1 (래퍼) |

## Phase 와 완료 기준

각 Phase 는 **빌드 · 테스트 · 이해 확인** 세 항목이 다 채워져야 완료입니다. 이해 확인은 실행 전 예측, 요청 경로와 버퍼 소유권 설명, 조건 변경 시 결과, 실패 원인 입증 방법 네 가지 질문에 답하는 것입니다.

| Phase | 학습 질문 | 최소 구현 | 실패 실험 | 상태 |
|---|---|---|---|---|
| 1 고정 프록시 | 요청 하나가 두 채널을 어떻게 지나고 버퍼는 누구 것인가 | `:8080 → :9000`, HTTP/1.1, 요청당 연결 종료, 바디 1 MiB 집계, hop-by-hop 헤더 처리 | 백엔드 부재 → 502, 바디 초과 → 413, 클라이언트 조기 종료 | 뼈대 완료, 구현 전 |
| 2 경로 라우팅 | 매칭 우선순위와 미일치 | prefix 라우트 표, 404 | 경계 충돌, 겹치는 prefix | |
| 3 타깃 그룹 | 백엔드 선택 상태와 헬스의 소유자 | 라운드 로빈, 주기 헬스체크 | 하나 장애 → 모두 장애 → 복구 | |
| 4 장애 처리 | connect 실패와 응답 지연의 구분, 재시도가 안전한 조건 | 타임아웃(504), 재시도 예산, failover, 중복 응답 방지 | 느린 백엔드, 느린 클라이언트, 재시도 중 끊김 | |
| 5 요청 식별자 | 동시 요청에서 식별자가 섞이지 않는 자리 | txId, 상관관계 ID 수용, 채널 컨텍스트 | 정리 누락 재현, 비동기 경계 뒤 로그 | |
| 6a 로그 스키마 | 실패를 입증하는 필드 | JSON 한 줄, 동기 기록 | 민감 헤더 미기록 | |
| 6b 비동기 큐 | 로그 I/O 가 루프를 막지 않는 구조와 포화 정책 | 제한된 큐, drop 카운터 | 소비자 정지 → 포화 | |
| 6c 이력 저장 | DB 지연·장애의 격리 | JDBC 배치 저장, 실패 격리 | DB 정지 → 요청 무영향 | |
| 7 관측 확장 (선택) | 로그가 검색 시스템에 닿기까지 | 수집기 → 검색 백엔드 | 수집기 정지 | |
| 8 관리 API | 처리 중 요청과 새 요청이 보는 라우트 버전 | 라우트 추가·삭제, 불변 표 교체, 잘못된 설정 거절 | 처리 중 변경 | |

## 실행

```bash
./gradlew build          # 컴파일 + 테스트
./gradlew bootRun        # 앱 기동
```

## 기기 사정으로 바꾼 값

- 전역 Gradle 설정이 daemon JVM 을 JDK 17 로 고정하고 있어, 이 랩은 `build.gradle.kts` 의 `toolchain { languageVersion = 25 }` 로 컴파일·실행 JDK 만 25 로 올립니다.
- 절대 경로는 git 에 넣지 않습니다. 첫 빌드에서 Gradle 이 Temurin 25 를 자동 프로비저닝했습니다. `./gradlew -q javaToolchains` 로 어느 JDK 가 쓰이는지 볼 수 있습니다.
