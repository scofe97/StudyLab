Kubernetes 네트워크 흐름: Pod에서 다른 노드의 Pod까지

다른 노드에 있는 Pod를 Service 이름으로 부르면, 패킷은 Pod의 가상 NIC에서 나와 호스트의 veth·브리지를 지나고, kube-proxy가 만든 iptables 규칙에서 목적지가 실제 Pod IP로 바뀐 뒤 노드 사이 네트워크를 건넌다. 아래는 그 순서다.

2. 단계별 설명

#어디서무슨 일이 일어나는가
1Pod 안Pod는 자기만의 네트워크 네임스페이스를 가진다. 애플리케이션이 my-svc:80을 조회하면 CoreDNS가 Service의 ClusterIP를 돌려주고, 패킷은 Pod의 eth0로 나간다.
2veth 쌍eth0는 veth 쌍의 한쪽 끝이다. 다른 끝은 호스트 네임스페이스에 있어, Pod 안으로 들어간 케이블처럼 동작한다. 한쪽에 넣은 프레임은 반대쪽으로 나온다.
3브리지 / CNI호스트 쪽 veth 는 브리지(cni0 등)에 붙거나 CNI 플러그인이 만든 라우트로 연결된다. 목적지가 같은 노드 Pod이면 브리지에서 끝나고, 아니면 호스트의 라우팅 테이블로 올라간다. Cilium 같은 eBPF CNI는 브리지 없이 같은 일을 다른 방식으로 한다.
4Service 변환ClusterIP는 어느 NIC에도 붙지 않은 가상 주소다. kube-proxy가 노드마다 iptables(nat) 규칙을 만들어 두고, KUBE-SERVICES → KUBE-SVC-* → KUBE-SEP-* 체인을 따라 목적지를 실제 Pod IP 하나로 DNAT 한다. 후보가 여럿이면 확률 규칙으로 하나를 고른다.
5노드 사이바뀐 목적지(10.244.2.7)는 다른 노드의 Pod 대역이다. CNI 에 따라 VXLAN 같은 오버레이로 캡슐화해 보내거나, 라우팅(BGP 등)으로 그대로 보낸다.
6노드 B노드 B가 패킷을 받아 (필요하면 디캡슐화 후) 자기 Pod 대역으로 라우팅한다. 브리지와 veth 를 지나 Pod의 eth0에 도착한다.
7응답응답 패킷은 반대 방향으로 간다. 노드 A의 conntrack이 DNAT 매핑을 기억하고 있어서, 출발 주소가 Pod IP에서 다시 ClusterIP로 되돌려진 채 클라이언트 Pod에 닿는다.

3. Service는 어디에 있는가

Service 는 프로세스도 NIC도 아니다. API 서버에 저장된 객체와, 그것을 읽은 kube-proxy 가 각 노드에 심어 둔 규칙의 묶음이다. 그래서 어느 노드에서 호출해도 같은 ClusterIP 가 같은 Pod 집합으로 풀린다. Pod가 바뀌면 EndpointSlice 가 바뀌고, kube-proxy 가 규칙을 다시 쓴다.

kube-proxy 모드가 ipvs 이거나 CNI 가 kube-proxy 를 대체(eBPF)하는 클러스터에서는 4단계의 구현이 다르다. 개념 흐름은 같다.

4. 직접 확인하는 명령

# Pod의 인터페이스와 라우트
kubectl exec -it <pod> -- ip addr show eth0
kubectl exec -it <pod> -- ip route

# 노드에서 Service 규칙 보기 (iptables 모드)
sudo iptables -t nat -L KUBE-SERVICES -n | grep <cluster-ip>
sudo iptables -t nat -L KUBE-SVC-XXXX -n

# DNAT 매핑 추적
sudo conntrack -L | grep <cluster-ip>
