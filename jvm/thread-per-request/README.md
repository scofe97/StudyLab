# thread-per-request — 요청당 스레드와 Go 를 같은 부하로 비교한다

Spring MVC(Tomcat)는 요청 하나에 스레드 하나를 붙입니다. 작은 요청이 대량으로 오거나, 요청 하나가 느리거나 크거나, 연결이 오래 열려 있을 때(SSE) 이 모델이 어디서 막히는지, 가상 스레드와 Go 의 goroutine 이 그 지점을 어떻게 바꾸는지를 같은 엔드포인트·같은 부하기로 재어 봅니다. 정교한 벤치마크가 아니라 CS 호기심을 숫자로 확인하는 작은 실험입니다.

- write 문서: `runners-high` 의 `write/09_spring/project/thread-per-request/README.md`
- 그래프: `viz/index.html` 을 브라우저로 엽니다(`results/` 를 바꿨다면 `./mkdata.sh` 먼저).

## 구성

| 폴더 | 내용 |
|---|---|
| `spring/` | Spring Boot 4.1.1 · Java 25 · `spring-boot-starter-webmvc`(Tomcat). Gradle 프로젝트 |
| `goserver/` | `net/http` 로 같은 엔드포인트. 연결마다 goroutine 하나 |
| `loadgen/` | Go 부하기. 기본은 닫힌 루프(동시 `c` 개 워커가 끝나자마자 다음 요청을 보낸다), `-sse` 는 연결 N 개를 열어 두고 이벤트 지연을 잰다 |
| `run.sh` | 서버를 띄우고 시나리오를 돌려 `results/*.json` 에 쓴다 |
| `mkdata.sh` | `results/*.json` 을 `viz/data.js` 로 묶는다 |

엔드포인트는 `GET /small`(즉시 짧은 JSON), `GET /slow?ms=200`(블로킹 대기), `GET /big?kb=1024`(큰 본문), `GET /sse?interval=1000`(연결을 열어 두고 interval ms 마다 `data: <서버 송신 시각 ns>` 이벤트), `GET /stats`(스레드 수)입니다.

## 변형

| 변형 | 설정 |
|---|---|
| `spring-platform` | Tomcat 기본, `threads.max=200` |
| `spring-platform-small` | `server.tomcat.threads.max=20` (풀이 막히는 장면을 짧은 시간에 보이려는 값) |
| `spring-virtual` | `spring.threads.virtual.enabled=true` |
| `go` | goroutine per connection |

시나리오 D(SSE)는 변형 이름이 다릅니다. 같은 `/sse` 를 서로 다른 구현으로 받습니다.

| 변형 | 구현 |
|---|---|
| `spring-platform-blocking` | 핸들러가 `while` 루프로 쓰고 `Thread.sleep` — 요청 스레드를 쥔 채. 풀 200 |
| `spring-platform-emitter` | `SseEmitter` 를 반환해 Tomcat 스레드를 놓아주고, 공용 스케줄러 스레드 한 개가 모든 emitter 에 send. 풀 200 |
| `spring-virtual-blocking` | `spring-platform-blocking` 과 같은 코드, `spring.threads.virtual.enabled=true` |
| `go` | goroutine 하나가 루프를 돌며 쓰고 `http.Flusher` 로 flush |

Spring 의 구현 선택은 `--tpr.sse.mode=blocking|emitter` 입니다(기본 blocking).

## 실행

```bash
./run.sh all all                 # A·B·C 변형 4 × 시나리오 3 + D 변형 4 × 연결 수 2, 약 12분
./run.sh spring-platform-small B # 변형 하나·시나리오 하나
./run.sh all D                   # SSE(연결 1,000·5,000)만, 약 4분
./mkdata.sh                      # 그래프용 data.js 갱신
bazel test //jvm/thread-per-request/...               # Go 단위 시험
bazel test //jvm/thread-per-request:gradle_test       # Spring 시험(manual, 네트워크 필요)
```

- `run.sh` 는 `ulimit -n 10240` 으로 올린 뒤 서버를 띄우고, 준비되면 3초 예열 후 시나리오를 돌립니다. 각 실행은 워밍업 2초 + 측정 10초입니다.
- D 는 연결 N(1,000·5,000)개를 4초에 걸쳐 열고, 1초 더 기다린 뒤 15초 동안 받은 이벤트를 잽니다. 서버는 N 마다 새로 띄우고 예열하지 않습니다. 예열로 힙이 커져 있으면 GC 가 줄인 뒤의 RSS 가 기준선보다 작아져 연결당 증가분이 음수가 되었기 때문입니다.
- 부하는 `localhost:18080` 으로만 보냅니다.
- OS 스레드는 `ps -M`(macOS)로 부하 중간에 한 번 잰 값이고, RSS 도 같은 시점입니다.

### D. `/sse?interval=1000` — 연결 N 개 유지

지연은 "부하기가 받은 시각 − 서버가 적은 시각" 입니다(같은 기기라 시계를 공유). 첫 이벤트를 받은 연결만 "유지"로 셉니다. "첫 이벤트 못 받음"은 TCP 는 열렸지만 이벤트가 오지 않은 연결입니다. 연결 실패·못 연 연결은 모든 칸에서 0 이었습니다. 연결당 RSS 는 (부하 중 RSS − 기동 직후 RSS) ÷ 유지된 연결 수이고, 1,000 개에서는 JVM 이 기준선 아래로 내려가 읽을 수 없어 5,000 개 칸만 적습니다.

## 읽는 법

**리틀의 법칙 대조(B).** 느린 요청의 처리량 상한은 `min(스레드 수, c) ÷ 0.2s` 입니다. `spring-platform-small` 은 풀 20 이라 약 100/s 가 예상이었고, c=100 에서 100/s, c=1000 에서 100/s 로 맞았습니다. 대신 지연이 c=1000 에서 p50 10초까지 늘었습니다(풀이 비기를 기다리는 시간). `spring-platform`(풀 200)은 c=1000 에서 1,000/s 로 상한과 같고, c=100 에서는 479/s 로 상한 500/s 의 96% 입니다. 가상 스레드와 Go 는 c=1000 에서 4,350/s·4,902/s 로 상한 5,000/s 에 가깝고 p50 은 약 200ms 를 지켰습니다.

**SSE 대조(D).** 풀 200 에서 루프로 받는 변형은 연결을 열어 두는 동안 요청 스레드를 쥐고 있어서, 연결이 1,000 개든 5,000 개든 첫 이벤트를 받는 연결이 200 개(풀 크기)였습니다. 나머지는 Tomcat 이 TCP 연결은 받았지만(`maxConnections` 8192 아래) 일할 스레드가 없어 이벤트가 오지 않았습니다. 같은 코드가 가상 스레드에서는 5,000 개를 유지했고, `SseEmitter` 는 요청 스레드를 놓아주어 같은 풀 200 으로 5,000 개를 유지했습니다(스케줄러 스레드가 이벤트를 보냅니다). 이벤트 지연은 유지된 연결 모두에서 p99 7ms 이하였고, 풀 200 변형의 5,000 칸 p99 50.8ms 는 한 번 튄 값이고 원인은 확인하지 않았습니다(같은 변형의 1,000 칸은 1.5ms). `ulimit -n` 10,240·localhost 출발 포트·`maxConnections` 에는 걸리지 않았습니다.

**오류.** 최종 표의 오류는 모두 0 입니다. 다만 전체 실행 중 `spring-platform` A c=1000 에서 한 번 HTTP 404 가 3,243건 나왔고, 같은 조건 재실행 두 번에서는 재현되지 않아 그 한 칸은 재실행 값으로 바꿨습니다. 원인은 확인하지 못했습니다.

**한계.** 한 번씩 잰 값입니다(분산 없음). A 의 변형 간 차이(수 %~수십 %)는 같은 기기에서 부하기와 서버가 CPU 를 나눈 영향과 구분하지 못합니다. 의미를 두는 것은 B 의 자릿수 차이, D 의 유지 연결 수, 스레드·메모리의 차이입니다. D 의 연결당 RSS 는 JVM 힙 증가의 계단 때문에 거친 값입니다(기동 직후 RSS 도 220MB 안팎에서 흔들렸습니다). C 는 localhost 라 네트워크 대역이 병목이 아니어서 "큰 응답" 의 의미가 약합니다.
